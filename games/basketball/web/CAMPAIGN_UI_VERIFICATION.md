# 战役界面接入与验证

战役入口、准备房间、中场准备和赛后继续已接入现有平台界面。创建时选择单场、新战役或原密码继续；对手、球员、装备和战术在准备阶段选择。场内控制器继续使用平台个人配置，PC 和手机均放在比赛画面之外。

## 界面与状态

`CampaignPreparationEditor` 只显示服务端进度和合法选择，复用于等待房间、中场及下一场准备。图片使用已提取的原球场和球员头像，并保留本地回退。主场比赛的对手卡片显示实际主场图，不把对方城市误显示成本场球场。

等待房间使用原平台封面、席位、准备和开始入口。已入座玩家按原权限选人，房主管理共享装备和对手；装备仍属于四名热血队球员，不属于网络席位。库存为空或人物未装备时使用简短提示，避免重复展示大量空槽位。

中场和赛后使用公共 `Modal`。关闭弹窗不撤销已确认的选择，普通快照更新不重开；进入新的阶段才显示新的弹窗，也可主动重新打开。第一席在中场完成选择后关闭窗口，按原 START 开始下半场；赛后通过明确的「准备下一场」「继续战役」「开始下一场」请求推进。

准备操作捕获界面当时的 epoch、period、revision 和库存索引。库存按钮的 DOM 标识包含准备版本，防止按下时看到的旧物品在松手时被同一索引的新物品替代。观战者只读，托管期间不显示可执行的真人操作。

打开准备弹窗会关闭控制器输入。控制器异步加载完成时也读取当前弹窗状态，不能使用加载开始时的旧闭包重新启用按键。托管倒计时在弹窗内保持可见，滚动到装备列表底部也不会隐藏；关闭弹窗后仍可在比赛区域看到倒计时。

## 原名称与接口修正

`selection/campaign-labels.json` 保存 32 件装备、5 种战术的原名、编辑译名、原指针与字形编码。`export_campaign_labels.py` 核对原 ROM SHA-256、固定区 C2C8 装备名称指针、九字节原记录和既有角色字形转写；遇到 FF 停止，不能把下一条名称的字节拼到前一条。源字形核对图保存在 `.local/campaign-ui/equipment-source-names.png`。

中文名称属于编辑翻译，不声称官方译名，也不从名称推断装备效果。名称文件 SHA-256：`e8c8a798f4752a186c0e362fba5ceb77dc79cd8a7d0897774370d24a598ff0ac`。

浏览器验证发现并修复了两个接口问题：

- Go 的 `[]uint8` 会输出 Base64 字符串。公开的对手列表改为整数数组；原规则组件仍保留 byte 类型。
- 战役选项增加显式 `entry: "new" | "password"`。原密码继续的空输入由服务端拒绝，不能因为等待房间的保存按钮绕过原生表单校验而静默变成新战役。旧的未声明 entry 请求仍按有无密码识别。入口表单直接反映当前选项，恢复或其他客户端更新不会遗留旧的选择状态。

## 验证结果

先编写浏览器流程和失败场景，再实现组件；保留初始缺少组件的失败日志，以及对手列表格式、异步加载权限、倒计时可见性、入口意图和提示文字对比度的失败记录。

| 验证 | 结果与限制 |
| --- | --- |
| 独立 React 场景 | 23 项通过，使用真实 HTTP 记录和中场快照，覆盖图片回退、权限、鼠标旧索引保护、原生触屏、弹窗开关、创建选项和倒计时 |
| 延迟加载权限 | 使用实际 Board 和受控延迟客户端，验证弹窗后不能启用输入；该用例不模拟 Wasm 或比赛规则 |
| 真实平台页面 | 37 项通过，使用生产前端构建、实际登录、创建、准备请求、双人加入和开局；覆盖战役密码准备及原单人／合作／对战入口 |
| 服务端 race | 8 个相关顶层测试通过，覆盖入口、库存校验、胜负继续、下一场、真实 HTTP／SQLite 和托管确认 |
| 样式 | 检查最终计算颜色，准备区和入口提示正文对比度至少 4.5:1；保存 PC 与 320px 截图，手机弹窗内部滚动，无横向溢出 |
| 构建与边界 | TypeScript／Vite 构建通过；20 个游戏无跨游戏实现导入 |

真实平台战役部分验证到等待房间提交；实际开局段复核原双人对战及控制器布局。独立场景的赛后操作记录请求，不替代从自然创建开始完成整段战役的浏览器验收。
