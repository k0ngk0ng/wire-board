## 如何理解覆盖状态

| 层级 | 可以证明 | 不能据此证明 |
| --- | --- | --- |
| 原数据／静态分析 | 某原表、分派入口、参数或条件已定位 | 原版自然执行到该分支、完整玩法可运行 |
| 隔离原函数对照 | 所列输入下，Go 与未修改原指令的输出一致 | 菜单可以合法选择该配置、自然整场能触发、完整世界衔接正确 |
| 原自然运行对照 | 指定原输入轨迹的调用或连续阶段一致 | 未出现的队伍、装备、人物、场地和动作已经覆盖 |
| Runtime 接线 | 冷配置和真实世界流水线可以使用该能力 | 所有可达分支无缺口、完整比赛必然结束 |
| 完整比赛门禁 | 指定配置从开局到结果，重复和恢复一致 | 所有内容、原版逐周期完整对局、真人联机整场或画面全部一致 |
| 平台／发布验收 | 实际产品入口、权限、操作、音效、素材和联机经过验收 | 引擎的局部测试可以替代此层 |

所有原来源绑定用户提供的 ROM，SHA-256 为 `0fa28f60abb8d2ccbbeee90e79e3fa160a5cf32feb90f47ebf1a89168cff569b`。本文数字 ID 指原程序的队伍、人物槽或场地编号，不是已核实的中文显示名称。当前仅纽约场地及默认国夫队／纽约队身份有现成记录；其余名称需从原菜单文字与选择记录核定，不能从建筑外观或球队编号猜出城市，也不能假定队伍 ID 与球场 ID 必然对应。

## 下一批最小验收配置

以下是按独立风险拆分的下一批，不是缩小最终内容范围，也不是声称用少量配置覆盖全部组合。先列失败场景和验收，再改实现；保留固定种子 `0x12345678`、原时钟、48,000 视频帧上限、每 300 帧及中场恢复、两次重复与 Native／Wasm 摘要一致。遇到首差保留前态并恢复原分支，不换种子或缩短比赛。只有新变更影响到相应边界时才补跑关联回归，不运行其他游戏。

1. **剩余场地隔离批：** Court 3、4、5、6、7 分别用既有 `[0,1]` 球队、`[0,1,0,1]` 人物跑混合和四电脑，共 10 个配置。先以固定默认阵容定位场地缺口；Court3 正在进行。每场另用原指令及正常控制器路径核验专属机关，Court6 必须实际触发奖励并比较 RNG、比分、音效和显示，不能以无触发整场代替。完成后再登记新场地可用。
2. **球队／人物优先诊断批：** 在已稳定的 Court1 先固定 7 个四电脑配置：`Teams=[0,1], Characters=[2,3,0,1]`，以及 `Teams=[0,t], Characters=[0,1,0,1]`，`t=2..7`。这会优先暴露球动作 16／17／14／15／18／19／22、team2 避让 11、team5 mode34、team7 mode33／35。未触发的分支继续补对应原函数和自然输入证据，不能将一场结束当作该队所有能力通过。
3. **32 人物展开批：** 上述阻断恢复后，使用 8 组轮转对阵 `[t,(t+1)%8]`，每组两套阵容 `[0,1,2,3]` 与 `[2,3,0,1]`，共 16 个四电脑配置，覆盖每队四个人物在两个进攻方向。该批仍不覆盖人物在队内两个位置互换或所有合法搭档；由原菜单清单补齐允许的互换／搭档与特殊协同。再按原分支增加真人控制／托管接管，不能用全电脑替代操作验收。
