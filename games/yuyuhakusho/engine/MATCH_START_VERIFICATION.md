# 战斗初始化：实现前验证范围

恢复 `0xf2a4` 的阶段 0／2 及实际场地、对象和人物建立 helper；之后交给已恢复的阶段 4～26。人物初始化 `126c8` 在对象调度时另行执行，不能在建立 header 时提前执行。场地、控制器和原版队伍／角色编号不等同于平台席位。

可能失败的场景：资源载入请求与就绪门槛混淆；阶段 0 落入阶段 2 的顺序改变；暂停／模式禁用仍改写；硬编码两人而遗漏四槽或空配置；角色或控制器的 byte 减一哨兵错误；仅替换坐标高 word 却丢掉小数；错误清空旧人物、子槽或其他 header 字段；队伍／原通道／目标位号混用；动作初始化过早；色盘只写后十色却覆盖公共前六色；录制／播放及模式选项遗漏；HUD／场景呈现写入被当作玩法状态或完全忽略；库或存储失败泄漏早期变化；把隔离原 CPU 输入当作自然菜单可达性。

必须先保存完整原 CPU 自然返回和明确私有输入的边界，再编写测试、记录真实缺实现失败，最后写独立规则。原内核同输入的完整 RAM／视频基线必须不变。比较实际改写的对象、全局、色盘和呈现区域，事件按已证明格式适配原版输出。生产层使用具名状态／请求，不携带完整 RAM，不执行 ROM 或发布资源。

## 已恢复的规则与请求

`StepMatchStart` 覆盖阶段 0／2 的完整规则部分，返回 `MatchStartOutcome.Events` 有序请求，不执行硬件渲染：

- 阶段 0 设置视频模式和声音请求 4，恢复已确认的视频／反馈默认值，清理呈现存储的请求由 `reset` 表达；拷贝初始 64 色并发出该场地的实际资源清单请求。阶段改为 2 后立即落入资源忙检查，新清单令其保持等待。
- 阶段 2 在资源忙标志清零后才建立全局、相机、边界、管理／场地／背景对象及选中的人物 header。原人物 `126c8` 初始化在之后各自调度时执行，建立 header 不提前初始化或推进人物。
- 四人物槽固定在 `8400/8800/8c00/9000`。选中角色的配置 ID 先减一；通道配置 0 减一得到 `255`，表示原 AI 通道。队伍从配置直接复制；目标位号、原对象 ID 与平台席位分开。
- X 只替换高 word，地面 long、层和深度按原四槽不同值建立。未选中的槽、其他旧字段和三个子槽均保留，没有额外清空。模式对象与场地附加对象也只在实际条件下建立 header。
- HUD 模板、名字三个 glyph ID 和 portrait 坐标／属性／图形参数以实际调用顺序发出 `words/name/portrait`。HUD 布局表只有已证明的 1～4；布局 4 不请求 portrait。公共前六色不被换色覆盖。槽 2 原分支不执行换色，槽 2／3 使用同一第三色盘槽，不能擅自补成四色盘独立覆盖。

场地 ID 是原 word 偏移 `0/2/…/14`，不是猜测的场地名称。资源 ID、回调种类和 glyph ID 只是已恢复数据的来源身份，不是可执行地址。模式 0／4 的附加对象及轮次参数按原表建立；未解码的轮次索引原子失败，不读取邻接代码。

## 验证与明确排除

原版固定输入的 3,600 帧完整 RAM／视频基线一致，取得 21 次自然完整返回（阶段 0 一次、阶段 2 二十次）。另有 1,047 个声明私有输入的完整规则调用，覆盖 8 场地、16 种人物选择掩码、11 角色、4 个 HUD 布局、原 AI／人类通道、颜色 byte 边界、配对／全同队配置、模式／选项和解码轮次表。4 条单初态流共 16 次调用，只在声明点把资源忙清零，均从阶段 0 到阶段 4，不回灌原中间状态。

比较包含完整四族人物 4,096 bytes、固定其他对象／header 的未写字段、整个 `A000..A1FF` 512-byte 全局区、`E080..E0FF` 64 色和四槽声音队列；这里没有声音队列例外。系统区只比较已恢复的具名字段与默认字节，原始完整窗口仍随夹具保留。

硬件文本光栅、精灵缓存、SAT 和 DMA 队列不在规则 API 内。测试明确排除 manager `8048..807F` 的 portrait 暂态及系统区未建模的硬件呈现字段，不能把结果描述为完整 `f2a4` 硬件回调或全部 RAM 逐字节一致。与这些排除相对应的 reset／资源／HUD／名字／portrait 请求参数由原 CPU 调用点被动观察，并逐个与 Go 事件比较；未将呈现结果注入生产状态。

测试文件在生产实现前建立。首次预实现 Go 命令因已清理的 `GOTMPDIR` 不存在而在编译前退出，原日志保留；没有获得本模块独立的缺符号 red，不将此环境错误冒充缺实现失败。随后建立工作目录并执行真实原 CPU 规则对照与连续调用，原生竞态和 Node/Wasm 的三项聚焦测试通过。此项证据限制与完整来源／日志摘要见[验证记录](testdata/match-start-validation.json)。

## 复跑

```sh
mkdir -p .local/md-yuyuhakusho/tmp
PYTHONDONTWRITEBYTECODE=1 python3 scripts/yuyuhakusho/capture_match_start.py \
  --out .local/md-yuyuhakusho/match-start-replay
GOCACHE="$PWD/.local/go-cache" GOMODCACHE="$PWD/.local/go-mod" \
GOTMPDIR="$PWD/.local/md-yuyuhakusho/tmp" \
go test -race -count=1 -run '^TestMatchStart' ./games/yuyuhakusho/engine
```

Wasm 使用研究工具说明中的执行器。当前聚焦验证采用 `match_lifecycle.go`、`match_start.go` 和 `match_start_test.go` 的显式源码构建，父阶段仍须执行整个游戏包回归。
