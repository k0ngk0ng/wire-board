# 声音优先级消费：实现前验证范围

目标为完整 `0x37c44..0x37cb2`，输入是四槽队列、当前优先级 `FFF800`、已选择声音 `FFF809` 与原 `0x3a50e` 数据。只恢复队列仲裁和改写，不把它称为音频合成或完整声音生命周期。

失败场景：扫描顺序 A→D 与 D→A 混淆；声音代码 0 下溢后的空槽分支错误；索引减一或最大 254 越界；比较时漏掉低 7 位掩码或改变同优先级覆盖；把候选 byte 的符号位提交条件与比较大小混淆；特殊优先级 FF 被当成普通最大值；特殊分支漏清当前槽、错误清理后续特殊槽、错误覆盖选择或错误提交当前优先级；无新选择时清掉旧 F809；覆盖声音区其他字节；记录不完整、观察器改变原版基线或误判异步来源；只保留按字段摘要而漏掉完整原 RAM 写入；以每步原输出回灌 Go 输入；将 255 个可索引代码说成 255 个可播放音效。

先保存原版完整调用及声明的原 CPU 隔离输入，再写测试并保留缺实现失败，最后编写独立 Go 语义。自然执行必须保持固定 3,600 帧 RAM／视频基线；比较整个声音 RAM 窗口及范围外改写，覆盖队列各位置、符号与优先级边界、特殊分支及连续消费。生产代码不读取 ROM 或运行模拟器。

## 已恢复语义

`ConsumeSoundQueue` 从 D 槽到 A 槽扫描四个 byte。每槽先清零；代码 0 不查表，其他代码用 `code-1` 查原 PC 相对表 `0x3a50e`，最大索引为 254。只读 `SoundPriorityTable` 为按值传入的 255 项数组，不访问 ROM。固定来源表及字节摘要保存在 [sound-queue-priorities.json](testdata/sound-queue-priorities.json)；这证明输入代码的查表范围，不证明全部代码对应可播放声音。

普通候选按 `priority & 0x7f` 与当前候选低 7 位比较，大于等于就改写候选和 `FFF809`，因此相同优先级由后扫描的低地址槽覆盖。扫描完成后，只有候选完整 byte 为 signed 非负时才写 `FFF800`。比较用的掩码与最后提交用的符号条件是两件不同的事；原表包含 `0x81` 的负 byte，不能把它当作普通大优先级。

优先级 `0xff` 进入独立分支：当前槽已经清零，将声音代码写 `FFF809`；后续低地址槽只保留优先级同为 `0xff` 的请求，其他全部清零。后续特殊请求既不覆盖本次选择，也不停止扫描，而是留给下一次消费。本分支直接返回，不提交之前暂存的普通候选优先级。

## 原 CPU 验证

79 次自然完整调用、12,156 个隔离原 CPU 调用及 16 条单初态流共 128 步，与独立 Go 结果完整一致，原生竞态与 Node/Wasm 均通过。每次比较全部 256 bytes 声音 RAM 窗口（`FFF800..FFF8FF`），包括 `FFF800`、`FFF809`、四槽及全部保留字节；自然和隔离执行均无范围外 RAM 改写，全部 3,600 帧 RAM／画面基线一致。

自然记录全部非空，其中 28 次走特殊分支。隔离覆盖全部 255 个非零代码、四个槽、候选值与比较边界、所有空队列当前 byte，以及原表各优先级类别的四槽组合和不同代码的同级覆盖。连续流只初始化一次、不恢复存档和回灌期望状态；其中 46 步有非空队列，验证特殊请求保留后逐次被消费，之后才为空队列。

先前动画采样的 8 次队列差异已与本次消费者逐项关联：帧、人物、动画入口 SP／SR、队列前后值完全一致，且消费者以更高 SR 掩码及更深栈进入，均从普通出口 `0x37c8e` 返回。见[跨采样关联](testdata/sound-queue-animation-links.json)。这些关联没有把期望改写注入 Go 动画函数，也没有伪造完整声音时基。

79 次自然消费的原返回地址均为 `0x375d0`，观察到的入口 SR 包括 `270x` 与 `200x`。[调用方片段](../../../docs/research/md-yuyuhakusho/static/sound-queue-callsite.txt)确认：驱动入口 `0x375a6` 的正常路径在若干前置辅助后检查四槽 long，非零才于 `0x375cc` 调用本消费者，随后执行 `0x37cb4`；`FFF807` 非零则走另一条驱动路径。当前实现不据此假设固定 IRQ 周期，驱动前后辅助、完整调度、合成和平台音频播放仍须恢复。原消费者指令见[既有静态证据](../../../docs/research/md-yuyuhakusho/static/animation-records-consumer.txt)。
