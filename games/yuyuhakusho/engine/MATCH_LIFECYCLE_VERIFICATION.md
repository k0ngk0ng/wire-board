# 对局／回合生命周期：实现前验证范围

先通过原版对象头和实际分派确认管理入口，再恢复开局、胜负、回合转移及结束条件。不能仅从人物生命值推断胜者，也不能把菜单、碰撞管理器或人物动作当作对局管理器。

可能失败的场景：错误识别对象或回调；对象初始化与活跃分支混淆；把视频帧当成所有逻辑计时；忽略暂停、慢动作和外层场景状态；只观察双人默认模式却声称四人／组队规则完整；把 KO 请求或负生命值直接作为结算；同队存活、平局、超时或同时 KO 分支遗漏；固定对象编号被误当平台席位；原 word／byte 的有符号、回绕与临界值错误；转场绘制副作用遗漏或混作规则；以隔离样本冒充自然完整对局；观察器改变原 RAM／画面；下游错误后部分改写；回灌预期中间态代替连续规则。

完整原 CPU 输入／输出夹具先于独立规则与单元测试实现。自然跟踪保持同输入完整 RAM／画面基线；补充输入或私有初态明确声明并提供未挂钩原内核对照。所有原始证据、来源摘要、覆盖模式和剩余边界须保留，不把未到达路径描述为不存在。

## 已恢复边界

原版主对象 `FF8000` 的活跃入口是 `0x9ad0`，其阶段 20 等待战斗子管理器结束。真正战斗管理器是 `FF8040 / 0xf2a4`；分派表从 `0xf2c0` 开始，包含阶段 0～26 的 14 项。当前 `StepMatchLifecycle` 完整恢复阶段 4～26（12 项），包括原函数内部的连续落入下一阶段。阶段 0／2 的场地、人物和资源初始化仍明确返回未恢复错误；暂停或 `A096==2` 的入口跳过先于该校验。

阶段 4／6 启动及等待淡入；8／10 建立开战呈现并等待 256 次更新；12 解除输入停用并立即落入 14。阶段 14 的第一个检查只考虑回调为 `0x12668` 且生命非负的人物，第二个检查排除的却只有生命恰为 `-1024` 的人物。两次均只剩同一个原版 `BaseTeam` 后才进入 16，因此负生命但尚未退场的人物仍能阻止结算。阶段 16／18 停用输入、等待 64 次更新并继续等待全部负生命者完成 `-1024` 退场。阶段 20 才确定队伍结果、更新原版统计并建立结果呈现，随后落入 22；24／26 启动淡出、等待淡出完成，再按 `353a` 清除 `FF8040..<FFA000` 的全部对象。

结果使用原版队伍码，不能直接当平台席位。没有唯一有效队伍时保留 `0x8000`（`MatchDrawCode=-32768`），平台应映射为显式和局。`Results` 事件发生在阶段 20；对象会在阶段 26 清空，不能在清场后才从人物生命推导胜负。原版本地统计也不等于平台积分。

返回的 `ClearWorldFrom=0x8040` 是完整对象区清理请求。调用者须清除该区所有类型及尚未纳入此类型视图的字段；测试对完整原始对象区应用清理请求后，逐字节核对原 CPU 输出。`Intro`／`Results` 是对应原调用点的呈现请求，不执行 ROM 地址。

## 已验证结果

3,223 次自然完整阶段、5,140 个有界语义隔离调用与 4 条单初态流共 3,112 步全部一致，原生竞态和 Node/Wasm 的三项顶层测试通过。另 40 个刻意使用队伍 128／255 的原 CPU 输出作为 `reference-only` 留在隔离夹具；它们会越过已解码的 taunt 配置／ROM 表边界，独立规则明确原子拒绝，没有将相邻代码字节编造成玩法。

完整比较 `FF8040..<FFA000` 的 8,128 bytes 对象区、`FFA000..FFA1FF` 的 512 bytes 全局区、淡入淡出寄存器、两组 128-byte 色盘、160-byte 统计窗口、暂停／输入掩码、按下通道和四槽声音队列；没有字段屏蔽或队列例外。大夹具按记录流式解码，避免测试堆中重复保留数百 MB，但压缩和解压后的完整内容均受 SHA-256 约束。

自然观察使用固定输入至第 3,600 帧后松开控制，未挂钩原内核与被动观察内核在全部 5,500 帧 RAM／画面一致。观察到第 4,226 帧进入退场后阶段、第 4,292 帧写入胜队 4 并建立结果呈现、第 4,757 帧清场。此自然场景只有两个角色及一组模式字段，不证明全部菜单、人数和正式规则模式已验收。其余队伍、四对象、同时退场／和局、统计条件、按键及数值边界来自声明私有初态的原 CPU 调用。

连续流只初始化一次，之后只外部更新已声明的生命值和淡出完成标志；四条均运行至真实清场。它们没有人物运动、碰撞或色盘驱动的完整世界循环，不可作为完整独立对局证明。当前闭合的活跃阶段没有独立对局倒计时结算；其他模式或外部调度仍未证明，结果显示计时不冒充对局超时。

## 共享统计及录制别名

| 状态字段 | 24 位 CPU 地址 | 语义 |
| --- | --- | --- |
| `HeadToHead[16]` | `FFFF60..FFFF6F` | 四控制通道的胜负对表 |
| 保留区 | `FFFF70..FFFF7F` | 本函数不改写，完整测试仍保留 |
| `WinsByCharacter[64]` | `FFFF80..FFFFBF` | 每通道 16 个角色位置 |
| `LossesByCharacter[64]` | `FFFFC0..FFFFFF` | 每通道 16 个角色位置 |
| `LossesByCharacter[60:64]` | `FFFFFC..FFFFFF` | 与输入录制的 `EndMarkers` 同一实际存储 |

世界组合层必须为统计尾部和 `EndMarkers` 提供同一存储或双向适配，不能为两个组件各维护一份独立值。原统计只在 `A062==2` 时更新；`A088==2` 和其他值使用不同配对方式，计数在 200 饱和，已有头对头计数达到 200 时会提前跳过后两项更新。该行为按原顺序保留。

隔离 CPU 的普通 `FFE0` 返回跳板与统计表别名。成对诊断实际观察到 `0xf84c` 对 `FFFFD9` 的计数写入把栈中的返回 `0000f78a` 改成 `0001f78a`；把栈设到原游戏使用的 `FF00` 下方后，统计写入相同且返回地址不变。最终全部隔离使用 canonical `A5=ffff8040` 和安全栈，未修改 Go 来迎合错误私有寄存器布局。见[栈诊断](testdata/match-lifecycle-stack-diagnostics.json)。
