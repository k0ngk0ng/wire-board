# MD 输入窗口协议的先行失败场景

本清单先于实现和测试。范围是完整 12-bit 输入窗口及有界历史，不包含世界时钟预测、自动托管决策、呈现快照或网络连接调度。

- FC 8-bit 或 JavaScript 32-bit 打包截断 MD 的 X／Y／Z／Mode；控制器边沿或录制历史被从世界 digest 排除。
- 非法按键高位、自动化掩码高四位、零帧、重复／倒序／跳帧或 uint64 溢出被接受。
- 同一 tick 的控制权变化未出现在本帧记录中；把客户端自动化标记当成服务端授权。本协议只传递每帧显式标记，应用由共享 tick 边界决定。
- 窗口超过 120 帧、游程为 0／超过 120、游程总量与帧数不符、字节截断或尾随 run 被接受。
- 相邻相同游程被拆开，或 base64 带不规范 padding／空白／非零尾部位仍通过，导致同一内容多种摘要。
- 未知版本被猜测解码；空窗口有多个表示；firstFrame 使用 JSON number 后损失大于 2^53 的整数。
- JSON 缺字段、重复／未知／null 字段、错误类型、尾随 JSON、非规范十进制字符串仍被接受。
- Push 接受坏历史或变动调用方 slice；超过 120 帧仍保留历史；编码／解码失败返回部分结果。
- 字节编解码往返通过，但实际规则状态、输入边沿、RNG 或有序事件在连续对局中分歧。
- 把大存档、像素、音频、内部调度历史或每帧完整世界作为常规同步载荷。

先运行缺实现 red，再冻结测试。完整对局从空 `engine.NewChuSession` 与固定配置开始；直接逐帧输入和经过窗口编码／解码的输入各推进自己的世界，完整状态、事件与生命周期比较。这里不是原 CPU 音频或任意客户端渲染的证明。
