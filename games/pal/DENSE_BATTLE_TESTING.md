# 密集法术动画验收

从未修改血量的原版三人战斗开始，用原版指令触发施法。先在同核心记录原生参考帧和实际等待时间，再在正式浏览器页面测量。保留[同步性能预算](PERFORMANCE.md)，原版故意重复画面或延长帧间时间时，按原版序列比对，不能以加速补足帧数。

## 实现前失败场景

1. 首次施法时临时下载特效，导致首帧或多帧看不到；浏览器读到同样的权威帧后再次施法才恢复。首战和缓存命中分开记录。
2. 权威定时、WebSocket 或画布各自跳帧；仅凭定时回调次数、菜单箭头或 rAF 频率达标就宣称法术动画完整。
3. 绘制时跳过特效、震屏、命中或伤害字样，或者在可见命中之前改变画面中的资源。以原版索引画面及战斗公开状态校验顺序。
4. 固定按 40 毫秒回放原版不同的法术等待时间，改变镜头、重复次数或战斗节奏；测量不能把原版有意静止的同一张画面计成变化。
5. 为补慢端而逐帧发送资源、完整存档或无界缓冲。单独记录游戏包、重同步包、规则推进、原生输入和画布结果。不得通过改法术、敌人、伤害、奖励或资源质量换取帧率。
6. 资源提示丢失已装备的合击、临时队员、敌人替换或召唤图集，或提示错误阻止旧档续玩。验证提示只含图集身份；让同一场战斗从原快照继续对照。初次准备和后续更新不能反复下载同一份已准备的素材。
7. 为等待额外素材而冻结服务端帧时钟、重新触发全局就绪或在手机画布之外增加控件。资源等待只限制当前看到该战斗的浏览器提交指令。

## 修复前基线

同一原版核心、实际房间随机种子和普通体力下，三名原版队员执行一次合击。动作区间从第一帧开始到原版进入奖励等待前为止：原生计时 2.72 秒，69 个 40 毫秒帧，68 张不同画面。其中，特效图集 50 的 7 张画面依序绘制，原帧 3 本来就连续停留两次。原生状态在最后一张特效帧结算敌人伤害，之后才移除敌人，最终获得 3 文。

| 浏览器场景 | 整幅画面变化／秒 | 可见间隔 P95／最长 | 实际看到的特效 | 游戏包 P95 |
| --- | ---: | ---: | ---: | ---: |
| 桌面，延迟交付首个特效 CDN 响应 600 毫秒 | 19.49 | 51.0／666.3 毫秒 | 0/7 | 4582 B |
| 320px 手机，游戏连接 RTT 约 200 毫秒，CDN 正常 | 24.63 | 51.2／84.6 毫秒 | 6/7，缺第一张 | 4581 B |

两个服务端均按顺序发送了 7 张不同特效及一次原版重复帧，规则耗时 P95 分别为 16.28 和 16.21 毫秒。另一次未注入 CDN 延迟的桌面冷启动，发布清单的特效图集描述文件耗时 528 毫秒，随后图片耗时 55 毫秒，同窗观察到 616.5 毫秒无画面更新。受控桌面试验只延迟同一已发布 URL 的真实 HTTP 200 响应，原始内容保持；无上传、资源替换或游戏数据修改。

整幅画面变化用于测连续性；特效用原版图集中不同帧的不透明索引像素和原版调色板逐帧识别，另外保留原生与实测整幅哈希用于诊断。整幅哈希尚未建立逐帧对应关系，不用它判断此次特效缺帧数。手机虽达到整幅变化率，仍漏了第一张特效，因此这两组均未通过。当前只覆盖此场合击，结算的可见顺序、更多不同速度的法术及密集并行房间仍须另验。

## 素材准备与候选复测

原生核心读取当前队员已学法术、按原装备规则得到的合击、现有敌方施法能力，并解析召唤人物和后续火系图集的依赖。服务端只公布去重的图集编号。战斗夹具准备 13 个相关图集；抽换队员和敌人后，原版引擎给出不同清单，其中有原敌方法术和召唤依赖，不再包含李逍遥的合击。

浏览器按提示取回并解码已发布的图集，最多四路准备请求。同一图集在该画布内合并请求并复用解码结果。正在开局或续档时计入平台原有加载；进行中的更新只限制当前浏览器提交战斗输入。该提示不会修改规则、阻止保存或重置画布。保留核心没有提示时仍使用原有绘制路径。

| 候选场景 | 整幅画面变化／秒 | 可见间隔 P95 | 实际特效 | 规则耗时 P95 |
| --- | ---: | ---: | ---: | ---: |
| 桌面，首个 CDN 响应延迟 600 毫秒 | 25.00 | 51.5 毫秒 | 7/7 | 17.84 毫秒 |
| 320px 手机，游戏连接约 200 毫秒 RTT，首个 CDN 响应延迟 600 毫秒 | 24.27 | 65.6 毫秒 | 7/7 | 42.84 毫秒 |
| 手机同条件单独复测 | 25.00 | 50.8 毫秒 | 7/7 | 20.93 毫秒 |

桌面和手机均在首次操作前请求并解码图集，真实施法期间未再次下载这两个 CDN 对象。桌面最长画面间隔由 666.3 降到 83.3 毫秒，手机复测为 84.7 毫秒；原版有一帧重复停留，P95 预算保持 80 毫秒。图集 50 的 7 张画面按序出现，结算 3 文；同步消息 P95 为 4795 字节。桌面达标，手机画面与消息达标，规则回调仍未达到 20 毫秒阈值。未将结算像素顺序、透明图层全部像素、其他法术或并行密集战斗计为通过。

新旧原版内核在同种子、同输入下的战斗状态、随机数、规则时钟和奖励一致；新核心保存后由全新运行器续档，逐帧一致。实际应用进程使用旧规则包保存，再换本地候选包重启，原账号继续、旧页面拒绝和手动回退均通过。候选包保留前两代核心，源代码重建一致。发布预检复用原规则数据和两个旧核心对象，仅新核心及新规则清单需要发布。图像和音频内容、地址不变，本轮无上传。

## 复现

在仓库根目录为每轮准备新的作用域和独立前端产物：

```sh
. scripts/env.sh
scope=dense-repeat
dense_dir="$PWD/.local/pal/performance/dense-battle-$scope"
mkdir -p "$dense_dir"
(cd web && npm run build -- --outDir "$dense_dir/web-dist")
PAL_BOARD_BROWSER=1 PAL_BOARD_ENTRY=battle PAL_SCREEN_BATTLE_CURRENT=1 PAL_DENSE_BATTLE_SCOPE="$scope" go test -v ./internal/server -run '^TestPALBoardBrowserFixture$' -count=1 -timeout=8m
```

夹具写出 `url` 后，在另一个终端执行 `python3 -B games/pal/tests/dense-battle-browser.py dense-repeat --asset-delay 600`。手机另开作用域，传入 `--phone --delay 100`。脚本按实际房间随机种子生成原生对照，保留 Canvas 采样、定时记录、网络数据、截图和加载的前端摘要。实际基线保存在 `.local/pal/performance/dense-battle-desktop-cdn-cold/` 和 `.local/pal/performance/dense-battle-phone-cdn-default/`。

候选测试先执行：

```sh
. scripts/env.sh
python3 -B games/pal/build/native.py --battle-fixture 1 --fixture-field 18 --out .local/pal/dense-battle-candidate/battle
python3 -B games/pal/build/native.py --battle-fixture 17 --fixture-roles 3,2,5 --fixture-field 18 --out .local/pal/dense-battle-candidate/alternate
PAL_BATTLE_ASSETS_E2E=1 go test -v ./games/pal/engine -run '^TestOriginalBattleAssetPlanAndFreshSavedContinuation$' -count=1
```

使用新前端构建和独立作用域，在启动夹具时加 `PAL_DENSE_BATTLE_NATIVE=candidate`，运行浏览器采样时加 `--require-prepared`。桌面和两轮手机原始证据分别在 `dense-battle-desktop-prepared`、`dense-battle-phone-prepared-settled` 和 `dense-battle-phone-prepared-repeat`。本地候选包目录与发布预检分别记录于 `.local/pal/dense-battle-candidate/server-package.json` 和 `server-preflight.json`。
