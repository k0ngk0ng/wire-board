# 两个单人房间并行播放「风神」验收

两名独立账号在同一个服务进程中的不同单人房间操作。桌面走正常连接；320px 手机经过固定传播延迟代理，实测约 200 毫秒游戏 RTT。两个浏览器分别保留原生输入、游戏流和自己前台画布的像素，两个房间仍各自只有一名玩家。

## 实现前失败场景

1. 两端实际施法错开，或其中一端只开放房间并未播放密集法术。两次原生施法及风系特效持续区间必须重叠至少 2000 毫秒；分别核对服务逻辑时钟和两个前台画布。
2. 两个账号、浏览器或房间混用了同一快照或同一个 WebSocket 流。用原账号、房间编号、同一服务实例标识及不同操作代次核对。
3. 延迟端拖慢另一房间，导致原版帧丢失、重排或长时间停住。每边都须收到并在实际画布呈现 16 张图集画面依序循环三次；各自的原版逻辑区间 2360 毫秒，网络观察允许与该区间相差不超过 200 毫秒。原版的同画面停留不计成额外变化。
4. 用每秒消息数替代原版像素，或者让后台标签采样而声称两端都有实画面。两个独立前台会话都要保留全部 rAF 样本；P95 不超过 35 毫秒，原版画布尺寸保持不变。
5. 为追帧而推送整个存档、错过原版伤害顺序或多发奖励。沿用游戏消息 P95 16 KiB 门槛，核对两局独立消耗一次真气、发放一次 3 文奖励。单房间另用原 20 毫秒规则回调预算；本试验另外记录并行负载下各房间回调，不能用它改写原预算。

## 结果

两个账号在同一服务中创建不同房间。两局原版「风神」特效同时推进，在服务时钟上重叠 2283 毫秒，实际前台画布重叠约 2217 毫秒。原始计时记录中有 58 对规则回调在两个房间同时执行。

| 客户端 | 游戏 RTT | 已收原版帧 | 可见特效变化 | 规则回调 P95 | 全部 rAF 间隔 P95 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 桌面键盘 | 0 毫秒（本机读数） | 60 | 48 | 17.68 毫秒 | 18.0 毫秒 |
| 320px 手机触摸 | 202 毫秒 | 60 | 48 | 17.34 毫秒 | 18.3 毫秒 |

桌面的风系特效跨度为 2360 毫秒，手机为 2359 毫秒；两段召唤形象及 16 张风系画面依序循环三次，每局各扣 64 点真气并获得 3 文，游戏消息 P95 均为 1755 字节。两份图集描述在两端各模拟 600 毫秒响应延迟，实际施法前取齐，资源地址保持。这次测量覆盖固定网络传播延迟，没有模拟断开、丢包或任意数量房间。

首轮两边画面均完整，但采样器挂在文档上，没能记录由窗口输入层接收的桌面键盘事件。保留首轮的未通过记录。采样器改为在窗口捕获事件后，才得到两边可信原生输入、规则事件和画布的完整复测。未修改规则、画面或线上资源，无上传。

## 复现

在仓库根目录使用现有[「风神」原版核心](SUMMON_WIND_TESTING.md#复现)和同一候选前端，以新作用域启动测试服务：

```sh
. scripts/env.sh
scope=summon-parallel-repeat
out="$PWD/.local/pal/performance/dense-battle-$scope"
mkdir -p "$out"
(cd web && npm run build -- --outDir "$out/web-dist")
PAL_BOARD_BROWSER=1 PAL_BOARD_ENTRY=battle PAL_SCREEN_BATTLE_CURRENT=1 PAL_DENSE_BATTLE_NATIVE=summon PAL_DENSE_BATTLE_SCOPE="$scope" go test -v ./internal/server -run '^TestPALBoardBrowserFixture$' -count=1 -timeout=8m
```

待写出 `url` 后，在另一终端运行 `python3 -B games/pal/tests/parallel-summon-browser.py summon-parallel-repeat`。脚本启动两个隔离的浏览器会话，等双方都选中原版法术后安排确认；每端分别留下实际像素、游戏流、输入和结算，统一按同一服务的房间时钟核对。

首轮和通过复测的原始证据位于 `.local/pal/performance/dense-battle-summon-parallel-primary/` 和 `.local/pal/performance/dense-battle-summon-parallel-verified/`。
