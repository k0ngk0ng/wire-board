# 原版连续画面性能验收

先从原版规则记录基线，再对照冻结预算。画面采样须和权威状态、原生输入及网络包各自计数。

## 实现前失败场景

1. 原版战斗时钟为每帧 40 毫秒，但服务器按 50 毫秒推进和合并发布，短动画帧被挡在画面之外。记录真实原版交替箭头的像素变化、网络帧及发送间隔。
2. 为提高画面频率而改变原版回合、输入或动画速度；不能插入重复画面凑数，也不能以空白或全屏调色的变化假冒移动。
3. 加速公共调度导致其他游戏帧变密，或慢连接积压拖住规则。即时通知仍只保存一个待处理信号，收件人重取最新画面。
4. 调度过点后产生累计相位偏差，或补播保存前的按键。沿用原生剩余等待时间、当前权威时钟和既有输入到期限制；战斗存读档冻结剩余等待。
5. 路线步数不足、踩到碰撞或触发事件后，仍宣称持续移动达标。移动样本要匹配静态地图位移，同时核对权威脚步上限和释放后停止。
6. 只统计已更新的帧或拿接收间隔冒充显示间隔。保留全部 rAF、真正发生变化的画布帧、权威帧、消息字节和网络往返。

## 实测结果

原版战斗的 25 个连续规则帧用时正好 1000 毫秒；在人工给唤醒加入 0、6、1、4 毫秒延迟后，下一帧仍使用原生未消费的等待时间，不累积偏差。保存时还有 17 毫秒，离线 24 小时后由另一运行器恢复，仍剩 17 毫秒，箭头、队员和钱袋不变，旧操作代次失效。实际手机战斗的法术菜单及已提交治疗指令各保存续玩一次，治疗、三人选招和 3 文战利金通过。

| 场景 | 可见变化／秒 | 可见间隔 P95 | 全部 rAF 间隔 P95 | 每条游戏消息 P95 |
| --- | ---: | ---: | ---: | ---: |
| 战斗基线 | 6.18 | 348.8 ms | 18.2 ms | 4107 B |
| 战斗桌面单房间 | 25.09 | 51.1 ms | 18.3 ms | 4106 B |
| 战斗 320px 手机单房间，RTT 201 ms | 24.73 | 51.0 ms | 18.4 ms | 4105 B |
| 客栈探索基线，键盘长按 | 9.60 | 117.2 ms | 17.8 ms | 2358 B |
| 客栈探索复测，键盘长按 | 10.92 | 116.6 ms | 18.3 ms | 2698 B |
| 两个战斗房间并行，采样端 RTT 203 ms | 10.36 | 298.4 ms | 18.4 ms | 4106 B |

战斗使用原版三人夹具、无加血，采样每组 5.5 秒。画布只计入原版当前行动者箭头中两帧共同的不透明像素，WebSocket 同时核对原帧号 68／69；背景、菜单高亮和重复包不能增加计数。桌面与延迟手机分别测得 138 和 136 次可见变化，规则回调 P95 约 15.5 和 16.4 毫秒。动作密集和多房间战斗不以这组箭头样本验收。

客栈用原版可走路线实按约 0.73 秒，前后权威位置均相差 7 个原生脚步，释放后持续停止。地图位移验证旧版 7 次、复测 8 次可见变化；复测包含本地预测领先的一步，释放后与权威收敛。短窗口包含起步，不能把每秒 10.92 次解读成原版逻辑加速。

保留三份失败原始样本：首次复测浏览器刷新长停顿；另一次前台刷新稳定，但显示和网络都有间歇丢帧；两个战斗房间并行时，窗口内有 275 次规则回调，采样房间只收到 119 个游戏包，未达到预算。不合并失败样本和单房间通过结果，也未找到能证明所有并行丢帧原因的证据。

仙剑启用平台截止时间帧，普通模块仍按原来的 50 毫秒处理。战斗以原生剩余时间安排下一次检查，连接只保留一个待推送信号。共享平台在竞态检测下通过加载、慢连接、默认和即时推送、定期检查点及计时唤醒检查。两个测试前端的导入包名不同，核对后仙剑代码相同；原版核心、音频和其他资源未变，无上传。旧 7902 个不可变产物及隐藏点进度保持。

## 复现

```sh
. scripts/env.sh
PAL_CADENCE_E2E=1 go test -v ./internal/server -run '^TestPALBattleCadenceRetainsOriginalFramesAndSavedDelay$' -count=1 -timeout=3m
PAL_BOARD_BROWSER=1 PAL_BOARD_ENTRY=battle PAL_SCREEN_BATTLE_CURRENT=1 PAL_CADENCE_TRACE=1 go test -v ./internal/server -run '^TestPALBoardBrowserFixture$' -count=1 -timeout=25m
```

另开终端运行 `python3 -B games/pal/tests/selection-performance-browser.py battle optimized --continuous`。手机延迟版加 `--phone --delay 100 --scope phone-rtt`，先结束旧夹具、另起仅有一个战斗房间的新服务。桌面、手机战斗均用前台标签；开始采样前验证刷新，采样期间记录全部 rAF。探索服务改用 `PAL_BOARD_ENTRY=performance`，参数改为 `field optimized --continuous`。在隔离副本复跑旧实现时将 `optimized` 改为 `baseline`，保留原归档数据。原生测试、房间证据、截图和失败轨迹可用 `python3 -B games/pal/tests/continuous-performance-evidence.py` 核对。

后续[并行房间复测](MIXED_ROOM_PERFORMANCE.md)在保留旧失败原样的基础上通过同范围原版箭头验收：两个单人战斗同时运行，手机 200 毫秒 RTT 时画面约 24.91 次变化／秒，其余客户端在同窗持续收帧。
