# 密集战斗帧的内存开销

在同一个普通体力候选核心中，测量原版三人合击。固定既有 20 毫秒规则回调预算、40 毫秒原版规则帧和浏览器实测门槛。

## 实现前失败场景

1. 私有续行直接覆盖还可恢复的旧内存，后续步骤失败时旧档已变。测试须先执行一个有效原版帧，再在同次批处理中拒绝非法输入。
2. 复用其他对局或调用方持有的内存。公开快照继续独立可读；同一原始存档在两个事务中并行前进，不能相互污染。
3. Wasm 已关闭或增长后，结果仍引用其内存；二进制快照的内存、栈指针、摘要、随机数和画面信息必须能在全新运行器继续。
4. 为减少延迟而跳过格式／内存校验、改单帧逻辑或改变外部格式。新旧格式的验收和真实保存续玩仍须通过。
5. 只看到某一轮手机通过就宣称优化。真实房间的前后回调、画布、可见帧和网络记录分开保留；孤立测试另记录每个真实帧累计分配的字节，避免用某一次本机调度波动证明节省。

## 实现与结果

优化前，用真实 320px 手机页面在约 200 毫秒游戏 RTT 和 600 毫秒首个特效资源延迟下做 CPU 采样。该次规则回调 P95 为 18.85 毫秒，之前同条件也有 20.93 和 42.84 毫秒的失败结果。规则回调的采样显示，收集原生快照及其内存 SHA-256 是主要成本之一。不能把一次自然达标当成优化收益。

私有续行原本每帧另外分配一份完整内存。现在仍在独立 Wasm 实例推进规则；完成观察和元数据检查后才复制回该事务已有的内存，再按原规则生成完整摘要。事务通过同一份状态同时持有内存和元数据；复制句柄不会分离两者。独立事务仍从各自的存档创建，公开快照仍返回独立内存。快照版本、压缩格式、完整 SHA-256、进度和原版帧数均未变。

同一普通体力核心的 58 个实际原版战斗帧保持 2320 毫秒，前后首尾原生内存摘要一致。累计分配从每帧 30.62 MiB 降至 22.13 MiB，减少 27.7%。这是累计分配量，并不等于进程常驻内存，也不表示每次帧耗时都同比下降。

| 同范围手机场景 | 服务端规则回调 P95 | 画面变化／秒 | 特效 |
| --- | ---: | ---: | ---: |
| 优化前，带 CPU 采样 | 18.85 毫秒 | 25.00 | 7/7 |
| 复用私有内存后 | 18.81 毫秒 | 25.00 | 7/7 |

优化后 320px 手机前台画面间隔 P95 为 50.5 毫秒，游戏消息 P95 为 4795 字节，实际特效仍在施法前取齐，同一个合击保持原顺序和 3 文战利金。本次测量证明该场景满足现有预算，前后两次测量的耗时差不足以证明普遍提速。未验收密集并行房间、其他速度的法术或正式发布。

真实保存回归包括四个独立原版事务并行、有效首步后的第二步失败回滚、复制句柄、公开快照不被改写、旧 gzip／JSON 与当前二进制格式、损坏拒绝。实际应用用旧规则包保存，换候选包重启后，原账号继续、手动读档、旧输入拒绝及旧场景存档恢复均通过。没有改核心规则或上传资源。

## 复现

在已有[战斗候选核心与浏览器夹具](DENSE_BATTLE_TESTING.md#复现)的工作区运行：

```sh
. scripts/env.sh
PAL_DENSE_MEMORY_E2E=repeat go test -v ./games/pal/engine -run '^TestOriginalDenseFrameMemoryAndIsolation$' -count=1
PAL_DENSE_MEMORY_E2E=repeat-race go test -race -v ./games/pal/engine -run '^(TestOriginalDenseFrameMemoryAndIsolation|TestNativeSnapshotBinaryEnvelopeAndLegacyContinuation)$' -count=1
```

使用新作用域运行原浏览器战斗夹具及 `--phone --delay 100 --asset-delay 600 --require-prepared`。如需采样，在 Go 夹具命令加 `-o "$dense_dir/server.test" -cpuprofile "$dense_dir/rule.cpu"`。前后浏览器证据分别为 `.local/pal/performance/dense-battle-phone-cpu-baseline/` 和 `.local/pal/performance/dense-battle-phone-memory-reuse/`。
