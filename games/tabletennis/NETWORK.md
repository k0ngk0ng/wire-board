# 实时同步设计

按用户要求，主要参考泡泡堂与热血篮球的现有实现；只复用公共平台通道，不从另一款游戏导入规则或输入代码。

- `games/bubbleparty/web/input.ts`：一次性动作边沿不能被后续普通状态覆盖；使用席位序号和比赛代次，发送窗口受平台 `inputWindow` 限制。
- `games/bubbleparty/web/prediction.ts`、`clock.ts`：本地预测只改善显示，不能生成得分或其他权威结果；丢包期间预测有上限，重新同步后以服务端状态校正，不累积漂移。
- `games/basketball/web/network-input.ts`：输入绑定房间、用户、席位和比赛；快照可以确认已接受的序号，不必等某个 HTTP 响应。旧请求晚到不能修改新局，取消、失焦、托管及连接变化清理自己的旧输入。
- `games/basketball/PLATFORM_CONTRACT.md`：同一时间窗口内的短操作必须保留，取消具有明确优先级，计时与恢复不得重置世界或让输入不断推迟系统帧。
- `web/src/realtime-stream.ts` 与 `main.tsx`：通过 `BoardProps.act` 使用已鉴权 WebSocket，断开时保留平台 HTTP 路径；不另建游戏专用连接。

乒乓球输入额外绑定当前一分与当前来球。每次划动是一条不可合并的击球意图；同一来球最多接受一次，不能把连划积攒为之后几拍。提前缓冲和历史补偿均有上限，已结算的一分不回写。动作只有服务端确认后才能改变球路和比分；本地球拍立即响应，短时的球显示预测必须以确认轨迹校正，不能产生假的触网、落台或获胜。

发球、球拍触球、落台、碰网、漏接、比分统一使用服务器时间轴。按需加载和全屏只改变呈现，不改变局内时钟或输入身份。

验收包含真实双端连接、请求重排／重复、快照先于 ACK、取消抢先、50／150／250ms 延迟、抖动、断线后恢复、换席、托管接管与服务端重启。确认延迟、画面位置误差和输入到本地反馈时间分别记录，不能用单机流畅代替联机验收。

当前补偿边界为 350ms。真实 TCP 测试在标称 250ms 延迟下记录到同一来球输入年龄 253ms；此前 200ms 限制会误拒绝。终点碰撞在补偿窗口关闭后才发布，避免合法迟到回球撤销已播报的二次落台。补偿不扩大物理击球范围：球越过本方端线后 0.33m 即结束有效接球窗口。

球拍移动使用独立的 `motionSeq`，包含二维拍位、自动接球深度、比赛代次和换边标记。移拍不推进规则，不改变比分、球路、击球序号或计时期限；重复、过期和旧换边移动不会覆盖新位置。客户端合并尚未发出的移动，每 80ms 最多发送一次、至多一条在途；击球不等待移拍确认。HTTP 回退只有一个可靠请求槽位时优先保留击球，连续移拍恢复后重新发送当前位置。

本人球拍立即跟随指针；远端使用实际位置快照和短时有界外推，并显示最近移动形成的淡化轨迹。电脑提前移动到公开来球的接触位置，击球后通过同一移动接口随挥。移动不得读取其他席位私有决策，也不生成虚假的出球事件。
