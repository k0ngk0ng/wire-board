# 全部游戏创建与人数切换验收

用户报告：乒乓球无法选择双人；各房间选择人数第一项后跳到第二项。

实现前冻结失败场景：公共选择框发送了错误人数或在确认后回跳；等待房间仍持有旧人数的分队、角色或装备数组，导致服务端拒绝；切换人数触发旧规则编辑器以旧人数覆盖新设置；离散人数被连续范围替代；人数低于已入座人数仍允许提交；固定人数被改写；创建默认人数超出当前模式上限；刷新或 WebSocket 更新撤回刚成功保存的人数；快速切换或请求失败后显示未保存的选项；桌面与手机行为不一致。

使用实际应用、认证、HTTP、SQLite 与 WebSocket，从创建卡片进入每款游戏，逐项切换所有公开合法人数，并重复选择第一项；核对请求、服务端人数、界面选择值及座位数量，刷新后仍一致。固定人数检查唯一选项。先覆盖全部已上架游戏，再重点验证乒乓球 2／4 人与受人数影响的模式配置。结果放在 `.local/_common/room-capacity/verification/`。

入口：`ALL_ROOM_CAPACITIES=1 node --test web/tests/room-capacity-browser.test.mjs`。仅创建本地测试账号与房间，不修改生产数据。


运行前准备同源码构建的 `web/dist/contra-delivery.json` 及 `.local/_common/room-capacity/runtime/pal` 的正式 PAL 规则包。后端使用 `production.Open` 加载与正式服务相同的全部模块，不用精简游戏集合冒充全量检查。当前实际覆盖 32 款 × 2 个宽度；数量由封面目录与服务端可用列表比对后动态确定。另为四款已复现游戏配置非默认规则，验证人数切换保留不相关的赛制、场馆、难度、时限与角色选择。
