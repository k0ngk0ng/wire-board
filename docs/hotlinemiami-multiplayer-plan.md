# 《迈阿密热线》多人混战方案

2026 年 11 月 21 日的开发前方案。游戏 ID 为 `hotlinemiami`，实现与验收入口见[游戏说明](../games/hotlinemiami/README.md)。

建议以第一代《迈阿密热线》为对照，首版支持 2 至 4 人自由混战，提供 3 张关卡改编地图、约 5 个角色造型和 7 类武器。采用限时击杀、快速复活；保留俯视像素画面、致命攻击、近战、武器拾取与投掷。先用一张地图完成真实联机的操作响应验收，再扩充内容。

用户最后确认仅做混战，因此首版不提供队伍设置。下文人数、内容数量、赛时和性能阈值均为开发前建议，并非已经实现或实测的结果。

## 混战规则建议

| 项目 | 首版建议 |
| --- | --- |
| 人数 | 2 至 4 个席位，允许真人、电脑和主动托管混合参与 |
| 比赛 | 默认 3 分钟，击杀加 1 分，自杀减 1 分，时间到最高分获胜 |
| 平分 | 最高分并列时按平台显式和局结算，所有参与者积分变化为 0 |
| 死亡 | 约 2 秒后复活，保持比赛连续进行 |
| 出生保护 | 建议 800 ms，主动攻击或投掷前立即解除；保护期间不能充当挡弹或堵门的实体 |
| 出生位置 | 优先避开敌方当前视线、近距离威胁和最近交火点；全部位置受威胁时选择风险最低处并保留保护 |
| 伤害 | 枪击和有效近战保留致命感；普通武器投掷以击倒为主，具体例外经原版对照后登记 |
| 地图对象 | 保留影响战斗的墙、门、玻璃与家具；移除剧情、通关触发器和固定敌人 |
| 角色属性 | 造型与玩法分离，速度、生命、碰撞体和武器规则一致 |

原版面具加成、Boss 抗性和角色专属武器限制不直接带入混战。Biker 等造型也可以使用公共武器池。这是为多人公平作出的规则改编，需要在玩法速查中写清楚。

击倒后可以起身或被处决；处决占用短暂动作时间，执行者仍能被第三人攻击。投掷、拾取、处决和门碰撞的优先级须在实现前冻结，避免客户端各自解释。暂不加入人质盾牌等需要额外双人绑定状态的动作。

计分只认可服务器确认的有效击杀。同一受害者同一生命只能结算一次。服务器按明确的帧内顺序处理攻击与死亡；真正同时生效的攻击可形成互杀，不按网络消息到达先后偏袒某一席位。

## 地图选择与参考图

首版目标为 3 张，以下为候选，最终楼层和人数适配须在恢复碰撞与原版画面后确定，不能仅凭关卡名称冻结。

| 候选 | 预期用途 | 改编重点 |
| --- | --- | --- |
| No Talk | 紧凑的小地图 | 检查是否能容纳 4 人；过小则只允许较少席位或更换候选 |
| Full House | 主要室内混战地图 | 检查房间绕行、门口争夺与出生点分布 |
| Push It | 夜店风格地图 | 保留空间辨识度，检查家具遮挡、开放区域与近战路线 |

采用适合独立交战的单层或连续区域。原版上下楼的关卡切换不能直接搬进混战，否则会产生传送口埋伏、加载等待和出生点不公平。保留原布局与美术，新增或调整的出生点、武器点和连接必须单独记录。

房主在创建房间第二步通过图卡选图；等待房间允许房主继续修改。每张图显示可识别的实际游戏区域缩略图，展开后可看更大的俯视图和推荐人数。预览来自最终可玩地图的同一数据，显示主要墙体、房间和出生区域，不用宣传图替代。

只有混战一种赛制时，不再添加重复的模式下拉框。地图图卡、人数和赛时构成同一规则分组，沿用平台准备和开始按钮。

## 角色与武器

角色控制在约 5 个，候选为 Jacket（鸡头主角）、Biker、Bodyguard、The Father 和 Richter。Richter 是关键敌对角色，不把他写成已核验的 Boss 分类。无需扩展成整套面具收集或引入第二代角色。

各角色在席位卡片中提供头像和实际俯视造型预览。允许重复选角，通过清晰轮廓、有限配色和姓名区分玩家，不叠加席位数字。角色选择只允许修改本人席位；房主可修改电脑席位。

需要特别核验 Boss 的动作覆盖。原版 Boss 可能只有特定站姿、专属攻击或剧情动作，不能假设都存在通用持枪行走动画。先形成「移动、持枪、近战、投掷、击倒、死亡」素材清单；缺少动作时，以原版造型为依据补齐或适配，并登记新增帧，不能把补绘描述成原版提取。

首版武器建议覆盖 7 类，以代表性武器落地：

| 武器 | 主要差异 |
| --- | --- |
| 手枪 | 精准、适中的射速和有限弹药 |
| Uzi 冲锋枪 | 连射、散布与快速耗弹 |
| M16 步枪 | 远距离压制，配合开火间隔和弹药约束 |
| 霰弹枪 | 多弹丸、近距离覆盖和较长射击间隔 |
| 小刀 | 快速近战、较短攻击范围 |
| 棒球棒 | 更明显的挥击范围与动作承诺 |
| 武士刀 | 具有辨识度的近战范围和攻击节奏 |

武器表是设计候选；射速、散布、弹药、攻击范围、投掷是否致命及子弹运动方式须通过 REA 对照后记录。原版 PvE 武器不天然适合 PvP，混战平衡调整与原版参数分别登记。

每人可在房间中选择起始武器，武器卡片显示实物小图；对局中可以投掷、拾取和换枪。建议保持有限弹药与换武器的节奏，不额外添加背包系统。复活使用所选武器的限定初始弹药，地上掉落武器保留实际剩余弹药，不能通过拾取或刷新补满旧枪。起始弹药与地图武器分布在首张地图实战后统一调整。

## 操作与画面

PC 默认建议为 WASD 移动、鼠标瞄准、左键攻击、右键投掷、E 拾取／互动、空格处决。动作通过平台统一控制器声明和改键，不在游戏内再建设置入口。原版操作与平台默认键位的差异要进入玩法速查。

手机使用左侧移动、右侧瞄准／攻击双摇杆，并保留拾取、投掷与处决按钮。轻推右摇杆瞄准，越过明确阈值后攻击；松开停止。不默认加入自动锁定。实体手柄使用左摇杆移动、右摇杆瞄准、扳机攻击，经公共连续值输入接口进入相同规则。

战场以像素图集绘制，优先 Canvas 2D 的缓存静态层与动态实体；首张地图的真实负载决定是否有必要改用 WebGL。血迹、尸体和粒子必须设定数量与存活上限，不能随比赛时间无限增加。减少动态效果时降低装饰震动与闪烁，不减少子弹、碰撞和规则推进。

各设备保持一致的有效战斗视野，不能让宽屏额外看到远处敌人。手机按相同比例布局并保留可用的触屏区，不能把整张大地图缩到人物无法辨认。全屏、玩家信息、音频与结算沿用平台能力。

## 即时同步与流畅度

建议独立 Go 规则引擎作为服务器权威实现，并将同一运动与碰撞规则编译为浏览器 WASM。业务坐标、速度、角度、计时、散布与随机数统一使用明确单位的整数或定点整数，避免 Go 与浏览器规则漂移。

采用本人预测、服务器权威战斗、远端插值的方案。客户端可立即预测自己的移动、转向、举枪、枪口与投掷表现；伤害、弹药、拾取、击杀和复活最终由服务器决定。共享规则不意味着客户端可以上传命中结果或权威状态。

建议的初始预算为 60 Hz 规则推进、独立的显示刷新、最高 30 Hz 的紧凑动态投影，关键战斗事件及时发送。接入 `RealtimeDeadlineFrames`，不能把普通 50 ms 平台检查当作 60 Hz 射击时钟。频率和预算须在开发前冻结，测后不通过放宽指标获得验收。

- 输入带操作代次、序号和目标帧。移动与瞄准可合并最新连续值；射击、投掷、拾取、处决等短按边沿有序保留。
- 分开确认「服务器已收到」和「规则已应用」。不等待单个 ACK 才继续采样、显示或发送。
- 本人根据已应用序号回放未确认输入。微小位置误差只平滑修正显示；穿墙、死亡、复活等必须立即服从权威，不能用平滑拖延规则。
- 初始建议将预测限制在 150 ms 内，远端插值通常为 33 至 67 ms，硬上限 100 ms；超出窗口明确恢复，不能靠无限缓存维持假流畅。
- 此方案只预测部分世界，常规网络发送必要输入、动态状态增量、事件和确认信息。地图、素材、完整存档和累计历史不随帧发送。
- 每条连接独立维护有界队列、事件游标与恢复窗口。慢玩家不能阻塞服务器或其他玩家；缺口、重连与状态失配通过快照恢复。
- 失焦、隐藏、断线和操作取消立即清理瞬时输入；恢复不补播后台攻击，也不自动启用托管。真人仅通过平台入口主动托管。

一击致命还需要独立设计有限命中补偿。先确认原版子弹是怎样运动和碰撞的，不能为省事把所有枪械直接改成即时射线。服务器保留短期战斗历史，补偿建议上限 100 ms；客户端时刻必须经服务器时间锚点和接收时刻约束，禁止任意指定过去或未来。

历史回溯须同时检查目标、墙、门和生命代次。高速子弹采用连续碰撞，不能跨帧穿过细墙；不能因迟到的攻击伤害已经复活的新生命。射线武器与飞行弹丸分别制定补偿规则，避免既回溯命中又二次推进同一弹丸。平台目前没有可直接复用的通用射击延迟补偿模块，这是新作工作量的一部分。

## 验收先于实现

先写失败场景和可复跑的多浏览器 E2E，再实现复杂功能。共享引擎若需隔离验证，先列出失败场景，再写针对性测试；不得实现后补写单元测试。

| 场景 | 开发前建议的验收条件 |
| --- | --- |
| 正常网络 | 定义为 RTT 不高于 80 ms、抖动不高于 20 ms、无注入丢包；双人和 4 人正式房间分别测试 |
| 键鼠响应 | 原生输入事件到首次可见响应 P95 不高于 33 ms |
| 触屏响应 | 原生触屏事件到首次可见响应 P95 不高于 50 ms |
| 显示推进 | 目标 60 FPS；帧间隔 P95 不高于 20 ms、P99 不高于 33 ms，同时报告实际可见更新数量 |
| 密集交火 | 4 人连射、门碰撞、投掷、尸体与血迹达到上限后仍按相同预算验收 |
| 快慢端共存 | 一端 RTT 250 ms 或受限带宽时，正常端仍达到自己的响应预算；慢端独立恢复 |
| 多房间 | 多个满员房间并行，报告规则推进耗时、截止落后和服务容量，不以单房间代表容量 |
| 手机 | 320 px、常用手机尺寸、横竖屏与全屏；验证人物辨识、按钮命中、多指与输入释放 |

必须覆盖的失败场景包括：

- 快速按下并松开被合并丢失；斜向移动加速；瞄准跨越角度边界；按键在隐藏后未释放。
- 两人抢同一武器；空弹药开火；投掷后原武器仍可射击；拾起武器意外补满弹药。
- 子弹穿过薄墙；门开关与射击同帧；投掷与近战同时命中；互杀；重复击杀结算。
- 复活后被旧生命的迟到事件击杀；保护状态攻击；保护实体挡弹；出生点全部受威胁。
- 乱序、重复和迟到消息；断线重连；后台恢复；恢复快照后重播枪声；慢端拖住快端。
- 本人预测与服务器碰撞不一致；普通确认反复重建显示时钟；显示刷新率与规则频率不整除。
- 电脑完整对局、混合真人、主动托管与手动接管；机器人动作超时拖慢规则帧。
- 地图或造型切换后预览错误；无权修改他人；等待房间修改与开局并发；资源失败后提前就绪。
