# 可回退手动存档

平台已接入可选手动回退能力，原有保存退出功能不因此自动开放回退。真实仙剑对白、原版自然战败及独立结局页面已通过读档验证；完整游戏和发布仍待完成。适用范围和验收要求见[平台存档规则](../rules/saved-games.md#可回退的手动存档)。

## 接口边界

游戏通过可选 `SupportsCheckpoint` 声明单人非竞技回退能力，同时接入 `SupportsSave`、`ResumeSaved` 和 `RestoreCheckpoint`。当前实例与上次成功手动存档独立保存；后者包含完整 `Match`、对应逻辑时刻、保存时间及原对局身份。普通规则帧、恢复和数据库持久化不能修改该基准。

读取沿用认证房间命令 `load_checkpoint`，使用当前未结算的原房间和 `MatchID`。平台从基准的逻辑时刻重新映射时钟，通过游戏的 `RestoreCheckpoint(Context, saved, active)` 恢复并清理输入，再经过公共加载门槛。回调接收两份独立副本：上次手动存档，以及读取前的当前实例；失败时二者均不提交。原子提交同时更新当前实例、操作版本下限及去重记录；手动基准保持原样。

恢复后的操作代次必须高于读取前当前实例，不能仅由旧档中的代次加一，也不能假设平台房间版本大于游戏代次。仙剑的初始代次含随机前缀，实际回退已复现旧代次重用；须使用 `active` 中的真实边界保证单调性，否则旧页面在更新房间版本后仍可能携带旧控制状态。

## 实现前失败场景

1. 能保存退出的游戏都自动开放回退，包括多人、竞技或已结算对局；没有成功保存也伪造可读存档。
2. 当前实例推进后覆盖基准，战败时读到已经失败的当前数据；继续游戏、重启或加载重发资源。
3. 陌生人、观众、电脑或伪造席位可以读取；公开响应泄漏基准的原生内存、私有数据或随机状态。
4. 同一读取重试、重复 nonce、并发请求或旧页面在已经继续行动后再次回退；恢复时名册或原对局身份变化。
5. 模块恢复回调失败、修改传入快照后失败或数据库提交失败，损坏当前实例／基准，提前公开成功或产生结算。
6. 恢复补跑离线时间、延长原操作预算、保留按住按键，或者控制代次回退／与读取前相同。
7. 第二次手动保存失败却覆盖第一份基准；成功后仍读到旧基准；基准与其时钟不在同一事务提交。
8. 原始核心战败后的文件槽重载被当作平台读档，静默重开剧情；已知失败演出未保留。
9. 旧版只有退出快照时猜测已经推进的当前状态就是手动存档；跨核心更改身份绕过兼容检查。
10. 新增读档控件占用游戏区行高，手机无法确认或保存／全屏手势误触画面；按钮状态与后端实际能力不一致。

首批 E2E 使用真实认证 HTTP 与 SQLite，先验证独立基准、资源／随机恢复、输入边界、权限、重试、事务失败和进程重启。随后接入仙剑实际战败及 PC／手机页面。公共契约、原版失败边界及具体游戏存档必须分别留证。

## 数据与事务

`Room.Module` 保存当前实例，`Room.Checkpoint` 独立保存格式 1 的手动基准，包含 `format`、`matchId`、`match`、`clock` 和 `savedAt`。`Match.CheckpointKey` 仍是即时规则持久化的关键阶段标识，两者用途不同；普通即时持久化不能替代手动基准。

创建对局时验证 `Unrated`；注册时验证单人、保存及恢复回调，不允许多人或竞技注册借用回退能力。每次成功保存退出，在同一房间事务内替换基准。继续或读取不会替换它，失败保存保留此前基准。读取前核对格式、原对局身份、规则信封和游戏回调，未知格式或运行器缺失均保留原数据并拒绝。

读取成功后，平台建立新的 `SetupVersion`，清除旧保存确认与续玩确认，取消当前托管，并经过公共加载就绪门槛。原账号、房间、规则选项及 `MatchID` 保留，不产生结算。公开摘要只增加 `supportsCheckpoint` 和 `checkpointSavedAt`，不暴露基准正文。

`RestoreCheckpoint` 的两个 `Match` 都是独立副本。回调必须保持原进度、资源、随机状态及已接受行动，清理瞬时输入，并保证新操作代次高于 `active`。仙剑复用已有的原生续行和输入释放，再以上一当前实例的真实代次为下限；不把旧内存绑定到新核心。

## 已通过的检查

- 公共 HTTP／SQLite 生命周期：保存后推进与模拟失败、精确资源／随机恢复、旧操作与旧读取拒绝、读取重试后不再次回退、模块回调修改参数后失败的隔离、数据库失败、重启及第二次手动保存的原子替换。
- 能力限制：未接入游戏不开放，错误的多人／保存／计分策略注册拒绝，竞技实例不能开始回退模式。24 个同时读取请求在单服务实例内只有 1 次恢复提交；没有新增战绩或积分流水。race 检查通过，不将其描述为多进程部署验收。
- 实际仙剑：从真实新游戏的对白保存，继续正常阅读 3 页，再恢复相同的原版页面、画面、队伍与资源。使用当前平台版本发送旧原版页面指令仍被拒绝，原生手动基准字节不变。结果为 `.local/saved-games/pal-checkpoint-dialogue.json`。
- 实际 PC／手机 Board：在原版结局独立夹具中推进到后续位置，再通过平台读取恢复完整冻结边界和音轨。手机确认使用原生触摸，弹窗留在全屏内；读取后保持全屏及 1280×800／320×200 画布。结果为 `.local/pal/checkpoint-ending-board-browser/result.json`。这是结局夹具，不替代真实拜月之后的完整流程。
- 实际原版战败：从真实新游戏取得战斗入口，以普通防御自然全队倒地。失败动画保存退出不替换此前可恢复基准；手机继续失败演出后读取，完整边界一致且能继续触摸选招。PC 无存档时可取消或确认新旅程，新 `MatchID`、原版新游戏及后续页面操作通过。两端保持全屏，详见[原版战败验收](../games/pal/GAME_OVER_TESTING.md)。
- 旧的多人保存退出／续玩、本人私有仙剑存档、公共加载时钟、公共保存页面及视区最小尺寸回归通过。既有不支持回退的游戏继续沿用原有能力。

读档加载保留原全屏容器，加载层在游戏区内呈现。游戏代码／资源准备与实际画面就绪共同满足后才确认；不能因保留已挂载画面而提前解除门槛。仙剑按每次加载代次重新验证画面，并清理此前的输入与媒体状态。

## 原版战败接入前的补充失败场景

1. 把盖罗娇等原版允许战败后继续的剧情误标为普通死亡，或修改体力／敌人／随机结果来制造失败。
2. 原版失败演出没有播放，文件槽重载静默重开新游戏，或者当前实例仍在等待不可用的原生输入。
3. 在失败演出或等待恢复时保存退出，覆盖此前仍可恢复的手动存档，导致只能反复载入失败局面。
4. 没有此前手动存档时伪造一个存档；把重新开始当作同一已结算对局的回退，或重复发放原版奖励。
5. 只用对白或结局媒体的回退证明原版战斗死亡及读取已经通过。真实失败、原版演出、读取和后续正常操作仍须分别验证。

上述首批战败流程已按对应验收留证。`PreserveSavedCheckpoint` 保留可回退基准，`Restartable` 经即时游戏信封同步本人重新开始权限；两者变化均先持久化再发布。此能力不增加剧情完成数，也不替代后段允许战败分支或整款游戏验收。
