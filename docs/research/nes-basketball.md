优先核对用户本地源码：`/Users/jason/Sources/github.com/morluto/rea`。本轮读取的版本为 **6.5.0**，提交 `9d6651e5b5296da31a88042a061bdc6f4e769f10`。该目录当时没有 `node_modules/` 和 `dist/`；未安装依赖、修改源码或注册 MCP。

| 已核实能力 | 对本任务的作用 | 限制 |
| --- | --- | --- |
| Ghidra 的 6502 裸二进制入口 | 查询指令、函数、伪代码、调用和数据引用 | 不解析 iNES、Mapper 或 bank switching，也不执行原游戏 |
| CLI 与 MCP | 让分析脚本或编码代理持续查询具体地址、保存分析证据 | 仍需可用的 Ghidra；REA 本身不是反编译引擎 |

关键证据位于 REA 本地文件：

- `docs/raw-binary.md`：明确支持 `6502`，也明确排除 iNES、卡带 Mapper 和换页。
- `src/ghidra/GhidraRawBinaryLanguage.ts`：绑定 `6502:LE:16:default`。
- `src/domain/rawBinary.ts`：检查载入地址和完整文件不能超出 16 位地址空间。
- `bridge/ghidra/ReaGhidraPrepareRaw.java`：文件偏移 0 必须映射到指定入口，并尝试在那里创建函数。
- `scripts/verify-real-ghidra-6502.mjs`：使用自有汇编夹具验证真实 Ghidra 通路。
- `docs/installation.md`：要求 Ghidra 12.1.x、匹配宿主架构的原生反编译器及完整 JDK；当前文档要求 JDK 21 或更新版本。

本 ROM 的 PRG 为 128 KiB，不能整体作为一个 6502 线性文件导入。需依据 MMC3 的 8 KiB 程序页映射，把 ROM 偏移、页编号、CPU 地址和采样帧关联起来。相同 CPU 地址在不同换页状态下可以指向不同代码，不能只用 `$8000` 这类地址标记函数。

此外，REA 当前把「文件载入起点」和「初始函数入口」绑定在一起。截取一页时，页首不一定是函数；随意把整个页面指定为入口会误判数据。接入时要以已确认的代码片段起步，保留缺失依赖；完整分析则评估独立的 NES／Ghidra 导入脚本或对导入接口的扩展。不能简单截取一段、改起点后就宣称调用链完整。

NES CPU 与通用 NMOS 6502 也有语义差异，例如十进制算术行为。Ghidra 静态结果需要结合 NES 实际执行校验，不能直接逐行翻译伪 C 得出 Go 逻辑。

## 建议的首个验证范围

先选同一场地、同一人物和可重放的初始状态，覆盖走动、起跳、持球、一次传球和一次投篮。实现前先留下逐帧按键、初始存档摘要、画面记录、换页状态和已确认的 RAM 字段，之后才编写对应的 Go 行为。

提前记录需要验证的失败场景：

- 连续按键、松开与同帧组合键导致动作丢失；按住与新按下被混为一谈。
- 小数累积、进位、符号位或定点取整不同，导致移动和跳跃逐帧偏移。
- 人物横纵位置、离地高度与画面坐标混淆，导致球与人碰撞或篮筐判定不一致。
- 同一 CPU 地址在不同页下指向不同逻辑，静态分析误串调用关系。
- 随机状态或初始内存不同，导致投篮结果、电脑选择无法重复。
- 动画表现与碰撞／得分时刻错位，出现尚未接球就持球或尚未入筐就加分。
- 断线、托管、重新接管或恢复存档丢失按键状态，产生持续移动或重复动作。

Go 内核建议提供确定性的一步状态更新，输入为当前状态、每个席位的按键及固定时步，输出下一状态和带帧号的事件。球员、球、动作计时、碰撞、得分、随机状态与电脑策略保持在独立游戏目录，避免散落在公共平台。

每个已恢复行为保存「输入／初始状态 → 原版轨迹 → Go 轨迹 → 首个差异帧」的可重复记录。涉及画面和手感的复杂功能以 E2E 为主；如需独立验证定点运算等小块逻辑，先列失败场景并先写测试。只按本游戏及实际改动的公共契约选择检查范围。

### 已确认的坐标更新

通过改变方向输入、观察角色画面和 RAM，再注册执行钩子，定位到 PRG 第 15 页的 `$EF5F..$EF7E`。这段代码先计算候选横坐标，后续代码还会处理碰撞等修正。

| 数据 | 原版地址（加对象索引 X） | 已确认含义 |
| --- | --- | --- |
| 位置小数 | `$0068` | 8 位小数部分 |
| 位置整数 | `$0075`、`$0082` | 低、高整数位；合计为 16 位整数、8 位小数 |
| 水平速度 | `$0478`、`$0485` | 有符号 16 位速度，低 8 位为小数 |
| 候选横坐标 | `$058E`、`$059B`、`$05A8` | 三字节加法的输出，尚未经过后续碰撞修正 |

执行钩子在 `$EF5F` 读取输入，在 `$EF7F` 读取结果，不修改寄存器或 RAM。六组场景共采集 2,377 条记录，覆盖 7 个对象索引，含静止、正速度、负速度和跨字节进位。对象索引 0 的方向输入和画面变化已关联到当前受控角色；不能据此推断其他索引的全部对象类型。

Go 样例以整数表达同一运算：对 24 位位置加上符号扩展后的 16 位速度，再按 24 位截断。没有引入浮点近似。先写测试并保存 `undefined: AdvanceX` 的失败记录，再添加实现，保存全部通过的结果。

### 反编译输出的实际陷阱

本次 Ghidra 输出的伪代码没有完整表达第二次 ADC 的进位传播。原版指令在低字节加法后保留进位，并将第二次加法产生的进位继续传给最高字节；本次伪代码计算最高字节进位时漏掉了低字节带来的进位。

原版采样中的具体反例：

```text
场景：arithmetic-right，模拟器帧 3574，对象 0
原位置：64640 / 256 = 252.5
速度：960 / 256 = 3.75
原版输出：65600 / 256 = 256.25
照搬本次伪代码的输出：64 / 256 = 0.25
Go 按实际指令重写的输出：65600 / 256 = 256.25
```

2,377 条自然执行记录中发现 1 条这样的反例。这证明 REA 的指令、引用和证据查询有用，同时也说明不能把反编译伪代码直接当作正确的 Go 实现。这里描述的是本次固定工具版本和输出的实测差异，不推断其他处理器或 Ghidra 版本的情况。

FCEUX 使用仓库内配置和限制文件写入范围的进程沙箱。REA 的进程管理需要调用 macOS 的 setuid `ps`，该程序无法在此沙箱中启动；REA 改用显式的工作区目录配置，Ghidra 的 Java 用户目录、缓存及临时目录由其启动器放入会话目录。Swift 模块缓存显式设置为仓库内路径。由于 Ghidra 项目路径不接受点开头的目录，会话临时目录使用忽略的 `dist/nes-tmp/`，不使用 `.local/`。

这些本地工具和 ROM 派生产物未纳入 Git，也未上传 OSS；新检出仓库需重新准备同版本工具及用户提供的 ROM。当前仍未恢复完整的跳跃／碰撞模型、投篮公式、篮筐判定、得分规则或电脑策略。下一步可沿已确认的状态字段扩展垂直运动和球的状态转换，再做相同输入的 Go 对照；不宜直接跳到完整游戏接入。
