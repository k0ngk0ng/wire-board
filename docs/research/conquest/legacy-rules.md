# 征服时代：旧版规则证据

## 参考版本与边界

用户确认的参照是早期 iOS《Age of Conquest: World》，并要求世界、欧洲等地图共用一款游戏。World 商店条目为 `386104577`，当前旧款应用版本为 `1.0.12`，首发记录为 2010-08-17；Europe 条目为 `318280645`，首发记录为 2009-06-16。商店首发日期不能证明当前提供的截图或二进制仍是首发版本。

本次取得官方仍公开提供的 **Age of Conquest III desktop 3.0.5318**，以其随包手册、教程文案和 Java 字节码作为旧系列规则的交叉参照。没有取得 iOS World 安装包，因此 **不能宣称该桌面版本与 iOS World 1.0.12 的规则逐字节相同**。本记录不使用第四代规则。

下载 URL、每份文件的大小、SHA-256、关键类摘要和 REA Evidence ID 见 [sources.json](sources.json)。原包、随包帮助和反编译中间文件只保存在仓库 `.local/conquest-research/`；不将原程序、美术或完整反编译源码作为本游戏实现发布。

## 证据分级

- **直接观察**：官方商店元数据、官方分发包中的帮助与教程文字，以及包内存在的类和资源。
- **静态推导**：下列 Java 类的计算和控制流程。由 CFR 0.152 阅读字节码，保留原始类摘要；尚不代表 iOS 实玩结果。
- **实现选择**：平台人数、公开信息策略、地图简化、暂停续玩等适配，应在游戏 README 单独列出，不能写成原版事实。

REA 用于原包身份与归档清单核验。Java 规则由安装在本机的 JDK 与工作区内 CFR 读取；另通过自写研究探针调用原 JAR 的市场及战斗类。没有启动游戏主程序、登录服务或修改系统配置。CFR 在大小写不敏感文件系统会将 `cg/bu.class` 输出为 `bu_0.java`，本文引用以原始类名为准。

## 回合与指令

`cg/rv.class` 的回合推进、`cg/ev.class` 的排序和 `cg/mb.class` 的校验表明：玩家先形成指令列表，所有列表合并后执行；不按网络请求到达的墙上时钟决定先手。

1. 招募、建设、部分外交与经济指令先执行。
2. 解散、部分特殊指令随后执行。
3. 移动与攻击最后执行。移动首先按该玩家的指令序号升序；同序号按回合开始时领土数较多者优先，再比较总兵力、金币，最后按势力索引较小者优先。
4. 执行时再次校验所有权、行动点、资金等条件。已失去出发地的指令不执行。出兵数会截断到该地当时仍有的兵力。
5. 所有行动结束后执行人口／经济／士气／行动点变化，再执行税收和支出。

手册所说“同序指令在玩家间随机”与该版本比较器不一致。实现参考此包时应遵循代码，并记录这一差异。

行动点使用十分之一点为整数单位。下一回合的整数行动点为：

```text
MP10 = floor(previousMP10 / 2) + floor((2.2 + territoryCount^0.63) * 10)
```

例如一块领土且无剩余行动点时获得 3.2 点。移动、招募各消耗 1.0 点；工事 0.5 点、瞭望塔 0.3 点、城镇 5.0 点、解散 0.1 点。证据为 `cg/ei.class`、`cg/zF.class`、`cg/wP.class`、`cg/pG.class`、`cg/mt.class`。

## 战斗

`cg/bu.class` 的地区防御计算与 `cg/pA.class` 的移动事件给出：

```text
defenseBase = round(defenderTroops * (1 + fort*0.8 + town*0.5 + ruler*0.3))
attackPower = (sentTroops * (rulerTravels ? 1.3 : 1))^1.019
defensePower = defenseBase^1.019
```

攻方必须严格大于守方才能占领。胜方剩余兵力按 `floor(本方兵数 * (1 - 对方强度 / 本方强度))` 计算；失败进攻部队全灭。相等时守方保留领土，守军降至零。公式中的浮点步骤是 Java `float` 与 `Math.pow` 的组合，跨语言精确复现需要保留取整阶段，不能仅比较最终整数。

占领有守军的地区会拆除原工事；原守军为零时不触发此拆除。城镇和瞭望塔不因普通占领被该段逻辑拆除。

**重要矛盾**：随包 UI 文案宣称工事加 50% 防御，而手册与执行代码都是 80%。不能用界面文案覆盖执行事实。

## 金币、招兵、海路与建筑

由 `cg/qM.class`、`cg/nd.class`、`cg/wP.class`、`cg/dA.class`、`cg/pG.class`、`cg/pA.class` 推导：

| 动作 | 规则 |
| --- | --- |
| 招兵 | 每名士兵 1 金币；单次不超过该地区人口的一半；人口相应减少 |
| 解散 | 部队减少、人口增加；不直接返还金币 |
| 工事 | 5,000 金币，提供额外 80% 防御 |
| 瞭望塔 | 2,500 金币，用于相邻地区可见性 |
| 城镇 | 75,000 金币，提供额外 50% 防御及人口增长影响 |
| 海运 | 每运送一名士兵额外花费 2 金币，己方调动和敌方进攻均收费 |

海路不是任意两块沿海领土互通。`cg/rL.class` 读取陆地邻接表和水域节点连接；两块领土需要共享一个水节点，或分别接入互相连接的两个水节点。因此地图须保存经过验证的海路，不能仅凭距离推断。

地区兵力上限 999,999，人口与经济值各上限 100,000（`cg/bu.class`）。这属于该参考包的边界，不是 iOS 已实测边界。

随机场景的默认初始化位于 `cg/aY.class`：势力金币 5,000、行动点 3.2、士气 90%、税率 10%、经济支出 80%、军事支出 80%；所有地区初始兵力 500、人口 25,000、经济 50,000；每个势力得到一个初始地区，带城镇和瞭望塔，不带工事。这是随机场景默认值，不代表每一个预制历史场景。教程要求招募 3,000 后会出现 3,500 兵，因此不能把商店截图中的 3,500 直接当作初始常量。

## 经济与人口

`cg/qM.class`、`cg/rL.class`、`cg/ei.class`、`cg/dg.class`：

```text
production = sum(floor(provinceEconomy * provincePopulation / 50000))
taxIncome = round((production * 0.08)^0.96 * taxRate/10 * morale/100)
economySpending = floor(floor(taxIncome/10) * economyRate/80)
militaryUpkeep = floor(floor(totalTroops/5) * militaryRate/80)
```

80% 军费设置对应约每兵每回合 0.2 金币，80% 经济支出对应约税收的 10%。整除顺序属于规则的一部分。

人口首先按 `1.01 + economyRate*0.001` 增长；城镇再乘以 1.25；随后每个地区把人口快照的 15% 平均分给陆地邻接地区。每个设置阶段受人口上限约束。经济在“人口大于经济”时按 `1.03 + (economyRate-80)*0.03/100` 增长，否则乘 0.99。

有非负金币时，军队按 `1 + (militaryRate-80)*0.5/100` 变化并对应增减人口。负金币时，军队每回合损失约 10%（小于 10 兵时减少 1）。税率高于 10% 会以两倍差值降低士气，低于 10% 则提高士气。完整帝国管理可以通过原版选项禁用，此时税率和支出固定；不能将“禁用管理”理解成没有经济系统。

## 君主、捕获与胜利

君主记录所在地区，并可选择随部队移动；君主不能单独作为另一枚单位行动。`cg/zF.class` 在移动后检查君主所在地区是否仍属该势力，`cg/kc.class` 处理捕获后的割地：

- 若失守后仍有至少 3 块领土，保留 `max(1, floor(剩余领土 * 0.18))` 块，其余归占领者；君主重新放在保留领土中。
- 若不足 3 块，则全部割让并淘汰。
- 余部先降至原兵力的 70%，正金币转交占领者。
- 保留地区按兵力、经济、人口从高到低排序，最后以地图地区索引打破平局（`cg/tS.class`）。

因此该参考包不是“一次夺取王冠必定立即灭国”。这与手册简述也有差别，需要明确参考的是哪个版本。

另一个容易误解的细节：`cg/pA.class` 只在己方调动或进攻胜利后移动随军君主；进攻失败时君主仍留在出发地。因此不能自行增加“随军进攻失败立即死亡”的规则。

`cg/yR.class` 的 Domination 胜利：占有全地图（盟友领土按 100% 计入），**或者仅剩一个存活势力**。后一条件不要求继续占完中立地区。普通 Standard 是另一套多数领土积分规则，不应混入统一地图模式。

## 外交与电脑

外交包含联盟、和平、停火、附庸和宗主；原版有“不启用外交”选项。联盟／和平等会禁止进攻，解除后还需要经历停火回合。主平台如果首版仅开放无外交玩法，应明确锁定这个有据可查的选项，而不是显示外交入口却不实现规则。

旧包电脑策略可在 `cg/rA.class` 阅读，包含招募、保王、边界调兵、攻打弱邻、建筑和外交判断。但部分难度会额外调整电脑金币：最高档增加约税收的 15%，最低档减少约税收的 35%。平台要求电脑与真人同规则，不应复制这些资源作弊；采用正常接口实现策略，并如实记录与旧版 AI 的区别。

## 原始规则类的可重复执行探针

[LegacyRuleProbe.java](LegacyRuleProbe.java) 是本次编写的研究程序，直接调用已核对摘要的原 JAR 市场、战斗、捕获、经济和指令排序类。52 条观察结果及源码摘要保存在 [legacy-probe-results.json](legacy-probe-results.json)。探针运行在新建内存世界，不启动主界面，也不访问游戏服务。

已观察到的例子包括：

| 情况 | 原 JAR 结果 |
| --- | --- |
| 1,000 普通进攻 500 普通守军 | 占领，剩 506 兵 |
| 1,000 对 1,000，无加成 | 守方保留地区，剩 0 兵 |
| 1,000 进攻 1,000 工事守军 | 失败，守军剩 450 |
| 4,000 进攻 1,000 城镇＋工事＋君主守军 | 占领，剩 1,421，工事摧毁 |
| 君主带 1,000 进攻 2,000 普通守军 | 失败，守军剩 710，君主未移动 |
| 1,000 进攻空工事地区 | 占领，剩 1,000，工事保留 |

金币探针确认 1,000 兵招募费用 1,000，海运费用 2,000，3,500 兵在 80% 军费时支出 700；生产量 25,000、税率 10%、士气 90% 的税收为 1,328。

扩展探针确认：

- 君主失守后的剩余领土为 0／1／2 时淘汰，3／5／6／11 时留 1 块，12 时留 2 块，17 时留 3 块。余兵按整数 `troops*7/10` 处理；正金币全部转移，负债不转给占领者。
- 原计划出兵 500，执行前只剩 200 时，实际只移动 200；海运也只扣实际 200 兵的 400 金币。出发地已失守则不执行指令，行动点和金币均不扣。
- 上述截断出兵仍需先通过整条指令的资格检查：原计划海运 500、实际只剩 200、金币只有 500 时，虽然实际运 200 只需 400 金币，原引擎仍因付不起原请求的 1,000 金币而跳过整个指令。招募请求的金币或人口不足也整条跳过，不自动缩小招募量。
- 相同顺序的移动按领土数、总兵力、金币、势力索引逐级决定次序；招募优先于解散，解散优先于移动。
- 单个默认城镇在无邻接迁移的合成局面中，第一次经济推进后人口 34,063、经济 49,500、士气 90%、行动点 4.8、税收 1,770、经济支出 177、军费 100、金币 6,493。探针连续跑过 12 次经济推进，并覆盖负债、高税率、高军费和人口跨境迁移。
- 负债士气扣减发生在本轮收支结算之后，以最终金币是否为负判断。原金币 -10,000 时收税 1,773、支出 267、结余 -8,494，士气最后才由 90 降到 89；原金币 -100 时同样发生负债减兵，但结余已为 1,406，士气保持 90。不得先减士气再用降低后的士气收本轮税。

## 复现方法

在仓库内下载 `sources.json` 记录的 ZIP 并核对 SHA-256。提取 `age_of_conquest_iii/lib/aoc-desktop.jar` 和 `aoc-desktop-conf.jar`；帮助位于后者的 `conf/text/manual.html`，教程位于 `conf/bundle/MessagesBundle.properties`。

用工作区内 CFR 0.152 输出到工作区内临时目录，阅读上述原始类名对应的方法。必要时使用 `javap -c -p -classpath <aoc-desktop.jar> <class>` 核对字节码。所有生成目录应留在仓库内。原始程序不作为发布依赖，反编译输出不提交到应用源码。
