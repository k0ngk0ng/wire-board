# 按游戏拆分维护边界的调研

调研基线：`c969fde`。本文记录重构前的分析；后续已实施的结构、兼容范围和接入方式见 [游戏开发说明](../game-development.md)，实际验证结果见 [拆分验证记录](../game-module-verification.md)。

建议保留单仓库、单 Go 服务、单 React 应用和 SQLite 部署方式，把六款游戏拆成独立维护的纵向模块。每款游戏拥有自己的规则、状态、动作、机器人、房间配置、计时策略、界面、素材和测试。公共层只保留稳定的平台能力和接入契约。

拆分是否成功，以「开发一款游戏时需要修改多少其他模块」衡量。减少共享代码的目的，是减少跨游戏协调和回归范围；允许游戏之间保留少量相似代码。

## 现有耦合与并行开发阻力

以下行数按当前工作树物理行统计；目录文件数仅统计直属文件，Go 目录仅统计 `.go`。

| 位置 | 当前情况 | 对并行开发的影响 |
| --- | --- | --- |
| [internal/game/game.go](../../internal/game/game.go) | `State` 包含六款游戏指针；`Action` 汇集所有游戏动作字段；`New`、`Apply`、`View` 分支调度 | 新游戏、动作或视图变更都可能修改同一个入口 |
| [internal/game](../../internal/game) | 325 个生产文件、353 个测试文件共用 `package game`；生产代码有 710 个 `*State` 接收者方法 | 文件按前缀分组，但没有包级隔离；移动目录还需要拆接收者和包内依赖 |

| [web/src/main.tsx](../../web/src/main.tsx) | 6,106 行；包含大厅、创建、等待、玩家栏、回合提示、结果及宝石／铁路棋盘 | 多个游戏开发分支持续争用同一文件 |

| [internal/server/admin.go](../../internal/server/admin.go) | 游戏 ID 和名称硬编码；`/api/state` 额外返回铁路地图清单 | 新增游戏还需修改平台目录与展示逻辑 |

最近 100 次提交中，`main.tsx` 出现在 28 次提交，`server.go` 出现在 20 次，`types.ts` 出现在 13 次。这说明它们是频繁变更的汇合点；该统计不代表已经发生的合并冲突数量。

卡坦岛占 `internal/game` 的 264 个生产文件，另有 17 个游戏专属生产文件位于 `internal/server`。因此，拆分规则文件但保留服务器中的配置、计时和归档逻辑，仍会留下主要耦合。

已发现的前端直接跨游戏依赖：`catan.tsx`、`catan-explorer.tsx` 和 `catan-world-editor.tsx` 引用 `rail-map-controls.ts`。这个工具实现的是拖动、缩放和视口定位，可改为不含铁路默认值的可选 UI 工具；如果两款游戏的交互继续分化，也可以各自维护。

## 推荐目录和依赖方向

建议按游戏集中前后端文件，使任务分配、代码评审和变更范围都对应一个目录。以下是目标结构，不是当前目录。

```text
games/
  carcassonne/
    server/             # 独立 Go 包：规则、状态、动作、机器人、计时、编解码
    web/                # 棋盘、配置、等待区、规则说明、结果、类型、样式
    assets/             # 本地资源或 CDN 资源清单
    tests/              # API／浏览器 E2E、兼容样本、对局记录
    scripts/            # 本游戏资源处理和验收入口
    docs/
    README.md           # 模块接入、开发和验证说明
  splendor/
  rail/
  sanguosha/
  dota/
  catan/
internal/
  gameapi/              # 小型接入契约；不定义任何游戏的手牌、棋盘或回合
  server/               # 账号、房间外壳、事务、幂等、通信、调度、积分账本
  app/                  # 组装 server 和游戏注册表
  testkit/              # 仅测试使用的服务启动、HTTP 客户端和产物记录
web/src/
  app/                  # 登录、大厅、房间外壳、聊天、资料和管理
  game-api/             # 前端宿主与游戏模块之间的契约
  games.ts              # 游戏模块注册；按需加载
  ui/                   # 少量无游戏知识的 UI 基础组件
```

继续使用现有 `go.mod` 和 `web/package.json`。Vite 和 TypeScript 的配置需要验证仓库内 `games/*/web` 的导入、开发监听和构建收集。当前前端嵌入路径 `web/dist` 可以保留。

生产依赖方向：应用组装层导入平台和游戏；平台与游戏依赖接入契约；游戏不导入平台实现，也不相互导入。前端同理，只有注册入口认识全部游戏。

不建议在这一步拆成六个仓库或六个服务。当前目标是并行开发，包和目录隔离可以解决主要问题；独立部署还会引入账号通信、版本协调和跨服务事务成本。统一构建仍可能受某款游戏的编译错误影响，模块拆分不等同于独立发布或进程故障隔离。

## 公共层保留什么

| 公共层保留 | 每款游戏自己维护 |
| --- | --- |
| 登录、会话、权限、CSRF、用户和好友 | 人数规则、地图、扩展组合、配置归一化 |
| 房间成员、房主、密码、准备、观战、聊天、上下架 | 等待阶段配置和自定义地图编辑 |
| HTTP／WebSocket、请求封套、幂等键、事务提交 | 动作类型、合法性、并发响应窗口 |
| 快照存储、动作审计、提交后广播 | 快照内容、版本升级、玩家／观众视图 |
| 定时器执行、托管标记、闲置房间关闭机制 | 机器人决策、到期响应者、倒计时暂停和恢复 |
| 战绩存储、排行榜和积分账本 | 胜负、名次、同分处理、公开战绩摘要 |
| 页面外壳、连接状态、通用弹窗、玩家资料入口 | 棋盘、玩家统计、回合提示、音效触发、日志词汇、结果详情 |

积分政策需要单独划清边界：游戏输出最终名次、获胜阵营及适用的通用计分模式，平台执行既有积分政策。平台不应再读取铁路车站、宝石卡牌数量，也不应继续通过 `kind == "sanguosha"` 判断团队计分。不得借拆分改变现有胜负或积分结果。

共享工具遵循三个限制：不引用游戏状态、不判断游戏 ID、不为一个游戏不断增加可选参数。`shuffle`、`sum`、小型渲染工具可先留在游戏内部；仅在语义稳定且确有多个使用方时提取。不建设通用卡牌、棋盘、资源、技能或回合引擎。

## 接入契约必须覆盖的行为

接口签名应在首批迁移中确定。下面列出必要职责，不要求实现一个包含全部方法的大接口。

1. **游戏描述与房间配置**：稳定 ID、名称、可用能力、配置校验、人数校验、等待阶段设置更新、开局初始化。地图目录等游戏数据由模块提供，避免继续扩充 `/api/state` 的游戏专属顶层字段。
2. **动作执行**：平台提供可信玩家身份、请求版本和时间；游戏解码自己的动作并验证执行。认证、幂等去重和事务归平台，游戏只能修改候选会话。非法动作或保存失败不得污染当前对局。
3. **并发窗口**：普通动作要求当前版本；铁路同时选任务、卡坦同时弃牌／交易、三国杀无懈、DotA 同时规划由模块确认响应令牌与允许的旧版本。平台继续拒绝未来版本和越权请求，模块也必须重新检查该玩家是否仍可响应。不能简单改为接受所有旧版本。
4. **调度**：模块给出可行动玩家、到期应处理玩家及下一次唤醒时间，并维护自己的暂停时间、阶段令牌和响应上下文。平台负责按时调用和托管席位管理。「可以行动的人」与「到期必须行动的人」不一定相同，例如卡坦交易回应不能直接视为所有回应者都要超时托管。
5. **私有快照与公开视图**：分别提供存储编解码和按观看者生成的视图。公开视图不得复用完整快照；观众、本人、对手、队友的可见范围由各游戏控制。
6. **结算与历史**：输出公开结果、名次及可归档的游戏摘要；平台在同一事务中保存对局、历史和积分，保持重复请求不会重复结算。
7. **前端模块**：提供配置编辑、等待阶段内容、棋盘、玩家信息、规则、结果和日志渲染。平台提供提交动作、当前用户、连接状态和素材地址；页签提醒只接收模块给出的「需要行动／提示文本」。

协议边界可用 `json.RawMessage` 承载游戏自己的配置和动作，但每款游戏内部仍使用明确的 Go／TypeScript 类型，不把所有逻辑改为 `map[string]any`。前端不再维护包含六款游戏可选字段的全局 `Game` 类型。

游戏自己的 `State` 保留自己的回合和阶段语义。DotA 的同时规划、三国杀的响应栈、卡坦的多人弃牌，不应被强制套进一个公共 `Turn/Phase` 状态机。

最初允许新增游戏修改两个很小的注册入口：Go 注册表和前端注册表；每个入口只增加 import／注册项。公共层不再新增游戏分支。若实际并行开发仍频繁冲突，再引入每游戏清单及确定性的注册代码生成，不必先搭建插件框架。

## 迁移顺序

| 阶段 | 具体工作 | 完成条件 |
| --- | --- | --- |
| 0. 固定行为基线 | 先记录失败场景，整理已有测试、旧快照和浏览器验收；为首批迁移补齐必要 E2E | 有可重复命令和结果产物；兼容、隐私、并发与计时预期明确 |
| 1. 建立接缝，迁移卡卡颂 | 引入小型接入契约和注册；将卡卡颂规则、机器人、前端和测试完整迁入自己的目录；未迁移游戏走旧适配器 | 卡卡颂日常开发不需要修改 `game.State`、`main.tsx` 或房间游戏分支 |
| 2. 用 DotA 验证契约 | 迁移同时规划、多人行动、阶段计时和团队结算 | 接口能支持并发阶段，而非只适配轮流行动游戏 |
| 3. 拆宝石、铁路、三国杀 | 抽出 `main.tsx` 内的宝石／铁路棋盘；各自带走配置、机器人、隐私视图、样式和历史逻辑 | 三款游戏分别可维护和验收；注册之外无需修改其他游戏 |
| 4. 完整迁移卡坦 | 整体迁移其规则、17 个服务器专属文件及散落在房间／战绩／前端中的逻辑 | 卡坦扩展开发不再改公共业务层 |
| 5. 清理与约束 | 删除旧 `State/Action` 聚合及旧适配入口；添加依赖检查；按模块组织 CI | 跨游戏导入被阻止；共享代码变化触发所有游戏验收 |

选择卡卡颂作为首例，是因为它只有 2 个按此前缀统计的后端生产文件，已有独立前端文件和涵盖重启、机器人、隐私、历史的 HTTP 测试。它适合建立完整迁移样板；紧接着迁移 DotA，防止接口只照顾轮流行动的游戏。

卡坦最后整体迁移，避免同时处理它的大量扩展组合和平台边界重构。其基础版、航海家、城市与骑士等仍归同一个游戏模块，扩展间存在真实规则依赖，本轮不把它们变成独立平台插件。新游戏在阶段 2 的契约稳定后即可按新目录开发，无需等待卡坦迁移完成。

前两个阶段由同一条主线收敛公共接缝。之后各游戏可分别开发；每条任务明确目录范围和验收命令。卡坦迁移还涉及公共旧文件，期间需要避免其他任务继续往那些位置新增游戏逻辑。

## 旧协议和存档兼容

当前 SQLite `rooms.snapshot` 保存整个 `Room` JSON，`match_history.snapshot` 保存历史摘要。仅变更 Go 包名未必影响 JSON，但移除聚合结构、改字段层级会影响进行中对局、历史记录和服务重启。

建议拆两步处理：

1. **先变内部结构，保留现有外部格式。** 各游戏提供旧格式编解码与视图适配，保留现有 JSON 字段和 API 行为。已打开的浏览器及旧快照仍按原协议工作。游戏专属适配归各模块，平台只保留通用调用。
2. **格式升级另做变更。** 如需统一为 `kind + schemaVersion + payload`，再定义旧格式读取、新格式写入和历史数据迁移策略。新版本能读取旧格式，并不代表旧版本能读取新格式；切换写入格式前必须验证回滚方案。

快照必须覆盖游戏自己的计时剩余量、并发窗口、待响应令牌和机器人推进所需状态。不能只迁移棋盘和手牌。运行时 Go 接口也不能依靠 `encoding/json` 自动恢复，必须通过游戏 ID 查找明确的解码器。

已有进行中快照需要覆盖迁移前保存、迁移后恢复、继续操作、结算和再次重启；历史摘要需要验证旧记录仍能展示。持久化格式保持不变的阶段，应另外验证新程序保存后旧程序可读取，不能只凭字段名称宣称可回滚。

## 测试和 CI 如何支持独立维护

当前有大量规则与 HTTP 测试：`internal/server` 的 234 个 Go 文件中，208 个是测试。前端 `web/tests` 有 41 个直属测试文件。应保留并迁移这些保障，不为改目录重写一整套单元测试。

现有 HTTP 测试有些直接读取服务器内存并停止定时器，例如 `TestCarcassonneHTTPPersistenceBotsAndHistory`。它们适合作为迁移回归保障，但不能替代真实浏览器、自然调度下的完整链路验收。[accept_natural_browser_match.py](../../scripts/accept_natural_browser_match.py) 已提供铁路／三国杀的浏览器对局及 `result.json` 产物模式；卡坦也已有服务器端 E2E 和产物写入，可按游戏整理这些入口。

先登记并覆盖以下迁移失败场景，再写实现；简单路径或样式调整采用针对性验证：

- 创建人数、地图、扩展校验变化；等待阶段修改后开局丢失配置。
- 本人、对手、队友、观众视图泄露秘密，或缺少必要操作。
- 重复 `nonce` 重复执行；非法动作修改状态；保存失败后内存和数据库不一致。
- 同时响应互相覆盖；合法旧版本被错误拒绝；旧响应令牌或未来版本被接受。
- 刷新或重启重置倒计时；超时托管错误玩家；取消托管错误延长其他人的响应时间。
- 机器人停滞、读取对手秘密或重启后不继续；手动与自动行动的闲置续期行为变化。
- 结算名次变化、团队计分变化、重复积分、旧历史无法展示。
- CSS 影响其他游戏；动态加载失败；资源路径变化；移动端溢出；日志、页签提示、动画或音效失效。
- 移动测试后遗漏用例、夹具或资源；CI 因目录变化跳过原有验证。

每款游戏的主要验收链路应包含：注册／登录 → 创建／配置 → 加入／准备 → 开局 → 玩家操作及机器人推进 → 观战 → 刷新／重连 → 重启恢复 → 完局／战绩 → 再来一局。复杂规则按该游戏自己的代表性场景补充，不要求所有扩展组合都重复一套浏览器流程。

E2E 产物统一放在仓库内 `.local/acceptance/<game>/<run>/`，至少记录提交、运行命令、环境、场景、断言结果、操作轨迹和错误日志；浏览器验收增加关键截图。可重放的复杂局面还应记录初始快照及随机决策。当前洗牌使用 `crypto/rand`，仅保存一个自定义 seed 不能保证重放；需要设计测试随机源或记录随机结果。私有测试快照与公开截图分开管理，使用测试账号，不从生产环境抓取秘密数据。

CI 的建议范围：

- 游戏目录变更：该游戏的既有测试、关键 E2E、平台接入冒烟；统一构建继续执行。
- 公共层、契约、注册机制或锁文件变更：所有游戏及平台验证。
- 发布：保留完整回归门槛；在模块覆盖映射经过验证前，不删除现有分片任务。
- 产物在成功和失败时都上传；失败保留足够的重现信息。

当前 `.github/workflows/build.yml` 实际为 20 个规则分片、单独 race 任务和卡坦专项 E2E；README 的本地说明仍称 CI 使用相同八片且全部带 race。实施测试迁移时应同步文档，以工作流实际配置为基线。部分前端测试还通过相对路径读取后端数据文件，需随所属游戏一起迁移。

## 拆分完成的验收标准

- 新增游戏的规则、前端、配置、素材、测试和文档均落在自己的目录；公共业务代码零修改，最多改两个薄注册入口。
- 修改某款游戏的动作或扩展，不再修改全局 `Action`、`Game`、`Room` 游戏字段和通用 `main.tsx`。
- 游戏之间没有直接依赖；平台实现没有具体游戏分支；例外仅限组装入口和有明确退出条件的迁移适配层。
- 每款游戏有独立、可重复执行的验收入口和结果产物；共享层变更触发全部游戏验证。
- 旧房间、历史、隐私、计时、并发、幂等、结算和现有部署方式均通过迁移验收。

下一步适合实施的范围是「行为基线 + 卡卡颂完整迁移 + DotA 契约验证」。完成后即可验证新游戏是否真的能独立接入，并据此推进其余游戏的拆分。
