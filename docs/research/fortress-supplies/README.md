# 疯狂坦克随机补给与电脑难度

## 原版证据

分析目标是已保留的官方网页战斗客户端 `tankclient_emsc.eeb2b.wasm`，SHA-256 为 `35974c0d7a06cf86f1f028b0ee1fc46c324921f6d829ce4db684f776199e489d`。它不是原版服务器，也不代表已运行 Steam 版本。REA / WABT 1.0.42 对 16 个保留原始函数体的静态切片生成 Evidence ID：`ev_6d00ee9eca22a5f519f105548f88d4b08f88f646955f5b17d5a9336dba35c03c`。被保留函数的原始文件偏移、长度和 SHA-256 位于 `.local/fortress-supply/research/supply-slice-provenance.json`；原始 REA 结果为同目录 `rea-supply-slice.json`。

| 结论 | 原始位置与观察 |
| --- | --- |
| 补给有独立运输过程 | RTTI `EItemDrop` 在内存 92404，vtable 92360；`f1027` 构造，`f3087` 用图片 7100–7109 绘制直升机，`f3078` 从运输状态生成 `EDropItem`。 |

| 箱子有下落与风漂移 | RTTI `EDropItem` 在 91616，vtable 91584；`f3265` 每次更新累加竖直速度，并按风值的一半更新十分之一像素单位的横坐标，碰地后生成 `EItem` 并播放声音 37。精确更新频率未由本次路径证明。 |

`EItemDrop` 同时承载其他演出分支，不能把它所有状态都叫补给。游戏原有开局两个库存道具不是上述空投路径。门户配置中的商品 `drop: 0` 也不能证明战场没有补给。

## 平台适配边界

本次实现原图直升机运输、随风偏移的落箱、落地提示、接触拾取、四格库存限制，以及通过现有道具操作使用补给。以下为明确的平台参数，不冒充原版服务器配置：

- 新对局在第 8 个行动回合首次投放，此后间隔 8–12 个行动回合；不是每名玩家每回合固定领取。
- 位置从存活坦克附近的有效地面选取，与当前行动席位无固定绑定；任何一队均可取得。不存在有效地面时跳过本次投放。
- 道具池沿用已实现的 8 种库存道具；不添加尚无规则的商品、钱袋或礼盒奖励。箱子拾取只增加库存，不立即加血、增伤或改胜负。
- 同屏最多保留 8 个箱子。库存满时不消耗地面箱子。箱子失去地形支撑时移除；没有擅自补写原版尚未复核的爆炸伤害公式。
- 运输期间属于系统阶段，暂不允许玩家行动；自动镜头跟随直升机与箱子，手动镜头仍保持用户位置。箱子落地后才给下一位完整操作时限，计时器迟到不缩短该时限。
- 运输、重力及动画毫秒值为重构参数；位置、投放、落地和拾取由服务器时间驱动。拾取保留 180ms 接触确认，与既有人物移动插值一致，避免视觉尚未接触就增加库存。
- 电脑通过同一公开移动和道具接口接近、取得、使用补给，不直接修改库存或生命。所有存活席位均按相同接触规则处理。
- 旧的进行中存档不凭空补投历史箱子；已有投放时间、待拾取确认、库存和下一次投放回合均随当前存档保留。

新媒体位于 `/fortressblue/v4/`，清单 `games/fortressblue/assets/manifest-v4.json`；原始帧尺寸、锚点和素材摘要在 `data/supplies.json`。没有改写 v2/v3 对象。落地音效复用已有 `BoxLanding.wav` 对应的平台音效资源。

## 电脑三档

设置字段为 `botDifficulty: easy | normal | hard`。新房间默认普通，旧存档缺失字段按困难恢复。困难保留原先 5°／5 力度的搜索与 ±2° 确定性误差。普通和简单分别使用 8／12 的搜索步长，叠加有限、可重复的角度／力度误差；不改变坦克生命、伤害、风、弹道或合法操作限制。真人托管与电脑席位使用同一策略。

## 本次规则与素材结果

`.local/fortress-supply/rule-results.json` 绑定最终 Go 源码摘要：服务端规则 `-race` 通过（1.923s），专属模块验收 `-race` 通过（178.470s），其中 34 组完整电脑对局、12 组跨难度／人数对局全部结束。原有出生点、状态周期和连续特殊弹夹具通过真实系统计时完成补给运输后再操作，没有跳过地图或放宽原断言。

`.local/fortress-supply/source-pixels.json` 核对 61 张原生帧：可见 RGBA、alpha 和锚点均一致。WebP 对全透明像素的不可见 RGB 做了规范化，记录中明确区分该差异。标准 `verify-assets.py --dist` 也已检查 v2、v3、v4 的清单、构建副本与摘要。
