# 声音请求、消费与驱动时基的失败场景

本清单先于新采样器和对应独立模型。现有 finite WAV 和逻辑 BGM 周期是只读来源，不能代替请求调度、优先级消费、暂停确认或帧内时序。

- 将 `A030` 的待请求音效误作 `F562` 的延迟声音，或给 `F807` 暂停标记、`F80A..D` 队列增加并行持久 owner。
- 延迟计数从 1 变成 0 的本次调用提前提交声音；延迟队列满或特殊请求冲突时丢失待提交编号。
- 驱动忙时漏掉重入积压、将 byte 计数当无限整数、或重入时遗漏先发生的延迟请求副作用。
- 补执行从帧尾批量合并为一次，或在驱动调用前递减积压，导致嵌套 IRQ 的顺序改变。
- `219ac`／`219ea`、`375a6`／`375ae` 或 IRQ 进入／退出混同计数，重复产生音频事件。
- 暂停、恢复标记被当普通队列音效，暂停路径仍消费新声音，或驱动已确认暂停后再重复切换。
- 特殊优先级、普通优先级、四槽反向扫描以及重复声音的 overwrite／drop 被错误展平为 FIFO。
- 用一次 world logical tick 替代一次视频步骤、音序驱动 tick 或 PCM 样本批；将 CPU cycle 数直接解释为 PCM 位置。
- 只在 callback 返回或 world pass 末尾消费一次，漏掉 IRQ 在 callback 内部清队列、取样和分派的事实。
- 事件仅按视频帧排序而丢失帧内先后、原始 PC／SR／SP／调用者与可核验的嵌套边界。
- 被动观察改变 RAM、画面或 PCM；hook 与 unhook 的完整固定输入、原内核、前端或基线不匹配。
- 仅比对字段差异而未说明忽略区；私有调用的未知 RAM 写入、未闭合调用或异常栈没有单独核验。
- 同进程 checkpoint 恢复未补 `refresh_cycles`，或把引用进程的硬件结构引入生产 Go／Wasm。
- 以新的期望快照逐轮覆盖独立模型，或为满足短期测试建立 CPU／RAM VM。
- 缺少可重复执行命令、原始失败、输入与来源 SHA，或采样／缓存写到工作区外。

新自然观察应冷启动复用同一合法输入，逐帧核对固定 unhook RAM／视频／PCM，保存原始有序 marker。原生原调用边界、独立语义模型与浏览器媒体调度是三种证据，不得相互冒充。
