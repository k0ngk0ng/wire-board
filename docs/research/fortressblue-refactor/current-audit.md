# 疯狂坦克现有实现审计

本审计针对重构前提交 `6e445c89257e7f72fde0bc056f13ce37441d60a9` 的工作树，检查服务端、前端、素材生成器、现有测试和保留的官方网页客户端解包文件。审计没有修改实现或测试，没有运行原版客户端，也没有把个人记忆中的原版参数当作规格。原版运行、Steam 视频及 REA 行为证据应另行归档，与下列事实逐项核对。

结论：现有实现取得了原版图片，但核心交互、回合状态、弹种模型和碰撞处理仍是另写的一套简化炮战。修正图片比例不足以完成重构。尤其存在确定的动画时钟错误、前景首次加载缓存错误及伤害记分错误，应在重构前先建立失败场景。

## 确定的实现问题

### 1. 炮弹还在飞行，坦克已经扣血、落地或死亡

- `games/fortressblue/server/engine.go:412` 的 `resolveShot` 同步求完整弹道、调用 `applyBlast`、更新弹坑、调用 `settleTanks`、判定结果，再立即 `advanceTurn`。状态没有飞行、爆炸或落地阶段。
- `games/fortressblue/web/Board.tsx:440` 记录绝对时间 `start = performance.now()`，但 `impactAt = duration * 0.86` 是相对时长。
- `Board.tsx:611` 使用 `frameNow < anim.impactAt` 判断是否显示旧坦克。页面运行超过约 2.8 秒后，该条件即使在发射首帧也通常为假，直接显示服务器最终坦克。`Board.tsx:246` 的受击闪白判断有同样问题。
- 地形使用 `now - anim.start`（`Board.tsx:527`），因此坦克和地形还会互相错位：坦克先下落，弹坑稍后出现。
- 公共玩家栏 `web/module.tsx:104` 直接读取最新 HP 和存活状态；即使只修 Canvas，公共栏仍会先扣血。自己的控制区血条也是最新数据（`Board.tsx:923`）。

需要验证的结果：同一发炮弹在飞行、命中、落地各阶段，Canvas、公共玩家栏、自己的 HP、音效和结算浮层必须处在相同服务端时间轴。减少动态效果也不能允许提前发生的下一次行动。

### 2. 下一回合已经计时，上一发动画尚未结束

`engine.go:205` 在射击请求到达时即设定下一席位的完整截止时间。`state.go:427` 同时把下一席位公开为 actor。只有当前浏览器通过 `Board.tsx:343` 的 `!anim` 阻止操作；电脑和直接调用 API 的客户端没有该锁。`LastShot` 只有一个，后发炮弹会覆盖前发；前端检测到更新即 `setAnim` 替换正在播放的动画（`Board.tsx:438`）。

这不是单纯动画长短问题：真人损失可操作时间，电脑可先于画面连续行动。原测试脚本 `scripts/fortressblue/check-browser.py:357` 已写明「Bots may chain shots」，选择等待最后一发结束，没有验证中间炮弹是否展示。

### 3. 前景加载完毕可能仍不绘制，直到首次弹坑变化

`useImage` 初始返回 `null`（`Board.tsx:85`）。地形 effect 在图像未加载时先设置 `terrainKeyRef`，再清空地形画布（`Board.tsx:535`、`:195`）。图片加载触发 effect 时，key 仅由地图和弹坑组成；key 未变即直接返回。没有图像就绪状态参与缓存条件。

初次挂载时可出现背景和坦克可见、可碰撞前景不可见；第一处弹坑使 key 改变后，前景才出现。应通过冷缓存、慢速前景请求及 CDN 失败回退复现，不能只查图片 URL 已加载。

### 4. 受害者也获得了造成伤害积分

`server/physics.go:267` 扣受害者 HP 后，`:268` 对受害者 `t.Damage += damage`，`:269` 又对射手 `shooter.Damage += damage`。不同玩家之间的伤害会同时计给双方；自伤时两个指针相同，累计两次。`state.go:377` 直接把 `Damage + Kills * 25` 写入结果分数。

旧 `TestBlastCarvesAndDamages` 只检查射手 `Damage > 0`，没有检查受害者计分保持不变、自伤、溢出伤害与最终结果一致性。

### 5. 全体状态在每个人的行动后都扣持续时间

`advanceTurn` 首先调用 `tickStatuses`（`engine.go:185`）；后者遍历所有坦克，扣持续伤害并减少所有状态的 `Turns`（`physics.go:313`）。新加毒、火也会在施加它的同一发炮弹后立刻触发一次。持续三个 turn 的护盾在八人局可能远未轮到自己就消失。

这是确定的当前行为；原版状态应按个人回合、全局行动、秒数还是其他事件计时，必须以参考证据确定后建模。不能直接把现有 `Turns` 当作正确语义。

### 6. 同一地形使用两套不同的碰撞实体

`scripts/fortressblue/prepare-original-assets.py:249` 的 `derive_bullet_mask` 不是解码原版独立碰撞文件，而是人为删除未连接至地图底部约 72% 区域的前景连通块。注释说明目的是避免炮弹过早撞到浮空轨道。坦克站立和移动仍用完整前景 mask（`physics.go:29`），炮弹改用过滤 mask（`:37`）。

本次直接统计当前 catalog 得到：

| 地图 | 可站立但炮弹忽略的 4×4 像素碰撞格 |
| --- | ---: |
| stage-2 | 1,796 |
| stage-3 | 2,115 |
| stage-4 | 5,127 |
| stage-10 | 2,987 |
| stage-13 | 7,784 |

应核对原版装饰层、前景层和真实碰撞层，而不是以「射得不够远」作为忽略平台碰撞的理由。`verify-original-source.py` 使用相同生成器重新生成 mask，只能证明转换可重复，不能证明这个人工规则符合原版。

### 7. 移动和爆炸后的落地采用不同规则

- `moveTank` 按 1.5 世界像素累计，一次请求目标 10 像素；实际通常移动 10.5 像素，剩余 fuel 少于 1.5 时仍可移动整步（`physics.go:163`）。
- `groundY` 只查单列从给定 y 向下的首个实体，未检查坦克宽度、底盘支撑或身体与墙壁重叠（`:75`）。向上最多回看 8 像素，后面的 `ny - t.Y < -8` 爬坡判断不能承担高台前方阻挡检测。
- 行走落到更低平台时直接设置 `t.Y = ny`，不计算落差伤害；爆炸后 `settleTanks` 会按同样落差扣血（`:201`）。
- 前端只画 idle 或 die 图（`Board.tsx:614`）；已取得的 move/fire 资源未用于对应动作。没有落地轨迹、底盘随坡度倾斜或移动插值。

重构需要先决定哪些落地规则有原版依据，再用同一运动过程服务行走、地形破坏和恢复。

### 8. 范围命中和出界射击结果表达不完整

`applyBlast` 可以伤害多名敌人，但 `Blast.Victim/Damage` 每次被覆盖，最后只保留最后一人（`physics.go:271`）；没有受害者时 `Victim` 默认还是 0。原版闪电链伤害只写事件，没有加入炮弹的额外命中信息（`engine.go:436`）。前端只绘制 `arcs[0]`、`blasts[0]`。

`simulateArc` 在越界时返回一个 Impact（`physics.go:120`），`applyBlast` 随后把它 clamp 到地图边缘（`:244`），仍执行爆炸与伤害；因此飞出边界的炮弹可能在边缘产生不在实际路径末端的伤害。精确出界规则待原版核对，但路径落点与实际伤害中心不一致应纳入失败场景。

### 9. 音效不跟随画面命中时间

`Board.tsx:489` 收到同一快照的 shot、hit、death、turn、finish 后立即提交音频队列，没有使用 `Animation.impactAt`。空地爆炸未发出 hit 或 explode 事件时，可能没有对应爆炸音。字段 `impactPlayed` 和 `beforeEvents` 虽保存，未参与该音效调度。

## 与原版对照时须重点确认的玩法

以下分清现有事实和原版缺口，不将未经验证的规则直接写入实现。

| 维度 | 现有事实 | 参考缺口／重构方向 |
| --- | --- | --- |
| 发射交互 | 设定 20～100 力度，keydown 空格或点击地图立即发射，无按下／释放蓄力（`Board.tsx:914`、`:955`） | 原版蓄力开始、最大值、松开时刻、移动及瞄准按键需实录；手机应保留同一核心操作 |
| 瞄准辅助 | 客户端计算受风影响的长轨迹并绘制末端十字（`aim.ts:112`、`Board.tsx:589`）；预览不考虑坦克碰撞、不考虑穿风道具 | 默认全轨迹／落点辅助是否存在须证据。现有机制显著降低试射、读风、记力度的作用 |
| 行动顺序 | 固定红蓝席位交替，死亡只跳过，无 delay 状态（`state.go:238`、`engine.go:164`） | 核对原版 delay 如何受车型、弹种、瞄准时间、道具、移动影响；不能只把固定顺序改为另一组随意常数 |
| 弹种 | 全车型都用同一弹道，主炮半径 50、特殊半径约 58；特殊每局 2 发；属性仅靠 skill ID 加毒／火／链雷／增伤 | 核对分裂、连发、埋雷、追踪、激光、水弹等实际车型表现及弹药限制。当前只有一次弧线加状态，不代表 14 种炮击机制 |
| 炮口角度 | 所有车允许最小 0°，只读最大角；每回合重置 45°、65 力度及主炮（`Board.tsx:398`） | 解包 `character.txt` 含 `MinAngle`，至少不能忽略该源字段；还需确认坡度、朝向、角度保留方式 |
| 比例与镜头 | 坦克 2.2× 原始图片、炮弹 0.55×；伤害实体仍是半径 20 的圆；镜头自动追当前车和炮弹，缺少自由拖动／缩放 | 用原版截图量化地形／坦克／炮弹关系，保留像素资源原始锚点，不以放大资源掩盖镜头问题 |
| 选车和道具 | 强制红蓝均分；每人随机两道具；8 分钟伤害翻倍／强风，12 分钟按总 HP 判胜 | 分别确认原版支持项与平台有意适配项，不再把平台自定模式统称原版 |
| 电脑 | 只选车、用道具、穷举角度力度射击；不尝试移动（`bot.go:12`） | 地形阻挡、贴身、陷坑、危险边缘时需能移动求解，不能仅靠 12 分钟超时来证明策略完整 |

### 已保留的原版配置证据

`.local/fortressblue-original/extracted/package/Asset/character.txt` 是制表符分隔文本，字段包括 `MaxAngle`、`MinAngle`、`Energy`、`Move`、`Attack`、`Defence`、`Range`、`A1Power`、`A1Round`、`A2Power`、`A2Round` 和各动画字段。

例如 Character 1 的最小／最大角为 15／80，Character 2 为 25／45，Character 5 为 20／45；数值与当前车型 HP 等主要值对应，但现有 `data/tanks.json` 丢弃最小角度。`A1Round/A2Round` 的实际语义暂未确认，不能仅根据名称认定为 delay、弹数或爆炸范围。

官方门户保留的 `portal/configs__skill.json` 仅注明爆炸、毒、火、雷属性，未提供「毒每次 25、持续三次」「火每次 18」「雷链距离 90、伤害 55」等当前常数。门户 `configs__tanks.json` 也没有证明「特殊弹仅两发」。这些必须在来源表中标记为现有自定规则，而非官方精确参数。

## 旧验收为何没有发现

1. `check-browser.py:349` 只确认 `shot id > 0`、`animating=1`、存在 projectile 标记。没有逐帧对比目标 HP、底盘坐标、地形和结算状态。检查到画了炮弹不等于命中顺序正确。
2. 第二次点击开火仍检查 `shot id > 0`（`:419`），此前已经大于 0；随后弹坑变化可以来自电脑（注释明确允许）。可能在点击未成功时依然通过。
3. 前景图片检查证明加载成功，Canvas 多样性也可能由背景和坦克贡献，不能发现前景缓存未刷新。
4. 满力射程和全轨迹预览被直接写成验收目标（`:321`），没有原版基准；它们会保护当前偏差。
5. `TestSelectAndTurnAdvance` 要求 Apply 开火后立刻轮到另一席（`rules_test.go:167`），恰好把缺少飞行阶段固化成通过条件。
6. `TestDamageFormula` 只要求伤害在 80～400 之间；`TestAimBounds` 只测试 clamp 函数。没有逐车型、逐弹种的证据模型。
7. 全电脑测试每动作前进 5 秒，允许时间到判胜（`module_e2e_test.go:63`）。证明能够结束，不能证明策略能脱困、不会重复无效射击或完整展示炮弹。
8. HTTP 恢复测试对已结算快照做 DeepEqual；没有飞行或落地阶段，因此不可能证明重连不会跳过当前动作。
9. 素材重新解码和碰撞镜像测试使用相同生成器，属于一致性验证；缺少独立原版行为基准。

## 实现前失败场景清单

以下先作为重构验收要求；在原版行为证据明确后，先写可失败的 E2E 或针对性验证，再实施。不得后补与实现同构的单元测试。

1. 页面启动超过 10 秒后发射必中的长弹道：飞行中所有 HP、位置、存活状态和结果保持命中前值；命中帧后统一更新。
2. 先后造成范围多目标命中、护盾伤害、毒／火／雷效果和末名敌人死亡：每个目标各有可验证的命中时间；结算不得抢在最后一次命中前。
3. 真人对电脑、全电脑及直接 API 行动：飞行和落地时无下一行动 actor；下一回合时间从可操作时刻开始。
4. 弹道中途刷新、断线重连、恢复 SQLite 存档：继续当前进度，不从头重播、不提前结算；普通快照不能重新打开已关闭结算。
5. 网络延迟或丢过一个快照后连续两发、多弹和连锁：不得覆盖丢失中间结果；减少动态效果仍使用同一行动与结算顺序。
6. 冷缓存、前景请求晚于背景、CDN 失败回退：前景就绪后立即可见；未就绪时不能显示误导性的空地图；记录前景特定区域像素与截图。
7. 站在浮空平台上、从下方和侧面射击该平台：显示、站立、弹道阻挡与原版证据一致；弹坑同时改变三者。
8. 行走靠近高台、陡坡、窄梁、坑沿、深渊、另一辆车和 fuel 小于一步：不可穿地、免费超步或瞬移到地底；主动落下与炮击落下采用已确认规则。
9. 射击边缘飞出场景、向上越界、回旋落回自己和负风：可见弹道终点、伤害中心与出界处理一致。
10. 不同车型最小／最大炮角、坡度、左右朝向：炮管表现与发射方向一致；非法参数在服务器拒绝。
11. 按住和松开蓄力、最大力度、取消手势、按键重复、切换标签页及网络 busy：每次释放最多一次射击，不产生卡住的蓄力或移动。
12. 弹种与 delay 的独立原版参考案例：更换弹种和花费不同操作时间后，顺序按明确证据变化；固定红蓝轮转应在该案例下失败。
13. 同一份原版素材在桌面、320px 手机、超宽屏下记录实际地图宽高、坦克像素尺寸、炮弹像素尺寸及实体轮廓；画面可见部分与碰撞吻合。
14. 2／4／6／8 人状态持续周期；护盾不能随无关玩家行动意外耗尽；刚施加持续伤害的首跳时机与证据一致。
15. 单目标伤害、多目标、友军、自伤、过量伤害、持续伤害击杀：受害者不得因被打获造成伤害积分，最终结果与事件累计一致。
16. 电脑遭平台阻挡、陷坑、危险边缘和弹药限制时仍能完成对局；分别覆盖混合真人、托管、取消托管和恢复后的同一局势。
17. 公共玩家栏、回合提示、战场和控制区在动画／等待／自己行动切换时保持位置稳定；计时不显示负值，也不先于可操作阶段消耗。

验收产物应包含可重跑命令、场景初始条件、服务端阶段及时间记录、逐帧关键截图和结果 JSON。原版未验证的常数需要保留明确来源缺口，不能由当前测试通过反推为原版规则。
