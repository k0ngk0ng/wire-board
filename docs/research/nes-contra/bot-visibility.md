电脑策略的正式验收必须使用与玩家已显示画面一致的观察。当前 `ObserveBot(World, actor, tick)` 读取当前规则对象，尚不满足这一要求；此前通过的首关、基地记录只证明合法按键能够推进规则，不能证明电脑的信息公平性，也不能作为完整游戏上线依据。

已确认的边界问题：

- `Session.StepPads` 在本次推进前提交上一批呈现数据。电脑目前在它之前读取当前规则位置，可能比 Canvas 的 `AppliedOAM`、`Background` 和 `AppliedScroll` 提前一个呈现边界。
- 图形目录中的 code 1 是 `blank`，没有绘图片段。敌人初始化会使用这一占位码，因此 `Sprite != 0` 不能证明对象已显示。
- 部分炮台、核心、护板和关底门绘制在背景中。不能仅因其占用敌人槽位就报告可见，也不能因槽位删除就提前隐藏仍在画面上的图案。
- 角色的平台接触在敌人碰撞阶段调整坐标，可能晚于逻辑显示对象的冻结；生产显示投影是否与原版共用坐标的行为一致，由世界／呈现集成单独核验。

正式输入应由已提交的视觉帧、玩家实际可见的 HUD 和不可变视觉资源目录构成。Bot 不应再接收 `World`、敌人槽位或原始碰撞窗口。图形类别只表达画面可识别的外观；同像素、同 HUD 的对象不能因为内部 Kind、slot、HP、动作计时、随机状态或生成脚本不同而产生不同观察。实体跟踪使用相邻可见帧的外观与位置配对，不使用内部槽位身份。

待新增视觉输入 API 确定后，先替换旧可见性测试，再接实现。必须覆盖以下失败场景：

| 场景 | 必须验证的结果 |
| --- | --- |
| 未提交的角色移动、敌人出生、背景请求或地图加载 | 提交前观察保持原画面，提交后才更新 |
| 全黑显示、blank 0／1、画面外对象、透明或被遮挡图形 | 不把内部对象直接报告为可见 |
| OAM 排序、硬件显示限制、图形页和颜色变化 | 使用与实际渲染相同的可见性判定 |
| 背景请求被拒绝、延迟、覆盖、清屏或尚未执行 | 视觉标签只随真正提交的写入改变 |
| 静态图案已出现而规则槽位尚未生成 | 可见图案的识别不依赖生成时机 |
| 槽位死亡但旧背景还在 | 观察保留实际仍显示的图案，不提前消失 |
| 私有 HP、计时、RNG、未出现实体和未显示地图发生变化 | 在相同可见帧、HUD 与公开输入时刻下，观察和策略输出不变 |
| 观测、Bot 和 Session 保存恢复，以及取消主动托管 | 恢复不偷看未显示状态；取消只停止电脑输入，不重置对局 |

现有 `TestBotPublicObservation` 在未提交且 OAM 全隐藏的状态中期待敌人，测试本身固定了错误定义，不能继续当作该边界的验收门槛。既有 HP／计时／RNG 不变性检查仍有参考价值，但不能替代视觉提交与遮挡检查。

阶段调试允许从标准 `NewSession` 重放已保存的合法手柄前缀，再由新策略继续控制。此类记录明确标记为 `focused strategy continuation`，不注入 RAM、生命、位置或结果，也不计为完整策略验收。最终单人、双人及真人混合验收必须从标准新局开始，以通过上述边界的观察完整打通八关，并保留独立按键回放、源码摘要和恢复验证。
