# FC《魂斗罗》复刻与合作计分方案

本文保留 2026-10-25 的初始调研结论，平台源码基线为 `4dd8f48e7f4becec401e9a2ba9c67d556f0b0249`。当时的交付范围是调研、ROM 核验和 REA 分析探针。后续已开始实现独立规则、联机与合作计分；当前方案见 [可行性复核](feasibility-review.md)，状态和验收缺口见 [实现与验收进度](IMPLEMENTATION.md)。游戏尚未正式上架或发布。

**技术上可行。建议以原版日版《魂斗罗》为唯一行为基准，用 REA/Ghidra 恢复代码、用 NES 调试环境记录原版行为，最终交付独立 Go 规则引擎与 Canvas 前端。合作局按整次闯关结算：全通关时所有参战者得分，挑战失败时所有参战者扣分。** 平台已有合作结果、实时输入、控制器、托管和恢复能力；合作计分与完整游戏行为仍需开发和验收。

## 2. REA 已实际验证的能力

本轮使用 REA 6.5.0、Ghidra 12.1.4，完成两项实际分析：

| 分析 | 本轮结果 | 证据 |
| --- | --- | --- |
| ZIP 与成员清单 | 核验日版压缩包、ROM 成员及 SHA-256；没有完整性冲突 | [REA 归档证据](evidence/rea-archive.json)，`ev_17fa061e53ce6370396c4266b7bcf6f63b26286207d230550de6d681c3d81328` |
| 6502 RESET 入口 | 提取末尾固定页中的 `$F80D..$FFFF` 静态片段，成功获得入口汇编、伪代码、调用和引用 | [REA 函数证据](evidence/rea-reset-function.json)，`ev_991c8771647c89ee3fdc10bceb653904d01c7666ab15a099ba56fe4449af6481` |

片段长 2,035 字节，起始 ROM 文件偏移 129,053，SHA-256 为 `e35c3fe1bc1ca5fc624c7764e06bb619d2ae54ccbc30336633c0a2892c32368e`。映射采用最后一个 8 KiB PRG 页位于 `$E000` 的假设，从已读出的 RESET 地址开始，避免把随意页首误当函数入口。

Ghidra 识别入口范围为 `$F80D..$F888`，124 字节；可见 `CLD`、`SEI`、读取 `$2002` 的等待循环、栈初始化、对 `$6000` 的读写，以及循环中的 `$0034` 更新。它同时恢复了 `$FFFC` 对 RESET 的数据引用。这说明目标字节可被 REA 的 6502 通路分析；这些观察尚不能解释角色、武器或关卡规则。

伪代码包含「bad instruction data」和移除 `$0000` 不可达块的警告。汇编可见跳向 `$0000` 的分支，片段没有对应 RAM、映射寄存器和实际执行状态。因此保留原始警告，不把自动伪代码直接当可执行规则；`relationship_coverage: complete` 只针对该静态函数的已解析引用，不代表游戏调用链完整。

REA 的工作范围应这样划分：

| 工作 | REA 的职责 | 需要补足的证据 |
| --- | --- | --- |
| 身份与定位 | 固定 ROM、切片、工具版本和 Evidence ID | 来源文件及切片映射清单 |
| 程序理解 | 查询 6502 指令、数据引用、调用、函数注释和伪代码 | NES RAM、PPU/APU、mapper 状态及逐帧执行 |
| 规则恢复 | 从已确认字段跟踪移动、碰撞、武器、敌人和过关逻辑 | 同初态、同输入的原版轨迹 |
| 重写验证 | 将静态结论与差异报告关联 | Go/Wasm 与原版的状态、事件和画面对照 |

REA 不直接解析 iNES 或执行 mapper，也不是 NES 模拟器。128 KiB PRG 不能整体导入 16 位线性地址空间。后续须维护 `(ROM SHA, PRG bank, CPU address, ROM offset, frame)` 映射；同一 CPU 地址在不同 bank 下必须视为不同代码。通用 NMOS 6502 的语义也不能替代 NES CPU 的实际行为。

原版对照环境优先复用仓库已有 NES 研究工具，再核验其 Mapper 23 支持、逐帧输入、RAM／换页跟踪和保存状态能力。需要时使用 FCEUX 或 Mesen；本轮没有启动模拟器，没有录制原版完整对局，不把已有篮球录制能力算作魂斗罗验收。

## 3. 复刻范围与恢复顺序

推荐首发支持单人及双人合作，双人共享原版镜头与关卡进度。人数由平台创建房间选项决定，直接进入游戏，不再进入 ROM 的一人／两人选择菜单。平台席位与原版角色编号分开映射；画面保留角色造型和颜色，不增加玩家数字角标。

完整目标为第一轮八关。八关结构至少覆盖横向推进、基地纵深战斗和瀑布纵向推进三类场景，不能只用第一关横版射击推断后续可复用。原版结局后可能继续循环的行为，应在平台的第一轮挑战结算点停止；重复周目若开放，另设明确玩法及计分策略。

实现前先录制、再恢复以下行为：

1. 按下与按住、移动、跳跃、趴下、方向射击、武器拾取与失去、射速和弹丸数量限制。定点坐标、进位和取整均依据原版。
2. 地形、平台、水域、坠落、移动障碍、镜头边界，以及两名角色互相限制推进的规则。
3. 每类敌人与 Boss 的状态机、生成条件、随机状态、弹幕、碰撞和受击帧；这部分必须从原版恢复。
4. 单人死亡、队友继续、复活／借命、增命、全灭、续关、关卡切换和最终通关。具体生命与续关次数由原版采样确定，不先填入未经验证的常数。
5. 日版的场景演出、调色板、CHR 页、精灵拼装、滚动、音效及配乐切换。图块解码完成不等于画面恢复完成。

原版玩家角色没有可直接照搬的合作电脑伙伴策略；在运行调查中仍应核验具体控制路径。平台要求的电脑队友和真人托管属于接入扩展，需独立实现走跳、避险、射击和推进能力，不能伪称恢复了原版玩家 AI。敌人 AI 与 Boss 行为继续严格按原版恢复。

建议新增 `games/contra/engine`、`games/contra/server`、`games/contra/web`，具体路径是实施建议，本轮未创建游戏模块。

| 层 | 负责内容 | 可复用依据 |
| --- | --- | --- |
| Go 确定性引擎 | 逐帧状态、碰撞、敌人、武器、生命、关卡和随机状态 | 篮球独立引擎模式；规则保持在本游戏目录 |
| 服务端模块 | 鉴权输入、权威推进、完整快照、合作结果、恢复迁移 | [`gameapi.Module`](../../../internal/gameapi/module.go)、[`module_realtime.go`](../../../internal/server/module_realtime.go) |
| 同源代码生成的 Wasm | 客户端重放及本席输入预测；最终结果以服务器为准 | [`basketball/web/network-scene.ts`](../../../games/basketball/web/network-scene.ts)、[`wasm.ts`](../../../games/basketball/web/wasm.ts) |

模拟器只用于原版观察。正式产品使用独立规则，不将 ROM、CPU 模拟器或完整 RAM 机器状态作为线上玩法引擎。

### 网络与恢复

平台已有认证 WebSocket、输入 nonce 去重、增量流、恢复快照及关键检查点。入口见 [`realtime_stream.go`](../../../internal/server/realtime_stream.go)、[`realtime_checkpoint.go`](../../../internal/server/realtime_checkpoint.go)。篮球有输入 epoch、按键边沿和本席预测实现，但类型与席位范围绑定篮球，需要按魂斗罗协议适配。

必须分别设计原版逻辑节奏、服务端调度、快照发送和浏览器绘制。宿主目前每 50 ms 唤醒；篮球按 100 ms 批次推进内部 60 Hz tick。它证明接口可承载实时游戏，不证明魂斗罗的跳跃、躲弹和双人射击手感已满足要求。原版 NTSC 视频时序与实际逻辑更新／掉帧也须测量，不能机械用篮球的 60 Hz 常数替代。

输入至少携带席位、epoch、单调序列和按键边沿；同一网络批次内先按后松的跳跃不能丢失。客户端预测只改善响应，不提前确认击杀、生命变化或胜负。受击、子弹命中、死亡和音效使用同一权威事件时间轴，校正不能重复播放。

现有检查点不是逐帧永久日志，崩溃恢复可能退回最近一次成功保存的位置。魂斗罗应把过关、生命／续关资源的重要变更与最终结果设为关键边界；引擎版本、随机状态、镜头、敌人、弹丸及输入确认位置随快照保存。开关托管、重连和恢复均清理过期输入，不重置世界。

客户端刷新使用服务端当前状态；计分挑战不允许客户端任意上传旧存档以撤销死亡或反复刷分。服务器恢复沿用原 `match_id` 与开局计分策略。规则或引擎升级需要快照迁移，不能用新规则静默重算旧局。

### 电脑、加载和界面

电脑队友通过普通逻辑按键完成全部开放关卡，不能直接改坐标、生命或关卡结果。只使用当前席位可见信息；不能读取画面外敌人的隐藏状态。覆盖单人托管、双人电脑、真人与电脑混合以及托管后手动接管。篮球的 `BotAction` 空返回依赖其内部原版自动角色，不能复制到魂斗罗作为电脑支持。

空闲、掉线、后台均不自动托管。失焦与断线要释放输入；全队暂停若开放，由服务端统一处理。单端停画面不能让它单独停止世界。屏幕中的敌兵与 Boss 是关卡 NPC，不属于「电脑玩家席位」；否则 PvE 永远无法计分。

首局使用公共加载屏障，代码、当前关卡必要素材与渲染器真正就绪后报告 `onReady`。关间加载使用带身份的幂等阶段，避免与公共屏障互相等待；已开局重连不冻结其他玩家。不预加载全部配乐和所有关卡。

复用公共创建／等待界面、FC 控制器、`GameFullscreen`、游戏内 overlay root 和 `BoardProps.audio`。键盘默认 J 射击、K 跳跃，分别对应逻辑 B／A，具体组合行为按原版核对；Start 的暂停语义在服务器处理。手柄放在比赛画面下方，320 px 手机也保留多指、斜向及连发操作。普通页面公开显示两人的生命等关键资源；全屏内仍需完整 HUD、操作、错误及结算。

封面遵循平台手绘 SVG 风格，游戏画面使用恢复后的像素素材。图片、音频和 Wasm 的发布按不可变摘要版本管理，来源与提取方式留证。是否可以公开分发原版素材与独立规则开发分别核验；本轮没有上传或发布 ROM、图片、音频。

## 5. 合作计分：全队同赢同输

### 现有平台已经支持什么

[`gameapi.Result`](../../../internal/gameapi/module.go) 已有 `Cooperative`：胜利时 `Winners` 包含全部席位，失败时为空，所有席位 `Ranks` 都为 1。它显式支持「无人获胜的合作失败」，不需要虚构对手或将结果标记成和局。星垒和篮球已有此结果用法。

但 [`rateMatch`](../../../internal/server/ratings.go) 目前同时有两道限制：合作结果强制不计分；没有赢家且不是和局时也不进入计分。这意味着仅删除 `Cooperative` 的排除条件仍不能实现合作失败扣分，且通用排名公式会给 `rank=1` 的失败者错误扣分幅度。

[`cooperative_e2e_test.go`](../../../internal/server/cooperative_e2e_test.go) 明确断言合作局无积分流水；[`results.tsx`](../../../web/src/ui/results.tsx) 还写着「合作对局不计竞争积分」。这些契约、测试和文案都要随新的策略更新。

### 建议结算口径

「全部通过」按整队完成第一轮八关理解。角色阵亡不等于退出参战名单；只要队伍最终通关，已经耗尽生命的队友仍然一起得分，不要求两个人同时存活站在终点。

| 状态 | 团队结果 | 积分建议 |
| --- | --- | --- |
| 完成第一轮全部八关并触发最终通关状态 | 全队胜利，全部初始参战席位为赢家 | 每位计分真人 `+20` |
| 一人耗尽生命，队友仍可继续或合法借命 | 挑战进行中 | 暂不结算 |
| 全灭但仍可依原版规则续关 | 续关阶段，仍是同一局 | 暂不结算 |
| 续关耗尽，或最终选择不再续关 | 全队失败，无赢家 | 每位计分真人 `−10` |
| 主动放弃已经开始的计分挑战 | 全队失败 | 每位计分真人 `−10` |
| 刷新、短时掉线、重连、服务器恢复 | 继续同一挑战 | 不重复结算，不自动改为失败或托管 |
| 加载前取消、可确认的平台技术故障且无法恢复 | 技术中止 | `0`，保留原因 |

`+20 / −10` 是沿用平台现有阵营计分幅度的建议，用户尚未指定具体数值；「通关同加、失败同扣」是本次要求。前七关的分数、杀敌数、个人原版得分可记录为成绩，不提前发放平台积分。

默认沿用现有「显式电脑席位或占玩家角色的游戏内固定电脑参与，则整局不计分」规则；后者由 `Match.HasComputerPlayers` 标记。关卡敌人和 Boss 不属于这类玩家角色。纯真人双人合作进入计分；单人可作为同一挑战策略的一人实例。若单人采用练习规则，必须在创建时明确不计分，不能通关后才取消奖励。增命秘籍、选关、无限续关、自定义难度或导入任意存档应单列练习模式，不进入标准挑战计分。

当前平台区分真人主动托管与显式电脑席位，前者不会单独把 `Rated` 清为 false。本方案沿用此口径：开局参与计分的真人主动托管后仍共享团队积分，不暗中改变已承诺的奖励。需要承认自动通关可能影响积分可比性；若后续决定托管局不计分，必须先统一调整平台政策、提前展示并记录整局曾使用托管，不能只在魂斗罗结算时另加例外。

### 公共策略的最小改动

建议给模块配置可信的合作挑战计分策略，例如 `coop_campaign_v1`；此名称是设计建议，目前没有该字段。

1. 开局由服务端锁定 `match_id`、原始参战名单、规则版本、计分策略与资格，客户端不能直接提交积分或切换策略。
2. `Result.Cooperative` 保持现有全赢／全输语义。`rateMatch` 对已启用策略的合作终局先分支：全员赢家为正分、无人赢家为负分。失败不能被「没有赢家」的旧入口条件拦截。
3. 保留机器人、练习和技术中止的资格检查；保留合作局全员同 rank 的校验，不伪造 `Team`、`Draw` 或失败排名。
4. 复用归档与 `rating_ledger` 的同一 SQLite 事务、`(match_id,user_id)` 唯一键。幂等重试、重启和重新打开结算都不得再次加减分。
5. 历史记录增加策略版本和终局原因，界面显示「全队通关」或「挑战失败」及每人变化；按实际不计分原因显示文案。
6. 已结束的合作局及部署前已开始的旧局不追溯计分。星垒等游戏逐个声明完整挑战终点后接入，不因存在 `Cooperative` 就自动更改全部历史行为。

平台现有积分本就不是零和 Elo，合作通关同加分可接入现有流水，无需人为给队友排高低。如果未来要比较竞技强弱，可按合作／对战分别展示成绩；这不应成为本次实现同加同扣的前置工程。

### 必须同时补上的退出边界

目前进行中的房间保留座位，房主仍有结束房间的公共入口；旧规则把中止视为不计分。计分合作若直接沿用，会允许失败前关闭牌桌逃避扣分。应在公共策略中区分「玩家放弃」与「平台技术中止」，让前者产生正式失败结果并先归档再关闭。是否要求队员共同确认放弃属于交互选择，不能让房主绕过失败结算。

同时审查 `Match.Eliminated`：它目前表示「已无决定或责任、可以离开」。仍可借命或仍有团队结算责任的角色不应仅因生命为零就标记为这种平台淘汰状态。原始名单必须保留到结算，退出页面不改变本局的加减分归属。

掉线不是放弃。服务器需要明确断线后的继续／暂停／恢复规则；不自动接管。已有 [`expireIdleRooms`](../../../internal/server/inactivity.go) 会在普通房间 24 小时、暂停房间 30 天无操作后关闭房间，并按不计分中止处理。计分挑战必须同时接管该路径：按开局已公开的到期规则终结，或保留可恢复挑战与计分责任，不能用普通自动清理逃避结算。最终期限由服务器记录，不依赖浏览器定时器；不能仅因存档尚未通关就立即判负。

## 6. 先定义验收，再写实现

以下是实施前应建立的失败场景与 E2E 清单，本轮未声称已经通过。

| 范围 | 必须覆盖的失败场景 | 可核验产物 |
| --- | --- | --- |
| 原版身份与映射 | 选到改版／街机版；混用日美 bank；RAM 当代码；切片错位 | ROM／工具摘要、bank 映射、REA Evidence |
| 操作与物理 | 短按丢失、斜射错误、跳跃逐帧漂移、连发停不下、移动越界 | 原版与独立引擎同输入轨迹、首个差异帧 |
| 完整流程 | 仅第一关可玩；基地或纵向关卡停滞；Boss 转阶段错误；通关后进入循环导致不结算 | 八关录像、事件记录与最终状态 |
| 合作生命周期 | 一人死亡就判负；借命重复扣除；续关重置匹配 ID；队友阵亡漏发奖励 | 双人完整成功／失败回放与账本 |
| 网络 | 双人延迟不对称、丢包、乱序、重传、预测超前、帧批次吞输入 | 两端按键／确认序列、延迟与校正测量、快照摘要 |
| 电脑与托管 | 只追敌不推进、跳坑卡死、抢镜头、偷读隐藏敌人、取消后旧输入继续 | 全电脑、真人混合、单人托管完整对局 |
| 保存与恢复 | 崩溃后刷生命、重放奖励、随机状态变更、旧引擎快照误读 | 关键阶段重启回放、归档与积分唯一性检查 |
| 计分 | 无赢家漏扣、部分赢家、结束房间／自动清理逃分、普通与暂停挑战到期、重启时过期清理、一次通关多次奖励、旧局被补算、电脑局误计分 | HTTP E2E、数据库流水和历史截图 |
| UI | 320 px 触屏难操作、资源零值不可见、全屏丢按钮／弹窗、ESC 后输入残留 | PC／320 px 截图、原生键鼠与多指触摸结果 |
| 加载与媒体 | 假进度、二重屏障死锁、重连暂停所有人、受击音重播 | 真实加载测量、切关／断网记录、媒体事件序列 |
| 性能 | 机器人或序列化阻塞全局锁，普通房间随实时负载卡顿 | 真实引擎的多房间压力结果；不借用合成计数器容量结论 |

网络原型可先使用 RTT 0／50／100／150 ms、非对称延迟、抖动和短暂断流作为试验矩阵；这些是建议实验条件，不是已达到的服务承诺。根据输入到画面延迟、回滚幅度及操作成功率决定正式支持范围。

复杂功能优先以 E2E 验收。少量定点运算或协议隔离测试也须先列失败场景、先写测试，再写实现。结果至少保存输入序列、初态、ROM／引擎／素材摘要、场景与随机状态、截图或录像、日志和重复执行命令。验收只覆盖魂斗罗与实际变更的公共契约，不启动无关游戏的完整规则矩阵。

## 8. 本轮证据与复查

本轮通过：5 个候选压缩包的 CRC／内容检查、两版原版 payload 匹配、源 ZIP 检查前后摘要不变、日版 REA 归档分析、RESET 函数的真实 Ghidra 分析。原版动态玩法、八关通关、联机体验、电脑和新计分方案尚未实施或验收。

从仓库根目录复查 ROM 身份与静态入口：

```sh
python3 -B scripts/contra/probe_roms.py
sh scripts/contra/probe_rea.sh
```

第一个脚本只读用户 ROM，下载固定提交的 DAT，结果写入 `.local/nes-contra-research/`。第二个脚本使用已安装的 `rea`、Ghidra 和 JDK；默认复用本机篮球研究工具路径，可用 `GHIDRA_INSTALL_DIR` 与 `JAVA_HOME` 指定已有安装，不自动安装工具。Ghidra 临时目录位于仓库内 `dist/contra-research-tmp/`，不会主动改写工作区外的文件。

归档分析可使用 REA `open_binary` 打开上述日版 ZIP，再调用 `inspect_artifact` 和 `export_evidence_bundle`，将输出指定到工作区内。证据中的静态结论应连同 ROM 摘要、映射假设和警告一起复查。

本轮最终保留本说明、两个复查脚本及 `evidence/` 中的完整检查记录。清理范围限于本轮生成的 ROM 切片、REA 临时项目和缓存；不删除用户 ROM、篮球研究工具、现有原型或其他游戏产物。
