# 地形工作值的完整帧来源与接入约定

原版随后执行的守卫清墙会读取前面操作留下的工作值。这个值可能来自玩家查询、扫行、武器透视、地图流式写入或图形定位，不能把它固定为零，也不能始终解释成最后一次绘图地址。独立规则使用一个 `TerrainWork` 所有者和具名操作保存这些结果，不提供通用 RAM 读写或 CPU 指令执行。

本项保留 2,997 个完整 `C001 → F8DB` 帧样本，包含 112,254 次原版工作值写入、27,220 个语义操作和 3,047 个检查点。参考投影每条场景只读一次初态工作值，之后按实际操作参数连续计算；没有把原版写入值或帧末结果回填到模型。所有已捕获写入均有对应操作，也没有发现帧间额外写入。

这些证据验证工作值和消费接口，不等同于整个 World 的八关连续验收。玩家位置、操作调用及部分消费者上下文来自原版观测，实际 World 是否在相同位置调用这些接口仍须另行验证。

## 来源与字节含义

`TerrainWork.Value` 为 16 位；下表的 low／high 指它的低／高字节。原版研究地址 `$12/$13` 只用于证据定位，运行时接口不接收地址参数。

| 具名操作 | 原版入口 | 确认的结果 |
| --- | --- | --- |
| `RecordQuery(sample)` | `$DFEC/$DFEE/$DFF4` | low=`TerrainSample.Column`，high=`SourceIndex`。Y≥224 返回空地形时仍发布计算出的列和索引。 |
| `RecordIndexRead(index)` | `$DFE0/$DFE6` | 仅 high=`index`，low 保留列。侧边、向下扫行每次实际读取都会更新索引。 |
| `RecordEntityProbeOverflow(x)` | `$EB9B` | 敌人 `Y+dy` 溢出前已写横向探测位置：仅 high=`x`，low 保留。 |
| `RecordGraphicLocation(address)` | `$C656` | 完整图形定位结果。队列拒绝未进入此函数时，不发布零值或假地址。 |
| `RecordStreamColumn(address)` | `$DD4B`、`$DF30` | 偶数列完成 14 次碰撞打包后，low=`(((address>>8)&4)<<4 \| (uint8(address)>>3))+56`，high=`(uint8(address)>>1)&3`。奇数列仅 low=`address>>8`，high 保留。 |
| `RecordStreamRow(axis)` | `$DDEF`、`$DF30` | high=0；low=`(axis>>1)*4`，偶数 axis 再加 4，奇数 axis 不加。 |
| `RecordPerspectiveX(x)` | 玩家 `$D7D1`、武器 `$83E3` | 仅 low=`uint8(x-128)`，high 保留。 |

查询与流式碰撞打包的字节角色相反。流式写入也不是「只有碰撞格实际改变时才产生工作值」：奇数 tile 列和奇数 tile 行仍执行部分准备写入。

`DFB8` 会在平台下检查实心格，并在返回前恢复原索引；它的最终工作结果仍对应最初查询点。`DFE0` 对给定索引执行相同的下层检查，最终 high 恢复为输入索引。无需把短暂的下层索引保留到下一操作。

玩家脚底的 `$D8D9` 与敌人探测不同：玩家 `Y+16` 溢出时完全不写工作值，室内固定地板判断也不写。不能套用敌人的「溢出只写 high」规则。

## 接入位置

- 玩家脚底、头部和水面等真正调用地形查询的分支，使用实际探测坐标发布 `RecordQuery`；分支没有查询时保留工作值。不能用玩家帧末位置补算。
- `hasSupportBelow`、`sideSolid` 的循环要在每次实际扫行后发布索引。检查实心支撑的辅助读取返回时恢复原索引，不把第二行临时位置误作最终结果。
- 室内前进的透视初始化会按玩家 2、玩家 1 的顺序处理尚未初始化的角色，包括已退出的另一角色；每次实际初始化后发布该角色的横向偏移。只发布当前操作玩家会丢失原版顺序。
- 室内成功发射的弹丸在 `$83E3` 计算透视速度时发布发射玩家的 X 偏移。必须在实际发射位置生效，后续玩家移动／查询可能再次覆盖它。
- 普通武器的地形探测发生在移动之前。它调用 `$DFB8`，需要同时保留实心支撑判断和原查询位置；未启用地形碰撞、尚未激活或未执行查询的弹丸不产生工作更新。
- `tileColumn` 使用调用时的 `TileAddress`，`tileRow` 使用调用时的 `Axis`。不要等外围循环递增／递减游标后再取值。初始化背景和战斗滚屏复用同样的具名操作。
- World 的事务副本持有唯一 `TerrainWork`。敌人的 `AlienBossContext.CollisionAddress` 借用同一个 `Value`，图形回调和流式操作也指向同一所有者；保存、重连及回滚不能另造副本或逐帧归零。

本项没有修改玩家、武器、滚屏或 World 的接线代码。根任务已经实现具名所有者；接线完成后须用连续 World 样本核验真实操作位置和顺序。

## 真实武器碰撞差异

第六关普通按键路线的 800 个玩家／武器阶段中，有 26 次武器查询遇到「当前格是平台，下方格是实心」。原版返回 `$80` 并进入命中阶段。首个例子在模拟器 frame 1549：原版弹丸停在 X=247，routine=2、Timer=6；原调用方只返回 `At.Kind`，弹丸继续到 X=250。

`TestOriginalWeaponTerrainSupportContract` 先保留失败，再由 `frame.go` 的调用方恢复 `$DFB8` 判断。测试从真实玩家阶段入口推进输入，并比较完整弹丸池；800 个阶段通过。它不单独声明其他 World 字段均已验收。

## 守卫清墙与有限图形队列效果

守卫拒绝绘图后仍执行 `$E989/$E9CA`。原版按以下掩码解释工作值，而不是先验证它是 PPU 地址：

```text
index  = ((value >> 8) & 7) << 4
       | ((value >> 4) & 12)
       | ((value >> 3) & 3)
column = (value >> 1) & 3
```

每块处理两行、每行两个 2-bit 碰撞格。最大索引为 132，超出 `CollisionWindow` 的部分恰好对应相邻图形队列的前 5 个字节。因此不能简单放宽地址校验、丢弃越界写入或把索引夹回碰撞窗。

在一个实际查询路径构成的受控完整帧中，E54F 入口值为 `$1801`，守卫下一阶段先减 `$20` 得到 `$17E1`，第二行命中图形队列首字节。原版依次使用 `$3F/$CF/$F3/$FC` 保留掩码，把首个 Kind 从 1 清为 0。对应输入队列的 81 字节来自此前真实原版运行的三个完整图形包。

独立规则通过 `ClearQueuedGraphicsPrefix(offset, andMask)` 发布这项有限效果，offset 只允许 0..4。`GraphicsQueue.ClearPrefix` 保留原有结构化包和 `Used`，编码时应用头部清位覆盖。首 Kind 变为 0 后停止绘图，但队列预算不变：同帧图形准入和下一帧调色板准入仍使用原游标。`Clone`、`Reset` 和保存状态也必须保留相应含义。

清墙的低字节左移发生在格写入及队列回调之前。测试逐条比较四次原版队列写入的掩码、结果和当时工作值，并比较完整编码、预算、碰撞窗和终止绘图行为。对无法在已有队列范围内解码的修改头，队列返回明确错误；本项没有把后续调色板／比分区域变成任意内存读取。
