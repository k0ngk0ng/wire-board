# 发布与部署规范

适用范围：提交验收、GitHub 版本发布、服务器更新、备份、回滚与清理。开发和工作区边界遵循[通用规范](common.md)，客户端资产遵循[加载与资源发布规范](loading.md#发布资产与镜像边界)。操作示例见[服务器部署与运维](../docs/deployment.md)。

## 授权与私密信息

- 发布和服务器更新按当前会话中的用户授权执行。已经明确授权的范围可以继续推进，不重复要求确认；发布成功与服务器更新完成分别核验、分别报告。
- 实际连接地址、域名、账号、端口、SSH 密钥路径、口令和令牌只在 Git 忽略的 `.local/` 或服务器私密配置中维护，不写入本文件、`AGENTS.md`、提交或 Release 说明。连接与部署入口查阅 `.local/server-access.md`；实际状态以本次读取为准，不能把其中的历史版本记录当成当前版本。
- 提交前核对工作区与远端状态，只纳入本次授权的文件；保留其他任务的修改、研究素材和未跟踪文件。日志与验收记录不得输出凭据。

## 检查范围与构建

- main 按影响范围验证，游戏独立维护、独立验收。公共检查覆盖平台、模块契约、公共前端、边界、编译和部署工具；不得因为修改一款游戏而固定运行其他游戏的规则、完整对局或扩展组合矩阵。遗留在公共目录的游戏专属测试也按归属选择。
- 游戏前端或素材修改只运行对应前端／素材检查；操作修改另保留本地 E2E 证据。服务端规则、规则测试及夹具修改才启动对应游戏的规则、完整对局和竞态验收。共享组件按明确消费者确定范围，不默认扩大到所有游戏。
- 增量范围从最近已验证的祖先构建计算，覆盖被取消或失败的前序提交；首次没有有效基线时建立完整基线。手动入口可指定单个游戏或显式选择全量验收。
- 所有本次必需检查通过后才生成可发布构建，保留检查范围和结果。以 `.github/workflows/build.yml` 中同一提交 SHA 的 `Test and Linux amd64 binary` 成功作业及其 `wire-board-linux-amd64` 产物作为发布来源。
- 前端模块、客户端运行时和素材发布到 OSS/CDN 不可变版本目录，按加载规范核验摘要、MIME、CORS 和实际回读结果，再从服务器包剥离。检查最终包、二进制嵌入内容及镜像，不能只检查 Dockerfile。入口和不含资源正文的清单仍可由应用服务器提供。
- 服务器构建前只保留入口与元数据清单；构建后运行 `scripts/cdn_delivery.py check-package`，核对二进制本身的 SHA-256、构建收据和嵌入文件清单，保存 `server-package-boundary` 产物。仅验证压缩包中的文件名不够，因为载荷可能被嵌入可执行文件。
- 客户端运行时与源码／构建标识的绑定必须有效。发布不得为绕过缺失产物而使用旧运行时、关闭校验或改变游戏注册和上架设置。

## 正式版本发布

1. 确认待发布提交已推送至 main，并等待该 SHA 的必需检查及 Linux 构建成功。
2. 选择未发布的 `vX.Y.Z` 版本号。创建指向已验证 SHA 的版本 tag，并通过推送 tag 触发 `.github/workflows/publish-verified.yml`。
3. 核对 Actions 的 ref 是该版本 tag，运行名称包含版本号。禁止用 `workflow_dispatch --ref main` 代替正式 tag 发布。
4. 发布任务复用同一 SHA 的 `wire-board-linux-amd64`，验证 `SHA256SUMS`，再打包运行镜像。tag 不重新编译应用，不重复规则分片、完整对局或扩展组合矩阵，也不重复上传客户端资产。
5. 检查容器启动、`/healthz` 和 SQLite 备份工具。核对版本 tag、Release、版本镜像及 `latest` 对应同一发布提交，再确认发布成功。

缺少匹配的有效构建、产物已过期、校验失败或来源检查失败时，停止发布。不得改用其他 SHA 的产物，也不得移动已经发布的版本 tag。手动恢复发布同样必须指定对应版本 tag，并提供匹配的运行编号、完整 SHA 和版本号；历史产物迁移也须核对提交一致与构建作业成功。

## 服务器更新与回滚

1. 从 `.local/server-access.md` 获取实际连接与部署信息。更新前记录当前版本、镜像摘要／标签、健康状态、游戏管理设置和剩余空间。
2. 在实际部署目录以已发布的明确版本执行 `./update.sh vX.Y.Z`。服务器使用现有脚本拉取镜像，不在服务器重新构建，不用浮动的 `latest` 代替本次目标版本。
3. 脚本持有 `.update.lock`，验证 Compose 配置，使用 SQLite 在线备份 API 获取包含已提交 WAL 数据的一致快照，检查可读性后再切换容器。不得复制正在写入的数据库文件冒充备份，也不得启动第二个游戏服务进程访问同一数据卷。
4. 脚本将版本解析为镜像摘要，等待容器健康；切换失败时尝试恢复上一镜像，保留备份。不得在失败后继续标记部署成功，或用旧数据库覆盖更新期间的新数据。
5. 更新后核对公网与本机的 `/api/version`、`/healthz`、容器健康、镜像版本／提交标签、二进制摘要与前端 CDN 提交目录。检查既有游戏上下架及其他管理设置没有被覆盖。

保留服务器的 `.env`、数据卷、`.image.env` 和 `.previous-image`。如果发现另一项授权部署已经推进到更新版本，先核对实际状态，不能无意回退。回滚使用既有脚本和已知有效版本，并再次执行健康、版本及数据检查。

## 更新后的清理

- 只有更新、健康、版本和管理设置核验成功后，才清理旧备份。持更新锁确认本次更新前备份和紧邻上一份可读取，保留这两份；只删除已识别的更旧数据库备份，不扩大到数据卷、用户素材或其他服务文件。
- 释放备份清理所持的更新锁后，运行部署目录的 `./update.sh clean`。保留当前镜像、上一版回滚镜像和任何容器仍引用的镜像；不执行全局 Docker prune。
- 清理后再次核对服务健康和剩余空间。保留可核验的运行编号、提交 SHA、版本、镜像摘要、备份与设置对比、检查结果和必要截图；删除本次临时构建、浏览器 profile、失败或重复运行的中间产物。
- 发布、部署、备份清理和镜像清理分别记录结果。未执行或失败的步骤如实说明，不把 Release 已公开等同于服务器已更新。
