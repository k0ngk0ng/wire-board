# 发布与部署规范

适用范围：提交验收、GitHub 版本发布、服务器更新、备份、回滚与清理。开发和工作区边界遵循[通用规范](common.md)，客户端资产遵循[加载与资源发布规范](loading.md#发布资产与镜像边界)。操作示例见[服务器部署与运维](../docs/deployment.md)。

## 授权与私密信息

- 发布和服务器更新按当前会话中的用户授权执行。已经明确授权的范围可以继续推进，不重复要求确认；发布成功与服务器更新完成分别核验、分别报告。
- 实际连接地址、域名、账号、端口、SSH 密钥路径、口令和令牌只在 Git 忽略的 `.local/` 或服务器私密配置中维护，不写入本文件、`AGENTS.md`、提交或 Release 说明。连接与部署入口查阅 `.local/server-access.md`；实际状态以本次读取为准，不能把其中的历史版本记录当成当前版本。
- 提交前核对工作区与远端状态，只纳入本次授权的文件；保留其他任务的修改、研究素材和未跟踪文件。日志与验收记录不得输出凭据。

## 检查范围与构建

- main 按影响范围验证，游戏独立维护、独立验收。公共检查覆盖平台、模块契约、公共前端、边界、编译和部署工具；不得因为修改一款游戏而固定运行其他游戏的规则、完整对局或扩展组合矩阵。遗留在公共目录的游戏专属测试也按归属选择。
- 小改动先选择快速组件检查：按模块和测试文件映射，不按改动行数猜测风险。快速结果独立于应用构建；未映射的公共核心改动仍执行公共检查。每个受影响游戏对应一个并行任务；仅修改 CI 或文档不生成应用发布包。手动 `validation=quick` 不上传 CDN、不打包，无法覆盖的改动必须报错。配置与重放方法见 [CI 检查范围](../scripts/ci/README.md)。
- 魂斗罗的初始化、负向和竞态验收只在该游戏任务执行；电脑研究只能通过独立工作流手动触发。公共打包保留必要的源码／运行时标识绑定，不重复执行游戏验收。
- 游戏前端或素材修改只运行对应前端／素材检查；操作修改另保留本地 E2E 证据。服务端规则、规则测试及夹具修改才启动对应游戏的规则、完整对局和竞态验收。共享组件按明确消费者确定范围，不默认扩大到所有游戏。
- 增量范围从最近已验证的祖先提交计算，覆盖被取消或失败的前序提交；首次没有有效基线时建立完整基线。CI／文档改动的成功汇总和检查计划可推进验证基线，不要求生成二进制；发布仍必须有同一提交的成功二进制构建。手动入口可指定单个游戏或显式选择全量验收。
- 发布重试必须复用输入未变且已有成功证据的游戏，不重复运行其完整验收。只重跑失败、尚未验证或输入确实变化的游戏；公共检查按实际影响范围执行。已有成功祖先时也须核对部分通过结果，不能仅因一次失败重新调度此前全部游戏。
- 所有本次必需的 CI 检查通过后才生成候选构建，保留检查范围和结果；本地 CDN 回读通过后才允许发布。以 `.github/workflows/build.yml` 中同一提交 SHA 的 `Test and Linux amd64 binary` 成功作业及其 `wire-board-linux-amd64` 产物作为发布来源。
- 前端模块、客户端运行时和素材发布到 OSS/CDN 游戏命名空间与不可变内容地址，按加载规范核验摘要、MIME、CORS 和实际回读结果。检查最终包、二进制嵌入内容及镜像，不能只检查 Dockerfile。入口和不含资源正文的清单仍可由应用服务器提供。
- 素材发布同时遵循[资源地址稳定与上传去重](loading.md#资源地址稳定与上传去重)。应用更新不改写未变素材的 URL，也不重复上传相同对象；发布清单须明确复用与新增的数量及上传字节数。
- **CDN 回读校验必须在本地执行，不得在 GitHub Actions 中执行，避免跨区域网络问题。** Actions 只上传不可变资源，并基于精确上传清单剥离和构建候选服务器包；上传完成不等于 CDN 校验通过。本地必须下载同一提交、同一次成功构建的 `web-dist`，执行 SHA-256、大小、MIME、CORS 和音频 Range 回读，保存报告，并通过 `scripts/cdn_local_ready.py --run <运行编号> --sha <完整提交> --mark-ready` 写入绑定该构建的 `cdn-local-readback` 状态。缺少成功的本地状态时，tag 发布必须拒绝；未经本地回读通过的候选包不得发布或更新服务器。
- 构建可以从已有成功构建恢复不可变素材缓存，但只复制与当前素材清单的大小和 SHA-256 完全匹配的文件。缓存恢复不复制旧应用代码或服务器程序；本次应用仍从当前提交构建，CDN 上传与回读校验照常执行。
- 服务器构建前只保留入口与元数据清单；构建后运行 `scripts/cdn_delivery.py check-package`，核对二进制本身的 SHA-256、构建收据和嵌入文件清单，保存 `server-package-boundary` 产物。仅验证压缩包中的文件名不够，因为载荷可能被嵌入可执行文件。
- 客户端运行时与源码／构建标识的绑定必须有效。发布不得为绕过缺失产物而使用旧运行时、关闭校验或改变游戏注册和上架设置。

## CI 流量与费用

- 普通 CI、单游戏检查、全量验收、研究任务和候选包构建的 OSS／CDN 资源正文下载预算为 **0 字节**。资源必须通过 `.github/actions/restore-resources` 从 GitHub 缓存恢复。缓存缺失、过期、摘要不符或服务不可用时，任务失败并记录缺失项；禁止自动回源、忽略恢复失败、扩大预算或改走 CDN 掩盖下载成本。
- 资源按用途登记。前端构建只恢复公开素材、前端直接导入的图片与字体、客户端运行时的声明输入及必要编译输入；服务器打包只恢复服务端编译和发行输入；共享检查只恢复平台输入；游戏检查只恢复对应游戏、公共测试和必要编译输入。不得因修改一款游戏而恢复其他游戏的测试夹具、研究资料或历史验收产物。共享静态检查不得通过 `go vet ./...` 隐式要求所有游戏的测试嵌入资源。
- 缓存键按本用途实际引用对象的 SHA-256、大小、MIME、编码和逻辑映射计算，不绑定应用提交、构建日期或无关游戏的资源清单。恢复前校验路径、符号链接、对象身份与本次清单；每次使用仍校验缓存正文的 SHA-256 和大小。
- 缓存准备只允许通过 `Prepare bounded private resource cache` 的显式手动入口执行。默认预算为 0，操作者必须提供非负整数的字节上限；单次硬上限为 2 GiB。执行前按去重后的缺失对象预留读取上限，超过预算时不得发出请求。响应超限立即失败；请求失败不自动重试。已保存且校验通过的缓存对象可继续复用；GitHub 缓存只在本次完整准备成功后保存。
- OSS 私有桶继续使用服务端或 GitHub Secrets 中的密钥签名访问。密钥不得进入缓存、资源包或验收报告。私有权限不代表公网下载免费；签名、公网端点、CDN 和内网端点的权限与计费边界必须分别核对。
- CI 发布不得为判断对象是否存在或复用而 GET 对象正文。当前构建的已有文件通过 HEAD 核对编码、MIME、长度、ETag 及已有摘要元数据；新对象以 Content-MD5、SHA-256 元数据和禁止覆盖的 PUT 写入。并发冲突通过 HEAD 复核。经过成功本地回读的历史外部对象可按完整身份记录复用；未知外部对象缺少可信记录或摘要元数据时停止发布。
- 每个资源恢复和发布任务必须保留实际 GET／HEAD／PUT 次数、下载字节数、上传字节数、缓存命中和缺失数量。失败也须保留报告，禁止用「上传 0 字节」代表无流量。上传成功、本地 CDN 回读、源码绑定和服务器包边界仍是独立验收项。
- 流量策略由 `scripts/ci/traffic-policy.json`、`traffic_lint.py` 和本机 HTTP／HTTPS E2E 共同约束。新增恢复入口、发布工具或工作流前，先补充失败场景与验证；普通检查必须拒绝直接下载、付费回退、自动缓存预热、非零预算和发布对象 GET。不得仅修改规则文字或放宽流量门禁以修复 CI。

## 正式版本发布

1. 确认待发布提交已推送至 main，并等待该 SHA 的必需检查及 Linux 构建成功；在本地完成同一次构建的 CDN 回读并记录成功状态。
2. 选择未发布的 `vX.Y.Z` 版本号。构建前在 `web/src/releases/history.json` 顶部记录版本号、日期、标题和完整更新内容，按版本号倒序排列，保留已有记录。网站详情与 GitHub Release 使用同一份正文；发布门禁拒绝缺失、空白、重复、无效日期或顺序错误的日志。历史记录和维护方法见[版本更新日志](../docs/release-history.md)。创建指向已验证 SHA 的版本 tag，并通过推送 tag 触发 `.github/workflows/publish-verified.yml`。
3. 核对 Actions 的 ref 是该版本 tag，运行名称包含版本号。禁止用 `workflow_dispatch --ref main` 代替正式 tag 发布。
4. 发布任务复用同一 SHA 的 `wire-board-linux-amd64`，验证 `SHA256SUMS`，再打包运行镜像。tag 不重新编译应用，不重复规则分片、完整对局或扩展组合矩阵，也不重复上传客户端资产。
5. 检查容器启动、`/healthz` 和 SQLite 备份工具。核对版本 tag、Release、版本镜像及 `latest` 对应同一发布提交，再确认发布成功。

缺少匹配的有效构建、产物已过期、校验失败或来源检查失败时，停止发布。不得改用其他 SHA 的产物，也不得移动已经发布的版本 tag。手动恢复发布同样必须指定对应版本 tag，并提供匹配的运行编号、完整 SHA 和版本号；历史产物迁移也须核对提交一致与构建作业成功。

## 服务器更新与回滚

1. 从 `.local/server-access.md` 获取实际连接与部署信息。更新前记录当前版本、镜像摘要／标签、健康状态、游戏管理设置和剩余空间。
2. 在实际部署目录以已发布的明确版本执行 `./update.sh vX.Y.Z`。服务器使用现有脚本拉取镜像，不在服务器重新构建，不用浮动的 `latest` 代替本次目标版本。
3. 脚本持有 `.update.lock`，验证 Compose 配置，使用 SQLite 在线备份 API 获取包含已提交 WAL 数据的一致快照，检查可读性后再切换容器。不得复制正在写入的数据库文件冒充备份，也不得启动第二个游戏服务进程访问同一数据卷。
4. 脚本将版本解析为镜像摘要，等待容器健康。只在上一镜像支持数据库记录的存档兼容代次时自动恢复上一镜像；跨代次切换后须保留原卷和备份，使用兼容镜像恢复服务。不得在失败后继续标记部署成功，或用旧数据库覆盖更新期间的新数据。
5. 更新后核对公网与本机的 `/api/version`、`/healthz`、容器健康、镜像版本／提交标签、二进制摘要与前端 CDN 游戏命名空间及清单来源提交。检查既有游戏上下架及其他管理设置没有被覆盖。

保留服务器的 `.env`、数据卷、`.image.env`、`.previous-image` 和 `.storage-generation`。存档兼容代次由镜像标签 `io.github.k0ngk0ng.wire-board.storage-generation` 声明，缺省为 0。新版可能写入旧版无法读取的存档信封、新游戏或新核心时，发布前提高代次并验证兼容恢复。首次启用该机制须先安装新版 `update.sh`，再切换镜像。如果另一项部署已推进到更新版本，先核对实际状态。回滚使用已知有效版本，并再次执行健康、版本及数据检查。

## 更新后的清理

- 只有更新、健康、版本和管理设置核验成功后，才清理旧备份。持更新锁确认本次更新前备份和紧邻上一份可读取，保留这两份；只删除已识别的更旧数据库备份，不扩大到数据卷、用户素材或其他服务文件。
- 释放备份清理所持的更新锁后，运行部署目录的 `./update.sh clean`。保留当前镜像、上一版回滚镜像和任何容器仍引用的镜像；不执行全局 Docker prune。
- 清理后再次核对服务健康和剩余空间。保留可核验的运行编号、提交 SHA、版本、镜像摘要、备份与设置对比、检查结果和必要截图；删除本次临时构建、浏览器 profile、失败或重复运行的中间产物。
- 发布、部署、备份清理和镜像清理分别记录结果。未执行或失败的步骤如实说明，不把 Release 已公开等同于服务器已更新。
