# 存档与续玩规范

适用范围：全平台的长期存档、保存退出、继续游戏，以及接入这些能力的游戏模块。开发同时遵循[通用规范](common.md)、[界面规范](ui.md)、[加载规范](loading.md)和[发布规范](deploy.md)。接口与复现命令见[保存退出与续玩](../docs/saved-games.md)。

## 能力与职责

- 长期存档是游戏按需接入的可选能力，不要求所有游戏支持。只有服务端模块显式声明 `SupportsSave`、完成接入验收后，才开放保存入口；前端按钮不能自行启用能力。
- 平台统一负责账号鉴权、原真人名册、席位释放、存档列表、状态流转、逻辑时钟、事务、幂等和发布。游戏负责完整规则快照、格式校验、输入清理及版本兼容，不另建账号、存档大厅或旁路写入接口。
- 长期存档与普通暂停、断线重连、客户端缓存、操作录像分开处理。`Match.Paused` 本身不代表长期存档，也不能让普通暂停房间自动获得存档权限。

## 身份、权限与实例

- 保存时保留原房间 ID、`MatchID`、规则选项和原席位身份。继续同一存档不得新建独立对局、重新抽签或重新发放初始资源；同一存档只能有一个可推进实例。
- 权限绑定认证账号 ID。单人存档仅本人可见和续玩，一次继续即可恢复；多人存档仅原名册中未退出的真人可见和确认，原成员到齐后恢复。相同昵称、房主转交、知道存档 ID 或原房间密码都不能替代原账号。
- 电脑席位不参与保存／续玩同意。真人托管仍是真人席位，电脑不能代替本人同意，也不能自动保存退出。
- 保存成功后释放原真人的活动席位，存档移出活动房间目录，账号可以进入其他游戏。未加入续玩等待的原成员不占用该存档席位；同一账号仍须遵守平台当前房间／观战互斥规则。
- 存档摘要只返回展示所需元数据，不返回完整规则状态、私有牌面、原生内存或随机种子。陌生账号与观众不能读取、加入或恢复存档；旧观战关系不能跨保存继续生效。

## 保存与继续

| 状态 | 允许的操作与推进 |
| --- | --- |
| `playing` | 正常操作；符合接入条件时申请保存。确认绑定当前局面，进度或控制状态变化使旧确认失效 |
| `playing` 且处于保存确认暂停 | 原真人确认或取消本次保存；规则、电脑和计时停止 |
| `saved` | 已持久化且不占活动席位；只有原真人可申请继续，规则不推进 |
| `restoring` | 等待原真人确认；只有已确认者占用续玩席位，规则与电脑仍不推进 |
| 恢复后的 `playing` | 保留原对局身份，建立新操作边界；完成公共加载就绪后继续规则 |

- 保存确认必须针对同一份权威局面。持续推进的游戏若无法在确认期间保持一致，应接入 `SaveControl` 冻结局面，不能跳过版本检查来凑齐确认。
- 使用 `SaveControl` 时，首位真人确认即进入保存确认暂停；任一原真人取消后，撤销本次全部确认，按原剩余预算恢复。未使用该暂停机制的模块，按平台原有逐人撤回及局面变化清票规则执行。
- 单人不增加等待其他玩家、重复确认或重新开局步骤。多人未到齐时不能用电脑、陌生人或更换名册绕过恢复条件。
- 等待续玩期间，已确认者可以离开并释放本人席位；未推进的存档继续保留。所有确认者离开后回到 `saved`，不结算原对局。
- 保存／续玩失败时，保留此前有效的局面和确认状态。只有持久化提交成功后，界面才显示保存成功、释放席位或发布恢复后的状态。

## 可回退的手动存档

- 「保存退出后继续当前进度」与「回退到上次手动存档」是两个能力。需要传统读档的游戏须另行显式接入，不能仅凭 `SupportsSave` 或保留保存时间就宣称支持；其他游戏不因此开放回退。
- 上次成功手动保存的完整规则快照及逻辑时刻须独立保留。继续游玩只推进当前实例，不能让普通帧、自动持久化、重连或恢复后的加载覆盖该手动存档；只有下一次手动保存成功才替换它。
- 游戏可用 `Match.PreserveSavedCheckpoint` 标记失败演出等不可替换手动基准的当前状态。此时保存退出仍持久化完整当前快照，但保留此前可恢复的手动基准；不能让一次失败退出把最后一份可恢复存档覆盖。只有已接入回退的单人非竞技模块可以使用此标记。
- 回退使用平台统一鉴权、加载门槛、版本保留与事务接口，不由游戏另建账号／文件槽。首批范围为已明确支持回退的单人非竞技游戏；真人对战、多人名册及已结算终局不能借用该入口撤销结果。
- 读取由本人明确发起，恢复同一未结算对局的已保存规则、资源、随机状态和逻辑时刻，清理当前瞬时输入并建立新操作边界。重复、并发或旧页面请求不能再次回退已恢复后开始推进的实例；失败须保留当前局面与原手动存档。
- 接入使用 `SupportsCheckpoint` 与 `RestoreCheckpoint(Context, saved, active)`，回调接收两份独立副本。新操作代次必须高于读取前的当前实例，不能只对旧档代次加一，也不能假设平台版本大于游戏代次。数据格式、事务及复现入口见[手动读档说明](../docs/checkpoint-saves.md)。
- 战败时保持原版演出及明确的失败状态，等待玩家读取或重新开始。不能因为原生文件槽未接入而静默丢弃进度或重新发放初始资源；没有手动存档时须如实显示，重新开始按新对局处理。
- `Match.Restartable` 明确声明失败旅程可以重新开始。平台只接受本人确认，建立新 `MatchID`、初始化资源和操作边界，移除旧手动基准；取消、初始化失败及持久化失败须保留原旅程，重复请求不能再次初始化。读取和重新开始状态通过完整快照及即时流保持一致，关键能力变化提交后再发布。
- 验收覆盖手动保存后继续推进、战败与主动读取、旧输入拒绝、离线时钟、随机／资源恢复、幂等、并发、写入失败、进程重启及跨版本运行器选择；平台普通保存续玩夹具不能替代上述读档验收。

## 快照、时间与输入

- 游戏快照必须包含继续所必需的规则状态、随机状态、队伍与资源、未完成决策、脚本续行位置、阅读／菜单位置和剩余时间。不能只保存关卡编号、截图、展示投影或初始种子。
- 平台保存逻辑时刻，冻结保存及等待续玩期间的离线时长。恢复不能补跑离线电脑、物理帧或定时器，不能把剩余操作时间重置为完整时限。
- 即时游戏必须提供 `ResumeSaved`，清理已按住按键、未消费输入、连发、控制租约及旧连接的操作代次。清理只能影响瞬时输入，不能清掉已被规则接受的指令、选择或奖励。
- 保存确认暂停同样需要清理旧输入，并保留原来的剩余预算；取消保存后不能补发暂停前积压的移动、攻击或确认。
- 游戏自身的暂停与为保存增加的暂停必须区分记录。继续或取消保存只解除本次保存暂停，不能擅自解除原来的游戏暂停或关闭原来的菜单。
- 恢复建立新的操作版本下限及游戏控制代次。即使游戏允许即时操作使用旧帧版本，保存前的页面、重试包和旧连接也不能越过恢复边界修改进度。
- 恢复沿用公共资源加载就绪门槛。加载完成前不恢复规则或计时，加载不能重置对局、操作预算或已接受指令。

## 事务、幂等与结算

- 最后一次保存确认、完整快照、房间状态及操作去重记录必须在同一持久化事务提交。继续时的确认、名册、时间映射、输入代次及规则状态同样原子提交。
- 数据库写入、快照读取或模块回调失败，必须一并回滚内存状态、确认名单、占位、计时及对外广播。模块回调不得原地修改传入快照，不能先释放席位再补写存档。
- 重复保存、继续、网络重试及并发请求必须幂等，同一次恢复只能有一次有效提交。并发请求或成功后的重试不能再次初始化或推进规则；失败重试可以从原快照重新计算，不能沿用失败过程中累加的状态。任何部署方式都必须保证同一存档只有一个恢复提交点；进程内锁只能证明单进程情形。
- 保存与等待续玩不是弃局、失败、和局或终局，不新增胜负、积分及结算流水。实际终局仍按原 `MatchID` 去重结算。

## 长期保留与版本兼容

- `saved` 和 `restoring` 不受活动房间的闲置清理期限影响。服务重启后必须保留存档、确认状态及原身份，不能把断电或长时间未玩当作放弃存档。
- 存档应带有可校验的格式／规则版本；依赖原生运行时或资源版本的游戏，还须保留对应标识。平台不解释和猜测游戏私有字节布局。
- 每次影响存档格式、规则运行时或资源解释方式的发布，都必须验证现有存档的继续能力。游戏可保留兼容的旧运行时，或提供经验证的显式迁移；不能只验证新建对局。
- 迁移必须保留原进度、资源、随机状态、未完成操作和剩余预算，保留可回滚的原档，并原子提交。未经验证的跨版本数据必须明确拒绝且保留原档，不能静默重开、丢弃字段或修改版本标识冒充兼容。
- 备份和回滚应覆盖存档本体及其依赖的规则／资源版本。发布清理不得删除仍被有效存档依赖的版本。
- 保存音乐或音效播放位置时，须同时绑定其资源版本及对应时长、采样数等时间元数据。更新音源保留旧版本记录与原 URL；旧档继续使用旧时长，不能只保留最新清单或静默改成当前版本。未知版本拒绝恢复并保留原档。
- 平台存档信封的字段变更同样属于兼容范围。回滚不能让不认识手动基准字段的旧程序写入当前数据库；须使用兼容程序或经过验证的配套备份恢复流程，并核对备份之后新增的存档。
- 发布可能生成旧版读不了的存档时，按[部署规范](deploy.md#服务器更新与回滚)提高镜像的存档兼容代次。覆盖新版本写入存档后启动验收失败、显式降级和兼容版本恢复；验证原卷保留新存档，升级前备份可独立读取。
- 开发辅助构建及修改体力、资源等规则的测试配置，必须使用可区分的存档身份和独立验收产物；正式模式与测试模式不得互相恢复存档，也不能通过改写版本标识绕过校验。可选难度若属于正式玩法，须保存原难度选项并校验其兼容性。测试构建隔离通过不能代替正式版本之间的兼容验收。

## 界面与验收

- 沿用平台「保存并退出」和大厅「继续」入口；不支持存档的游戏不显示无效入口。保存确认、失败、等待续玩和加载状态须与实际服务端状态一致。
- 存档操作遵循公共全屏规范，在游戏区内可操作；反馈优先复用操作区或浮层，不能通过新增占位面板挤占已有游戏区域。覆盖 PC、320px 手机和原生触摸。
- 平台契约验收使用真实认证 HTTP 和 SQLite，覆盖单人、多人原名册、电脑／托管、陌生人／观众拒绝、席位释放与跨游戏、撤回、局面变化清票、事务失败、重启、闲置保留、并发与重复继续、时钟冻结、旧输入拒绝及无重复结算。
- 每个接入游戏另须验证实际玩法中的保存与继续，包括未完成操作、关键资源与随机状态。公共夹具通过不能代替具体游戏验收；同构建恢复不能代替跨版本兼容验收。
- 持续动画场景应比较实际冻结时与恢复后尚未推进时的权威状态，保留原始相位和画面证据；另验加载就绪后动画正常继续。不能将点击保存前或恢复后已推进的画面当作同一时刻，也不能抹去相位差异来证明快照一致。
- 保留可重复执行的测试命令、版本／资源摘要、断言结果与关键截图。并发测试须对应实际部署方式，发布前逐项检查；未覆盖的能力应明确登记为待验收。
