# 仙剑奇侠传开发规范

开发前阅读[通用规范](common.md)、[复刻规范](recreation.md)、[存档规范](saved-games.md)、[界面规范](ui.md)、[控制器规范](controller.md)、[加载规范](loading.md)和[音效规范](audio.md)。

- 游戏 ID 为 `pal`，还原基准为《仙剑奇侠传 98 柔情篇》Windows 简体版。本次按用户确认的单人复刻范围实现，玩家操作全队，使用个人长期存档；不再开放多人席位。资源来源、版本与摘要保存在 `games/pal/assets/source-manifest.json`，参考源码只读使用。
- 仙剑按[即时游戏规范](realtime.md)开发。行走、对白、菜单、用物和战斗输入先在本地 Worker 执行同一已发布原版核心，再由服务端确认；不能只预测位置或光标。未确认输入最多 64 条，预测时长最多 1,000 毫秒；失步、拒绝和超时退回权威状态，清除过期操作，再按有效操作边界恢复。
- 本地执行使用独立控制代次和单调序号。普通菜单、对白或队员行动切换保留有序输入；保存、读档、接管和重新开始建立新控制代次。操作携带原版场景／菜单／对白边界，服务端只消费当前边界匹配的输入；未来边界最多等待 1,000 毫秒，不能把旧确认键执行到新剧情。
- 首次进入和失步恢复经既有鉴权同步接口传本人检查点，普通 WebSocket 只传新增规则操作、确认、摘要和必要公开信息。观众不取得原生内存。浏览器校验核心 SHA-256 和权威规则摘要，客户端不提交内存、物品、角色数值或结算结果。原始核心继续复用已发布 URL。
- 本次涉及的 TS／TSX、JS、Go、Python 和 CSS 文件通过[代码检查](../games/pal/LINT.md)，各语言配置分别校验命名、目录和禁止注释；规则说明放在文档，不写入代码注释。
- 游戏区域不得因控制器、状态文字或面板而缩小。普通页面优先保留原版比例的完整宽度，全屏使用可用区域保持比例放大。PC 和手机均不显示虚拟方向、确认、返回或「读完」按钮；手机直接在原版画面操作，不为触控分配额外高度。此项按用户最新要求执行，取代此前半透明覆盖按键的方案。
- 全屏的保存与退出入口同样悬浮覆盖，不保留工具栏行高或额外画面边距；沿用平台 `GameFullscreen` 的可选覆盖布局。验收须核对画布达到视口内原比例的最大尺寸，不能仅验证按键位于画布内。
- 对白通过点击或轻触游戏画面继续；键盘确认保留。一次手势只提交当前阅读位置，拖动、取消、多指缩放、保存和全屏操作不得误推进，旧手势不能跨剧情页或续档操作代次生效。人物周围点按控制原版四个方向，按住持续移动，松手、取消、失焦和禁用时释放。
- 场景波动遵循原版「地图、波动、人物／遮挡、界面」顺序，不能变形人物和对白。保留画面备份、保存后的相位及原版停止边界；完整验收须包含[原版像素对照和真实剧情页面](../games/pal/SCENE_WAVE.md)，不能只用独立场景夹具代替。
- 物理震屏在最终显示表面执行，整张逻辑画面的背景、人物和文字一起按原版奇偶位移，边缘填充原版调色板索引 0；不得移动页面、缩小画布或修改逻辑坐标。局部更新不消费震屏次数，且保留区域外的已显示画面；完整更新不累计旧显示依赖。原版渐变、剩余帧及显示图须可续档，按[震屏验收](../games/pal/SCREEN_SHAKE_TESTING.md)覆盖独立像素对照和真实剧情。
- 菜单和战斗直接命中原版文字、图标及目标；选择另一项与确认执行分开，长按返回，人物处长按或双指轻触可打开原版菜单。物品／法术列表保留滑动导航。操作只发送原版输入，不在客户端改写物品、目标或结算。验收覆盖对白、四向移动与释放、原版菜单／用物、全队选招、敌我目标和存档；见[画面直接操作](../games/pal/SCREEN_INPUT.md)。
- 保留原版人物、队伍聚散、场景、事件脚本、物品、养成与战斗规则。不以自编章节、占位地图或模拟器替代原版玩法。
- 隐藏物品、宝箱及可获得物品／金钱的支线均属复刻范围。按[隐藏物品清单](../games/pal/HIDDEN_ITEMS.md)核对原版位置、搜索条件、数量、提示、开启动画和领取后状态，验证取得前／取得中／取得后续档及防重复领取；宝物保持原版隐藏性。查漏优先使用带坐标、进入路线和触发条件的文字攻略，本次不再观看或分析视频。攻略须与原始事件表和脚本交叉核对，候选记录不代表实测完成。
- 防重复领取适用于原版一次性奖励。可重复商贩保留每次正常选择后的扣款与发货，存档恢复本身不得重放成交；条件资助保留原余额门槛、拒绝分支和次数上限。通过原版购物降低余额，不直接改钱或改库存；同一商贩或资助事件按一个点计数，不按购买或资助次数增加进度。
- 商贩的收费顺序按实际原脚本验收，不能统一假设游戏内答「否」不扣钱。苏州糖葫芦摊原脚本先扣 20 文、再询问，保留答「否」已扣款而不发货的行为；其选择中续档不得重新收费。原游戏内选择与平台取消请求分开处理，不在存档层改写原脚本结果。
- 原版可再生采集点保留每次新搜索的数量与条件，存档恢复本身不得额外发放。一次性物件的后续奖励按原续行逐段验证，再检查最终防重；不能为了统一验收而删除无限采集、箱底奖励或同点后续物品。同一事件的多次采集和后续奖励均不另增点数。
- 与采集道具同名的正常战斗掉落须独立记账。按实际参战敌人、原结束脚本、发放指令和实际提示核对，再将初始库存、搜索奖励与战斗掉落合并检查最终库存；不能删除原掉落或将其误判为隐藏点重复发放，正常战斗掉落不增加隐藏点计数。
- 战斗中召唤或变化的敌人同样按实际公开槽位的出现记录、原结束脚本和库存核对，不能只用开战编队推断掉落。保存召唤后与奖励提示中的原生状态，保留原版正常奖励及法术耗气。
- 原始数据中未启用或疑似不可达的奖励事件单独登记，保留原版数据与证据；不能为了提高收集数量挪动宝物、修改碰撞或将候选标为已经取得。多个物件共用奖励脚本时，须验证各自的领取状态独立保存。
- 原版队员由唯一玩家手动操作，保留剧情中的加入、离队和整队移动，不增加原版不存在的队员，不为队员分配额外平台席位。
- 原版脚本指定的临时参战队伍和自动战斗按脚本保留，不强行改成主角手动选招。角色编号不等于平台席位，也不一定唯一：例如苗人战斗使用 `[4,5,4]`；快照须保留数组槽位、顺序和进行中的自动战斗，不能去重、重开或额外注入选招。主角队伍的正常战斗继续手动操作。
- 剧情验收按用户最新确认，以开发加血流程通过为准；原版难度托管通关不再是本次交付门槛，不继续为此攻关。此条覆盖通用电脑规范中对本游戏原版难度完整托管的要求；保留单人手动操作和现有可选托管，接管及存档边界仍须正常。加血通过不能用来宣称原版体力下的托管通关，但可以计入剧情完成段数。
- 用户已授权仅在开发测试中加血。使用显式 `--test-battle-hp` 生成独立测试构建，按[开发测试说明](../games/pal/DEVELOPMENT_TESTING.md)隔离运行时、存档和验收产物；正式构建不开放此选项。正式游戏继续使用原版数值；加血流程记录作为本次剧情验收依据，测试构建及存档保持隔离。
- 战斗中的所有队员行动由玩家按原版菜单依次选择，保留原版合击和自动战斗，不设置轮换领队、队友同意或多人确认步骤；服务器负责输入、物品消费与原版结算。
- 战斗重连和前台恢复保留已加载画布。丢弃未送达的旧动作，服务器已接受的原版指令继续执行一次；按[战斗断线与后台恢复验收](../games/pal/BATTLE_RECOVERY_TESTING.md)核对实际画面、输入、耗气和奖励。
- 新核心按当前原版队伍、装备后合击、敌方能力及召唤依赖提示预备图集。提示只包含资源编号；本局可能使用的素材正文先按公共驻留规范完成准备，提示后的图集预备只从本地正文读取、解码，并限制并发。开局和续档计入原有就绪；进行中只等待当前浏览器的战斗输入，不回源下载、不冻结规则或重新触发全局加载。[密集动画验收](../games/pal/DENSE_BATTLE_TESTING.md)单独核对原序列和实际显示。
- 对话按原版操作推进；个人存档保存事件状态、脚本续行位置和阅读位置，重连不重播已完成剧情。单人界面不显示共同阅读计数、领队交接或等待队友文案。
- 电脑和托管使用与真人相同的操作接口与可见信息。单人手动控制全队是完整模式，不能强制由电脑代替操作其他队员。
- 按平台存档规范接入个人长期存档，仅本人账号可见和续玩，单人继续不等待其他玩家。保存原版脚本续行位置、阅读／菜单位置、随机状态和完整队伍；原生构建与资源版本标识必须校验，后续存在正式历史存档时，跨构建兼容通过前不得视为已完成发布验收。用户已确认 v1.62.0 发布前线上没有历史存档，本次不做旧版迁移，也不将历史存档兼容作为发布门槛；仍须验证当前版本保存、读档、账号权限和旧输入拒绝。
- 原生核心更新按[版本保留说明](../games/pal/NATIVE_VERSIONS.md)绑定真实核心／资源摘要，保留旧运行器。正式目录只接收同一规则配置的剧情核心；保留运行器验收不能代替正式资源发布和备份／回滚验收。
- 客户端图像、音频、地图与运行时遵循公共 OSS/CDN 发布流程。原始资源和本地研究目录不能进入正式服务器包；音源转换和播放时间线分别按[音频验收](../games/pal/AUDIO_TESTING.md)核对，转换通过不能代替主线播放或存档恢复通过。
- 验收按 `games/pal/ACCEPTANCE.md` 的当前单人范围执行。公共存档夹具、资源表解析和浏览器存档验收不代表原版仙剑游戏已完成；必须另有原版场景、全队操作、战斗与桌面／手机的可核验证据。此前多人验收仅作为历史研究记录，不作为当前交付要求。
- 剧情分段与进度以 `games/pal/STORY_PROGRESS.md` 为准。每完成一个阶段，按用户要求汇报「剧情进度 a/24」、完成内容、验证结果和下一段；功能工作单列，不增加剧情完成数。只有实际验收通过的完整剧情段才能计入，发现阻断问题时撤回对应完成标记。剧情全部完成后，按用户最新要求停止重复汇报剧情段数，只说明剩余工作、功能验收结果及需要复盘的内容。
- 隐藏点后续只汇报「已处理 b/c」，不再显示「已找到」。总数按当前奖励候选清单的去重事件点计算；已处理包括实际取得且通过存读档、防重复验证的点，以及有原始数据和独立出处确认、按原版保留的不可正常领取记录。两类分别留证，不能把不可达项算成已取得；同点重复验证不增加计数，新增条件分支或调整分母时须说明。
- 直接搜索清单未覆盖的道具使用条件奖励须另登记原始道具入口、面对目标判断、事件脚本切换、消费和奖励指令，再按事件 ID 合并去重；不改写已冻结的旧清单。不同接受／拒绝路线仍属同一事件，奖励附带学会法术不另计一点；每个已通过分支保留实际库存、菜单与续行证据。
- 触碰触发、战斗后交付及自动场景入口的支线奖励同样须核对。登记原触发事件、关闭条件、后续场景入口和奖励指令；同一完整事件链的多件奖励计一个事件点，不能按临时场景或物品数增加计数。临时单人和自动归队按原脚本时序保存，不为测试制造可停留的额外阶段。
- 原版道具放置和机关船须通过原菜单、原事件和当前阶段的靠岸位置执行，保留障碍切换、整队骑乘及途中续档，不能用固定传送替代多阶段水路。神像法术按原角色及队伍条件核对学习前后的完整法术表和实际菜单；同一物品事件的多条队伍分支去重，附带法术不另增物品点数。
