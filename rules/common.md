# 通用开发规范

游戏与专题规范的索引维护在 [AGENTS.md](../AGENTS.md)。文中代码路径以仓库根目录为基准。

本文件集中维护仓库的开发、验收和发布约定，适用于现有游戏及后续新增功能。

## 测试

- 不允许先编写实现代码，再补写单元测试。
- 复杂功能优先使用 E2E 作为验证机制，并保留可核验、可重复执行的测试记录或产物。
- 必须隔离测试时，先列出可能失败的场景，再编写代码。
- 简单、独立或低风险变更优先采用轻量级单元测试或针对性验证，不机械扩大 E2E 范围。

## 工作区

未经用户明确授权，不得创建、修改、移动或删除当前工作目录外的文件或目录。确有需要时，先说明目标路径、操作及原因，并获得授权。会话中已经明确授权的服务器更新等操作可在授权范围内继续执行。

每完成一款游戏或一个许愿交付，必须清理对应垃圾：删除临时构建、测试缓存（如 `__pycache__`）、浏览器临时 profile、失败日志、已合并的 subagent worktree／临时分支和不再需要的中间产物；只保留可核验的验收结果、截图和说明。不得删除用户素材、已发布 OSS 对象、数据库备份、其他游戏文件或仍在使用的 worktree。清理前确认路径属于本次工作，并在报告中说明清理范围。

## 检查和发布

- 正式发布必须由版本 tag 触发，Actions 运行记录的 ref 必须是该 tag，运行名称必须包含版本号。禁止用 `workflow_dispatch --ref main` 代替正式 tag 发布；手动恢复也须指定对应版本 tag。main 仅做检查和构建，tag 复用该提交的已验证产物。
- **main 按影响范围验证，游戏独立维护、独立验收。** 全局检查只覆盖公共平台、模块契约、公共前端、边界、编译及部署工具；不得因修改一款游戏而固定运行其他游戏的规则、完整对局或扩展组合矩阵。游戏前端／素材修改只运行对应游戏的前端／素材检查，操作改动另保留该游戏的本地 E2E 证据；服务端规则、规则测试及夹具修改才启动该游戏的规则、完整对局和竞态验收。遗留在公共目录的游戏专属测试也须按归属选择，不能用所在目录作为全量运行理由。
- main 的增量范围从最近已验证的祖先构建计算，覆盖被取消或失败的前序提交；首次无有效基线时建立完整基线。共享扑克牌呈现等有明确消费者的组件只关联对应游戏，不扩大到所有游戏。手动入口可指定单个游戏或显式选择全量验收；普通 main 提交不默认跑全部游戏。
- 所有本次必需检查通过后才生成可发布构建，并保存检查范围及结果产物。**tag 只做发布，不重复任何规则分片、完整对局或扩展组合矩阵。**
- **tag 只负责发布已经验证的构建。** 自动发布寻找同一提交 SHA 在 main 上已经通过的 `Test and Linux amd64 binary` 作业，复用其 `wire-board-linux-amd64` 产物，按 `Publish verified build` 的方式打包和发布；不重新编译应用。
- 保留必要的来源／SHA 绑定、产物校验和、容器启动及 SQLite 备份工具检查。缺少匹配的有效产物时停止发布，不能改用其他提交的产物或绕过失败的构建。
- `Publish verified build` 的手动入口可用于指定已验证的运行、提交与版本；历史 tag 构建产物迁移到该流程时，同样必须核对提交一致且构建作业成功。
- 版本 tag、Release、版本镜像和 `latest` 应对应同一发布提交。不得把已经发布的版本 tag 移到另一提交。
- 发布和服务器更新按用户在会话中的授权执行。更新服务器使用版本标签及既有备份／回滚脚本，核对镜像版本、健康状态和游戏上下架设置。
- 服务器空间有限。发布更新并完成健康、版本和上下架设置核对后，清理 `/opt/wire-board/backups/` 中的旧数据库备份，保留本次更新前备份和紧邻的上一份。先确认保留备份可读取，并使用更新锁避免与部署并发；只删除已识别的历史备份，不扩大到数据卷或其他服务文件。
- 同时使用 `/opt/wire-board/update.sh clean` 清理围桌的历史镜像，保留当前镜像、上一版回滚镜像及任何容器仍引用的镜像；不执行全局 Docker prune。清理后核对服务健康和剩余空间。

## 游戏上架

新增游戏默认上架，注册后即在玩家大厅和创建列表可见并允许创建；管理员可在后台显式下架。部署或发布不得覆盖已有游戏的管理设置。

## 和局与积分

- 真人对战和局时，所有参与者积分变化均为 0，不计胜场；保留对局次数、和局结果及历史记录。
- 游戏使用平台显式和局结果，不得把双方都标记为赢家来代替和局。含电脑的对局沿用平台不计分规则。

## 电脑玩家与托管

- 所有游戏必须支持电脑玩家和真人席位托管，覆盖该游戏开放的全部人数、队伍和规则模式。新增游戏不得把电脑支持留作后续功能，也不能只开放界面入口而缺少可完成对局的策略。
- 统一使用平台的添加电脑、托管和取消托管入口；策略、规则判断和合法行动留在各自游戏目录。基本电脑策略不依赖外部模型、付费 API 或额外服务配置。
- 电脑遵循与真人相同的规则和操作接口，只使用该席位可见的信息，不直接写入得分、胜负或物理结果。取消托管、重连和恢复存档不得重置对局、跳过动画或改变其他席位的操作期限。
- 验收须覆盖电脑完整对局、真人与电脑混合参与、托管与手动接管、特殊阶段及恢复存档，保存可重复执行的测试和结果。所有游戏同时支持 PC 鼠标／键盘和手机触屏，不能以支持电脑玩家替代桌面交互适配。
